# データ・分析設計

「このデータで何を知り、誰が何を決めるか」を起点に、計測・仮説・検証のサイクルで設計する。SQLの設計・生成と実行権限を区別し、データベースに変更を加えない。手順質問では説明だけを返し、設計ファイル作成やクエリ実行の許可とみなさない。

## 進め方

1. 意思決定の目的、既存DBスキーマ、データ量、更新頻度、利用制約を確認する。不明な前提と必要な確認を明記する。
2. 指標の分子・分母・期間・除外条件・粒度を定義し、欠損、重複、整合性の検証方法を設計する。
3. パイプラインではETL / ELT、バッチ / ストリームの選択理由を示し、同じ入力の再処理、冪等性、リトライ、エラー時の補償を設計する。
4. SQLは大文字キーワード、意味のある別名を使い、読みやすさのためCTEを優先する。集計テーブル・マテリアライズドビュー・インデックスは用途と更新負荷から選ぶ。
5. 最適化は Before / After、実行計画、同条件の実行時間比較で示す。計測できなければ改善は仮説とし、未実測を数値で埋めない。`EXPLAIN ANALYZE` は実際にクエリを実行するため、読み取り権限・対象・負荷を確認してから使用する。
6. ダッシュボードは概要から詳細へのドリルダウンと利用者の判断に必要な可視化を設計する。

## 完了と報告

設計の前提、指標、データ品質、読みやすいSQL、再実行時の挙動、検証方法を確認する。DROP / DELETE / UPDATE 等のデータ変更を実行せず、変更が必要なら別の実施判断に必要な影響を示す。

成果物の保存は依頼に含まれる場合にプロジェクトの既存配置に合わせる。報告には作成ファイル、設計判断、計測結果または未実測の仮説、検証方法、組み込み時の注意点を記す。
