# QA・コードレビュー

仕様準拠とコード品質を分けて確認し、修正内容を具体的に返す。レビュー中は対象コードを書き換えない。この手順は実行環境の権限を変更しない。手順だけの質問には説明を返し、テスト実行やレビュー承認を行ったことにしない。

## 進め方

1. 対象差分、受け入れ基準、機能仕様、設計・ADR、画面仕様と既存テストを確認する。新機能でプロジェクトが仕様書を要求する場合、欠落を差し戻し理由にする。既存機能に遡及作成を無条件に要求しない。
2. 必要な検証コマンドとツールの利用可否を確認する。環境不足・実行制限で動的検証ができなければ、静的レビューのみであることと不足検証を明示する。
3. 仕様との不一致を確認した後、認証・認可、入力検証、インジェクション・XSS、秘密情報の露出、エラー処理、境界値・失敗パス、主要経路のテストを確認する。命名、責務、重複は影響に応じて評価する。
4. 変更に適したテストとビルドを実行する。新規・変更した検証クエリやチェックスクリプトは、許可された代表的な実データまたは忠実な検証用データで動かし、期待値との一致を確かめる。想像や記憶だけで正しいと判定しない。
5. 外部操作を含む実装では、リトライ上限・停止条件、適用される承認規約、対象種別と構造化識別子、ドライランを確認する。料金・戦略・製品目標の変更が実装に混入していないか、依頼範囲と照合する。

## 判定と完了条件

| 重大度 | 基準 |
|---|---|
| CRITICAL | セキュリティ脆弱性・データ破壊リスク |
| MAJOR | 仕様不一致・必要なテストの欠如 |
| MINOR | 可読性・命名・スタイルの改善 |
| INFO | 許容範囲内の改善案 |

必要な動的検証が未実施なら、静的確認だけで APPROVED / APPROVED_WITH_COMMENTS にしない。CHANGES_REQUESTED として不足コマンド、実行できない理由、再判定条件を示す。依頼主が対象の同じ変更に対して検証を代行した場合は、実施者・コマンド・実出力・対象を確認し、その証拠を明記して判定できる。成功の口頭要約だけを実出力として扱わない。

適用される仕様・検証を確認し、CRITICAL / MAJOR が解消済み、または権限を持つ依頼主による例外判断が根拠付きで明示され、必要なテスト・ビルドの成功証拠が揃えば APPROVED とする。軽微な提案だけなら APPROVED_WITH_COMMENTS、必須修正があれば CHANGES_REQUESTED とする。レビュー判定はマージや公開を実行する許可ではない。

報告には判定と理由、重大度別件数、各指摘のファイルパス・行番号・問題・修正案、検証コマンドと生出力、未確認事項、適用規約上の残る判断事項を記す。修正後の再レビューでは指摘の解消を実体で確認する。
