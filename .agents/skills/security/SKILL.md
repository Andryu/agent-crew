# セキュリティレビュー

対象の実装と設計を読み、成立条件・影響・修正案を根拠付きで報告する。対象は修正しない。この手順はスキャンや外部サービス利用の権限を追加しない。手順質問には説明だけを返し、実際の安全性判定やスキャンを行ったことにしない。

## 確認手順

1. 対象範囲、設計、信頼境界、認証・認可経路、利用言語と依存関係を確認する。
2. アクセス制御、認証・セッション管理、暗号化、インジェクション、安全でない設計、設定ミス、脆弱な依存関係、ソフトウェア・データの整合性、ログ不足、SSRFを点検する。OWASP分類番号を使う場合は適用する版と公式資料を確認し、未確認の番号を付けない。
3. 秘密情報のハードコード、環境変数・シークレットの扱い、ログやレスポンスへの漏洩を確認する。報告には秘密値自体を転載しない。
4. Goではセキュリティ用途の乱数が `crypto/rand` 等の適切な生成源か、SQLやコマンドを未検証入力から組み立てていないかを確認する。乱数の全用途をセキュリティ用途とみなさない。
5. 依存一覧とバージョンを取得し、適切な脆弱性スキャナまたは信頼できる勧告と照合する。`go list -m all` は一覧取得であり、単独ではCVEチェックにならない。対象環境で利用できる検査方法・適用範囲を確認し、必要な通信が許可されている範囲で実行する。
6. 設定監査が依頼範囲に含まれる場合、対象プロジェクトの監査方法を読み、権限設定や参照切れなどを検査する。特定の運用イベントを理由に自動実行しない。

## 判定と報告

| 重大度 | 影響の目安 |
|---|---|
| CRITICAL | 認証バイパス、重大なインジェクション、秘密情報漏洩 |
| HIGH | 高影響の依存脆弱性、危険な暗号利用 |
| MEDIUM | セッション管理不備、不適切なエラー露出 |
| LOW | 攻撃準備に利用され得る限定的な情報露出 |

重大度は名称だけで決めず、到達可能性・成立条件・実際の影響を示す。CVE / CWE は確認できる場合にのみ添え、スキャナの検出と対象での悪用可能性を区別する。

報告には APPROVED / CHANGES_REQUESTED、重大度別件数、場所・問題・根拠・修正案、検査コマンドと実出力、依存情報の照合先と確認時点、未確認範囲を含める。必要な検査が未実施なら承認せず、検証不足と解消方法を示す。CRITICAL / HIGH が残る場合は差し戻すか、依頼主による明示的なリスク受容の根拠を記す。検出ゼロを安全性の保証にしない。
