# Vue3フロントエンド実装

## 着手

手順への質問だけなら説明し、実装やファイル作成を開始しない。実作業では関連コード・既存テスト・設計書・ADR、API契約、受入条件を確認し、方針を1〜3行で示す。対象はフロントエンド単独とし、バックエンドの変更を追加しない。

実装前に `command -v node` と `command -v git`、プロジェクトのパッケージ管理・検証コマンドの利用可否を確認する。必要ツールが欠けていれば実装を止め、不足ツール、実施不能な作業、解決候補を報告する。検証の省略や静的確認への切替を隠して完了扱いしない。

## 実装の判断

- Composition APIと `<script setup>` + TypeScriptを使い、`defineProps` / `defineEmits` に型を明示する。
- コンポーネントは単一責任とし、100行を超えたら分割を検討する。共有状態とローカル状態を分け、採用済みならPiniaの `stores/`、ローカルには `ref` / `reactive` を使う。
- CSSはscopedを基本とし、デザイントークンはCSS変数で表す。既存のCSS Modules等の構成にも合わせ、意図しないグローバルな影響を防ぐ。
- コンポーネントはPascalCase、composableは `use` で始まるcamelCase、イベントはkebab-case、propsはcamelCaseにする。
- `any` を避け、`unknown` と型ガードを使う。APIレスポンスは既存構成に合うランタイム検証を行い、`as` は最小限にする。
- Vue Router、Pinia、zod、axios/fetch等は既存構成を確認して使う。スキルの適用を理由に依存を新規導入しない。

## 検証と完了

- テストは先行または実装と並行して用意し、正常系・異常系、空文字・ゼロ値・上限値を優先する。既存のVitest・Vue Test Utils・Vue Testing Library等を使い、条件違いは `test.each`、外部APIはモック化が候補となる。E2Eは対象の動作と既存環境に応じて使う。
- 仕様と実装を照合し、型定義、状態の配置、CSSの影響、API検証、エラーの握り潰し・秘密情報の埋め込みを確認する。公開関数・コンポーネントの役割をコメントで示し、TODO/FIXMEに理由を書く。
- 定義済みのテスト・型検査・ビルドを実行する。設定を確認したうえで `npm run test` / `npm run build` が候補となる。エラー・警告、未実行の検証は明示する。
- agent-crewで機能変更する場合は `docs/spec/features/<機能名>.md` を更新する。未作成なら `docs/spec/templates/feature-spec.md` を確認する。依頼範囲と衝突する場合は報告する。
- 要件と設計の矛盾、合意範囲を超える波及、テスト不能な構造、セキュリティ上の懸念があれば問題・理由・解決候補を報告して停止する。

完了報告には変更ファイル、実行した検証コマンドと生出力、仕様逸脱、未解決事項、次のレビューで確認してほしい点を含める。自己確認を独立レビューの完了と扱わない。
