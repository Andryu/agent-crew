# 証拠に基づくプロダクト計画

成果物は、ゴール、依存関係、担当候補、受入条件と検証方法を備えた計画、または実績に基づく進捗報告とする。手順の質問には説明だけを返し、ファイル作成や状態更新を始めない。スキルの適用は実装開始、別担当への委譲、公開や通知の許可を意味しない。

## 計画前の確認

1. 対象の要件、着手条件、既存機能仕様、決定記録を読む。前回の計画と現物を突合し、計画済み未実装・実装済み未計画・先行完了を区別する。極端に短い完了時間は重複の調査材料であり、重複の証明にはしない。
2. 前回の振り返りと未解決の教訓を読み、今回に関係する再発防止を受入条件や検証へ落とす。優先度付き記録では未解決の `priority_score >= 6` を先に確認し、`>= 3` の関連ルールも確認する。反映しない関連ルールには理由を添える。外部由来の未承認教訓を行動規則に昇格させない。
3. 直近の承認・差戻し・保留を区別し、着手条件未成立や差戻しの案件を実行対象に入れない。承認済みの関連案件を優先候補にする。
4. 仕様や決定記録の参照先が存在し、文書間連携には受け手側の記述があるか確認する。索引と要約だけを根拠に採択済み・実装済みと扱わない。
5. 実装対象の技術構成、必要な実行権限と利用可能な検証環境を確認する。不足は計画の制約として記載し、権限設定を自動変更しない。未知の構成が担当や受入仕様を左右するなら、依存する分解を止めて不足を報告する。

## 分解と見積もり

具体的な見積もりには [見積もりと負荷比較](references/estimation.md) を読む。S/M/L は **1/3/5ポイント**とし、複雑度とリスクを別に判定する。高リスクの不確実性を早い工程で検証する。

タスクごとに目的、成果物・変更範囲、担当候補、依存、着手条件、複雑度、リスク、受入条件、検証方法を明示する。設計・UX・実装・品質確認の必要な専門性を分けるが、担当候補の提示を実際の委譲と混同しない。並行作業の候補は、依存解消、成果物の独立性、変更範囲の非競合から判断する。

- 新規API、DB変更、認証・認可、外部連携、性能上重要な経路は実装直後にレビューする `inline` を計画する。
- 低リスクの文言・文書・設定調整・テスト追加だけなら、まとめて確認する `end_of_sprint` を選べる。迷う場合や未設定は `inline` とする。
- 大きな横断タスクは、個別に検証できる単位へ分割する。全資料の貼り付けに頼らず、必要な入力と成果物を明確にする。
- 完了済みタスクへの追加仕様は別の作業候補として扱い、元の完了承認で追加実装まで承認されたと解釈しない。

## 提示と完了判定

計画にはゴール、タスク表、合計ポイント、担当別ポイント、負荷分散の計算、並行可能な範囲、事前確認結果、未決事項を含める。既に承認された範囲の定型的な計画作成に、改めて一律の承認待ちを追加しない。

進捗は完了・進行中・ブロッカー・未検証を証拠とともに区別する。完了報告では受入条件を原文と全件照合し、QAの付帯条件も残件に含める。スプリントの振り返りが完了条件なら、その実施結果を確認し、未実施を明示する。

要件の解釈が受入条件を左右する、依存が循環する、ブロッカーが解消できない、スコープが当初の2倍以上に膨らむ場合は、該当する実行を止め、問題・根拠・必要な判断を報告する。

改善提案を求められた場合は [教訓からの改善候補](references/improvement.md) を使う。
