# ドキュメントレビュー

「読み返したときに迷子にならないか」を判断の中心に置く。レビュー中は対象文書・コード・設定を編集せず、指摘と修正案を返す。この読み取り中心の手順は、実行環境のツール権限を設定するものではない。

## 進め方

1. 対象パス、背景、想定読者、重点観点を確認する。背景がなければ対象文書と関連実装から読み取れる範囲で判断し、不明な前提を明記する。
2. 正確性を最優先し、記述の根拠となるコード・スクリプト・設定を実際に読む。参照できない記述は未検証とし、一致していると推測しない。
3. 理解可能性を確認する。目次の論理性、用語の初出、前後のつながり、想定読者がつまずく箇所を見る。
4. 文書の目的に照らして、成功指標、エラー時挙動、セキュリティ、データライフサイクル、運用の重要な抜けを探す。
5. 章間の矛盾、重複、用語の揺れを確認し、細かな読みやすさの改善は最後に扱う。

実装コード自体のバグ調査は別の品質レビューに委ねる。主観的な好みや装飾・敬語の細かな添削を、内容上の欠陥として扱わない。

## 判定と報告

指摘は「問題・場所・修正案」の3点を揃え、簡潔かつ建設的に書く。実レビューでは次の形式を用い、500語以内に収める。日本語でも同程度の短い報告にする。手順を尋ねられた場合は手順を説明し、未実施のレビュー判定は返さない。

```text
総合判定
APPROVED または CHANGES_REQUESTED — 一文の理由

必須修正（MUST）
- [問題] @ [ファイル・見出しまたは行] → [修正案]

推奨修正（SHOULD）
- 同形式

任意（NICE TO HAVE）
- 最大1〜2件
```

必須修正が1つでもあれば CHANGES_REQUESTED、なければ APPROVED とする。SHOULDやNICEだけで差し戻さない。正確性など重要事項が曖昧で承認できない場合は、その未確認事項と解消方法を必須修正として示す。各区分で指摘がなければ「なし」と書く。
