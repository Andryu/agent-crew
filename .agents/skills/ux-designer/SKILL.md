# UX仕様の設計

「誰が・何を・なぜしたいか」を起点に、実装者が仕様書から判断できる粒度で体験を定義する。手順への質問だけなら説明し、仕様書の作成やUI実装を開始しない。

## 作業手順

1. ユーザーストーリーと対象タスクを整理し、既存の画面・ドメイン設計・用語を確認する。
2. 画面遷移と状態遷移を図またはMarkdownで示す。各遷移に操作・条件を添え、送信成功・入力不備・通信失敗などの分岐と復帰先を定義する。
3. 画面ごとに主要なアクションを明確にし、同時に求める判断を減らす。小画面から大画面への配置変化を考える。
4. 各コンポーネントについて以下を記載する。
   - 目的、入力名・型・必須性・説明。
   - 状態名、遷移のトリガー、見た目の変化。通常・空・ローディング・エラー状態を含める。
   - ユーザー操作と結果、エラー条件と具体的なメッセージ、回復方法。
   - アクセシビリティ上の配慮。キーボード操作、ラベル、フォーカス、状態の伝達など対象操作に必要な事項。
5. 指定された保存先・既存規約に従ってまとめる。指定がなければ `docs/ux/<slug>-ux.md` を候補にする。

## 完了条件と報告

対象ユーザーフローの正常系・エラー系、全コンポーネントの状態、空・ローディング・エラー表示が揃い、実装者が重要な動作を推測せず実装できることを確認する。「エラーが発生しました」だけの表示で済ませず、何が起きて次に何ができるかを具体化する。

受入条件に関わるドメイン動作や遷移が未定義なら、問題・影響・解決候補を報告して停止する。完了時は作成ファイル、画面・コンポーネント一覧、実装時の注意点、自明でない設計判断と理由、未決事項を報告する。
