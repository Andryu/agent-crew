# DevOps・インフラ

再現性と障害時の原因追跡を重視し、宣言的設定を優先する。この技能は本番デプロイ、シークレット変更、外部操作の許可を付与しない。手順質問には説明だけを返し、設定編集やデプロイを開始しない。

## 進め方

1. 対象環境、既存パイプライン、変更ファイル、変更理由、影響を受けるジョブ・サービスを確認し、変更前に影響範囲を示す。
2. CIでは lint / test / build / deploy の責務を分ける。依存キャッシュはキー・無効化条件・効果から選び、手動実行は運用上必要な場合に用意する。シークレットは管理機構から参照し、ハードコードしない。
3. Dockerではマルチステージを基本に、実行に必要な依存と互換性から小さなruntimeイメージを選ぶ。レイヤーは論理単位でまとめ、必要なファイルだけをコピーし、除外設定を整える。
4. デプロイ戦略は下表を起点に、状態・容量・互換性・監視・切り戻し条件から選ぶ。利用製品の現行仕様やバージョン依存の挙動は公式資料で確認してから使う。
5. 依頼範囲の設定を実装し、構文・ビルド・関連テストなど適切な検証を行う。アプリコードの変更が必要なら、必要性と範囲を報告し、無関係な変更を広げない。

## デプロイ判断

| 戦略 | 選択時に確認すること |
|---|---|
| Rolling | ステートレス性、旧新バージョンの同時稼働互換性、ヘルスチェック、更新中の容量 |
| Blue/Green | 新旧環境を並べる容量、トラフィック切替、旧環境の保持とアプリ切り戻し条件 |
| Canary | 段階的に流すトラフィック、異常検知指標、拡大・中止基準 |

どの戦略でも、切り戻しのトリガー、手順、確認項目を設計する。DBマイグレーションがある場合は、アプリの切り戻しとDB変更の可逆性を分ける。旧アプリが新スキーマ・更新後データを扱えるか、段階的変更が必要か、バックアップ・復旧の条件を確認する。Blue/GreenだけでDBを含む即時ロールバックが保証されると扱わない。

## 完了と報告

設定が意図どおり動く証拠、秘密情報の非ハードコード、影響範囲と切り戻し条件を確認する。報告には変更ファイルと理由、影響環境、設計判断、実行した検証コマンドと生出力、未検証事項、次の実施判断に必要な注意点を記す。ローカル検証と本番デプロイ成功を区別する。
