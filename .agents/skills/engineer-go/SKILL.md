# Go / Vue3 実装

正しさ、読みやすさ、計測に基づく性能改善の順に判断する。「動く」だけでなく、次の人が読んで理解できる実装を目指す。

## 着手と範囲

1. 着手条件と受入要件を確認し、未成立の条件があれば実装を開始せず報告する。
2. 関連コード、既存テスト、設計書・ADRを確認する。検索で関数・定義を絞り、大きなファイルは必要部分を読む。
3. 実装方針を1〜3行でまとめ、テストを先行または実装と並行して用意する。
4. 設計と要件の矛盾、合意した範囲を超える波及、テスト不能な依存構造、セキュリティ上の懸念に遭遇したら、問題・理由・解決候補を報告して停止する。大きすぎるタスクは分割を相談する。

進め方への質問だけなら手順を説明し、実装・ファイル作成を開始しない。

## Goの判断基準

- パッケージは `internal/` を基本とし、外部公開が必要なものだけ `pkg/` に置く。
- エラーは `fmt.Errorf("context: %w", err)` で文脈を付け、原因を保持して伝播させる。握り潰さない。
- `context.Context` を受け取る場合は第一引数にする。
- インターフェースは利用側で定義する。DB・HTTP・ファイル等の外部依存を差し替え可能にする。
- goroutineには終了の責任を明示する。キャンセルや `WaitGroup` 等で終了を扱う。
- テーブルドリブンテストを基本とし、カバレッジ数値より境界値・エラーパスを優先する。外部依存はインターフェース経由でモック化する。既存構成に合えば `testify/assert` を使ってよい。

## Vue3の判断基準

- Composition APIと `<script setup>` を使い、`defineProps` / `defineEmits` に型を明示する。
- コンポーネントは単一責任とし、100行を超えたら分割を検討する。
- グローバル状態はPinia、ローカル状態は `ref` / `reactive` を使う。
- CSSはscopedを基本とし、デザイントークンはCSS変数にする。
- コンポーネント名はPascalCase、composableは `use` で始まるcamelCase、イベントはkebab-case、propsはcamelCaseにする。
- `any` を避け、必要なら `unknown` と型ガードを使う。APIレスポンスは既存構成に合うランタイム検証（例: zod）を行い、`as` は最小限にする。

## 完了前の確認

- 要件を実装と照合し、未実装項目を隠さない。TODO/FIXMEには理由を書く。
- 正常系・異常系と空文字・ゼロ値・上限値を確認する。秘密情報のハードコードがないことを確認する。
- 新規公開関数・コンポーネントには役割がわかるコメントを付ける。
- 対象プロジェクトで定義されたテスト・ビルドを実行する。Goなら `go test ./...` / `go build ./...`、Vue3なら設定を確認したうえで `npm run test` / `npm run build` が候補。対象外の言語のコマンドは実行しない。
- ビルドのエラー・警告を確認し、残る場合は報告する。実行できない検証を成功扱いしない。
- agent-crewで機能を変更するときは `docs/spec/features/<機能名>.md` を更新する。存在しなければ `docs/spec/templates/feature-spec.md` を確認して作成する。今回の依頼範囲や規約と衝突する場合は報告する。

完了報告には変更ファイルと変更内容、実行した検証コマンドと生出力、設計からの逸脱・未解決事項・次のレビュアーに確認してほしい点を含める。実装者の自己確認と独立したレビューは区別する。
