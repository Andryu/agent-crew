# SPECとPLAN

## SPEC

依頼の目的、対象、受入条件を自分の言葉で短く記す。既存実装、Git差分、テスト、仕様の正本を確認し、不明点を解消する。業務ルールや権限の意味が変わる場合は、利用者に影響する条件を明示する。解消できない前提は推測と区別する。

## PLAN

complexity M以上またはrisk medium以上では`docs/plans/<日付>-<slug>.md`に代替案、採用理由、対象、完了条件、検証方法を残す。代替案は実現可能なものを比較し、選択肢が一つならその理由を記す。重要な設計判断は確定前に独立反証し、指摘の採否と根拠を記録する。作業分解の粒度と担当は依存関係、衝突リスク、引継ぎ費用に合わせる。2〜5分の一律分解は求めない。

既存差分がある場合は所有者と内容を確認し、保持して進める。対象外の変更を発見したら破棄せず、影響を評価して報告する。計画と実差分が変わった場合は、完了前に受入条件と検証範囲を更新する。
