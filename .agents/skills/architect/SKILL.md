# システム設計

業務上の問題と制約から設計し、抽象化の複雑さに見合う理由を示す。手順への質問だけなら説明にとどめ、設計書の作成や実装を開始しない。

## 設計の進め方

1. 要件、既存設計・実装、非機能要件を確認する。ドメインの用語、イベントとコマンド、主要エンティティ、不変条件を整理する。
2. 集約と境界づけられたコンテキストを定め、境界間の依存方向と責任を示す。DB設計ではエンティティ間の関係と制約、API設計ではエンドポイントと入出力・異常時の契約を具体化する。
3. 主要な構造の判断には少なくとも2案を比較し、採用理由と失うものを記録する。小規模チーム・境界未確定ならモジュラーモノリス、独立したスケールや明確なドメインが必要ならマイクロサービス、非同期処理ならイベント駆動、読み書きの非対称性が強ければCQRSを候補にする。単純なCRUDへ複雑な仕組みを追加しない。
4. スケール、障害モードと回復、保守性、観測可能性を評価する。変更を戻しやすい案を優先し、将来の拡張は現在の要件との関係で説明する。
5. 必要な粒度の構成図とADRへまとめる。ADRには状態、背景、比較した選択肢、決定、利点・不利益を含める。保存先は既存規約に従い、規約がなければ `docs/adr/`、`docs/design/`、必要なスキーマは `docs/schema/` を候補にする。

## 完了前の整合性確認

- 正常系だけでなく条件分岐、異常系、既存ガードとの相互作用、チェック順序を実装と突き合わせる。
- 背景、データモデル、コード例、テスト手順、チェックリスト間に矛盾がないか読み直す。新制約が既存サンプルやテストの前提を壊さないか確認し、矛盾は提出前に修正する。
- 対象範囲のエンティティ・関係・API契約とUX側が必要とするドメイン概念が揃い、実装者が推測で重要な仕様を補わず着手できる状態にする。
- 受入条件や安全性を左右する未定義事項は、問題、影響、解決候補を報告して停止する。

報告には作成ファイル、主な決定と理由、整合性を確認した根拠、実装・UXへの注意点、未決事項を含める。提案段階のADRを承認済みと扱わない。
