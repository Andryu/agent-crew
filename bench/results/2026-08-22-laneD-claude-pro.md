## 結論（表現を訂正）: この6問では能力差を検出できず、先に枠が制約になった

**測定できた5問（易1・中2・難2）はすべて満点**、品質減点もゼロ。難問10（症状から根本原因を
特定する問題）と難問12（出力の完全一致を要する問題）を Sonnet が満点で解いた。

⚠️ **「能力差がゼロ」とは言えない。** 上位3レーン（Opus / Codex / Sonnet）が全問で天井に
張り付いており、**このベンチが上位モデルを弁別できていない（benchmark ceiling）**可能性が高い。
正確に言えるのは「**現在の個人ベンチでは Sonnet / Opus / Codex の能力差を検出できなかった。
一方 Claude Pro では利用上限が先に制約になった**」まで。

**差は枠に出た。** 初回のバッチ実行では6問目（難問12）の途中で
`You've hit your session limit · resets 12:50pm (Asia/Tokyo)` に到達。
**Max では6問を余裕で完走できたが、Pro では5問強で5時間枠が尽きた。**
枠リセット後に再実行したら満点だったので、これは能力ではなく容量の問題。

→ ADR-018 の「実装を Codex に外出しする」判断を支持する根拠は、**能力差ではなく枠の消費速度**。
能力面については本ベンチでは何も言えていない（弁別できていないため）。
Claude Pro は判断・設計・critic・Notion/Artifact/Chrome に温存する。

## タスク03 が測定不能だった理由（ハーネス比較としての発見）

`.claude/hooks/task_completed.sh` を新規作成する課題。3通り試してすべて拒否された:

1. デフォルト権限 → 拒否
2. `--allowedTools "...,Write(.claude/**)"` → CLI が明示エラー:
   **「`Write(path)` 形式はファイル権限チェックに使われない。`Edit(path)` を使え
   （Edit ルールが全ファイル編集ツールをカバーする）」**
3. `Edit(//<workdir>/**)` ＋ `~/.claude.json` でワークスペースを信頼 → **それでも拒否**

`.claude/hooks/` は**自動実行されるスクリプトの置き場**であり、Claude Code が自動承認モード
（acceptEdits）では書き込ませない安全機構を持っていると判断する（設定で緩められない類）。
エージェントが自分の実行フックを書き換えられない設計はむしろ正しい。

**同じ「Claude」でも実行形態で解ける課題が変わる**という実データ:

| ハーネス | 権限モデル | タスク03 |
|---|---|---|
| Opus（Claude Code サブエージェント） | セッションの権限を継承 | 9/9 |
| Codex CLI | `--sandbox workspace-write` | 9/9 |
| **Claude Code headless (`-p`)** | `--allowedTools` が厳密＋hooks は保護 | **不可** |

### ベンチ側の課題

- タスク03 は `.claude/hooks/` を触るため、**ハーネスによっては構造的に解けない**。
  レーン間比較から除外するか、対象パスを `hooks/` 等に変えることを検討する
- レーンごとの権限設定を揃え、**「モデルの能力」と「ハーネスの設定」を分けて記録**する
