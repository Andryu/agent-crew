## わかったこと

- **3,071 バイト（32行）のパケットで足りた。** 会話履歴は不要
- 生成されたパケットの質が高い要因:
  - 「動作確認済み」に**失敗も書いた**（smoke.sh が `unknown command` で落ちるのは想定内、と明記）→ 受け側が誤って直そうとしない
  - **環境固有の罠を落とし穴に記録**（この環境には `flock` が無く fallback 経路が使われる）→ 会話にしか無かった情報が残った
  - 次の一手を `jq` の式レベルまで具体化 → 受け側が方針を再発明しない
- 後半は「検証方法」に書かれたコマンドを自分で実行して完了判定した

## 実装メモ

- `run_task.sh --score` は満点以外で非ゼロ終了するため、呼び出し側で `{ ...; } || true` が必要
  （`set -euo pipefail` 下で親スクリプトが停止するバグを踏んだ）
- 前半の停止指示は「N分ぶん、または課題の半分程度で止めて」で機能した（中間 56%）

### 実験2からの学び

- **「おおよそN分／半分程度で止めて」では Sonnet は止まらない。** タスク07（中難度）を
  完成させてしまい、中間スコアが既に満点になった。停止指示を
  「**全要件を満たす前に、全テストが通る前に必ず打ち切る**」へ変更（run_handoff.sh を修正）
- 運用の観点ではむしろ朗報（枠が続く限り完成させる）だが、**実験としては停止を機械的に
  制御する必要がある**。将来は「N ツール呼び出しで打ち切る」等のハーネス側の制御が望ましい
- **パケットの厚みにハーネス差が出た**:
  - claude/sonnet-5: 64行 4,712 bytes。検証済み項目を8つ列挙（閾値ちょうど・jq不在・実ファイル不変など）
  - codex/gpt-5.6-sol: 32行 3,071 bytes。簡潔だが必要十分
  - どちらも6節の書式は守れた。**「作業状態を渡す」設計はハーネス非依存で成立している**
- 例として `bench/handoff/example-05-codex.md` と `example-07-claude.md` を保存

タスク12（難問・抽出条件の一元化）。停止指示を強化した版で実施し、**前半が意図通り
途中で停止**（60%）。パケットは 92行 / 6,432 bytes ≈ 1,300トークン（仕様の2,000以内）、
6節すべてを充足。後半は**会話履歴を一切受け取らず**にパケットとリポジトリの現状のみで完成。

### 結論

- **「モデル／ハーネスを切り替えても仕事が続く」は実証された。**
  - 同種（codex→codex, 中難度）: 5/9 → 9/9
  - **異種（claude→codex, 難問）: 6/10 → 10/10**
  - いずれも単独実行時のスコアと同じ＝**引き継ぎによる損失ゼロ**
- 渡したのは会話ではなく**作業状態 1〜1.3千トークン**。実測で入力の96%を占める cache_read を
  再送しないため、**切り替えコストが構造的に小さい**
- パケットのサイズは難度に比例（中難度 3.0KB → 難問 6.4KB）。仕様の2,000トークン上限は
  この範囲では妥当

### 運用への含意

Claude Pro の週次上限に当たったら、**引き継ぎ書を書かせて Codex に渡せば作業は続く**。
枠切れは事故ではなく設計の一部にできる。次は Hermes の cron から自動でこれを起こす
（枠切れ検知 → パケット生成 → 別ハーネス起動）。

### 残る検証

- **hermes(ローカル gemma4) → claude**: 無料で下ごしらえ→クラウドで仕上げ。
  クラウド枠の構造的削減になるか（要 gemma4-64k 作成・Hermes 非対話起動の確認）
- 逆向き（codex → claude）
- パケット書式を変えたときの成功率差（②「育てる」の対象）

## 実測4（ローカル前半・失敗）

| # | 前半 | 後半 | 中間 | 最終 | 評価 |
|---|---|---|---|---|---|
| 4 | hermes/gemma4-64k（ローカル） | claude/sonnet-5 | **2/9 (22%)** | **9/9 (100%)** | **前半が機能せず**／後半は自力で回復 |

### 何が起きたか

- 前半は **1,500秒（25分）でタイムアウト（exit 124）**。**ソースの変更ゼロ、パケットも生成されず**
- 中間スコア 2/9 は**未解答ベースラインと同値**＝実質何もしていない
- 単純な疎通（`echo` を実行して報告）は3分25秒・2 tool calls で**成功していた**ので、
  tool calling 自体が壊れているわけではない。**実タスクの多段推論で完走できない**

### 含意（設計判断）

- **24GB / gemma4:12b では「前半の下ごしらえ」すら任せられない。** Raschka の実測
  （Gemma 4 E2B が tool calling 0/5）や「dense/小型は多段で崩れる」という報告と整合
- したがって **「無料のローカルで下ごしらえ → クラウドで仕上げ」は、この機材では成立しない**
- ローカルに残る役割は当初の想定通り **①資産データのローカル処理（ADR 0002 で外に出せない）**
  **②Slack 窓口・cron の意図分類** に限られる。コーディングの前半は不可
- **代替**: 探索・列挙・下読みは **Gemini CLI の無料枠（1,000 req/日・1M ctx）** に寄せる方が
  速く・賢く・電気代もかからない

### タイムアウトの扱い（ベンチ側の改善点）

前半がタイムアウトしてもパケットが残るよう、**ハーネスに「残り時間」を渡して自己申告で
打ち切らせる**か、**タイムアウト時に外部からパケット生成だけを別途走らせる**仕組みが要る。
現状は「落ちたら何も残らない」ため、実運用（枠切れ検知→引き継ぎ）では**枠切れ前に
余裕を持って起動する**必要がある。

### 後半の回復（実測4の続き）

前半が完全に失敗（パケットなし・変更ゼロ）した状態から、後半の claude/sonnet-5 が
**2/9 → 9/9 (100%)** に回復した。引き継ぎ書が存在しないため、後半は課題文とリポジトリの
現状のみで解いたことになる。

**含意**: 引き継ぎ機構は「パケットが無い」最悪ケースでも劣化しない（＝課題文が残っていれば
後半は単独実行と同じ）。パケットは**あれば時間を節約する**もので、無いと詰むものではない。
ただし実験1・3で見た通り、パケットがあれば前半の成果（56〜60%）を捨てずに済む。

限られ、24GB のローカルは対象外。
