# adversarial 第1弾: `-vague` 版で ceiling を破れるか（2026-08-22）

## 仮説

既存6問は上位3レーン（Opus / Codex / Sonnet）が全問満点で、**benchmark ceiling** により
モデル間の弁別ができていない。**受け入れ基準を削って「困っていること」だけを渡せば、
リポジトリを調査して仕様を推論する力の差が出る**のではないか。

## 方法

既存3問の `prompt.md` から**受け入れ基準・具体的なコマンド名・オプション名・閾値を全部削除**し、
「困っていること」と「制約」だけを残した `-vague` 版を作成。**holdout は元と同一**
（＝仕様を推論できたかがそのまま点になる）。レーンは Claude Pro / Sonnet 5。

## 結果 — ceiling は破れた

| タスク | 元の版 | vague 版（seed 7 / 88 / 20260817） | 低下 |
|---|---|---|---|
| 05-lessons-set-status | 9/9 (100%) | **7/9 / 7/9 / 7/9 (78%)** | −22pt |
| 07-lessons-to-vault | 10/10 (100%) | **4/10 / 6/10 / 6/10 (40〜60%)** | −40〜60pt |
| 12-rule-candidates | 10/10 (100%) | **6/10 / 6/10 / 6/10 (60%)** | −40pt |
| **合計** | **29/29 (100%)** | **17〜19/29 (59〜66%)** | **−34〜41pt** |

品質減点はいずれも0（**書いたコード自体は綺麗。落ちたのは「何を作るべきか」の推論**）。

## 何が落ちたか（弁別に効いた項目）

| タスク | 落ちた holdout | 推論できなかったもの |
|---|---|---|
| 05 | `add_status_option_stored`, `add_invalid_status_rejected` | add 側にもオプションが要ること、不正値を弾く必要 |
| 07 | `priority_threshold_boundary`, `sprint_filter_default`, `missing_prereqs_exit0` | 閾値の既定値、境界の含む/含まない、前提不足時に exit 0 |
| 12 | `extraction_condition_combos`, `excluded_trust_boundary_only`, `owner_approved_flag` | 抽出条件の組み合わせ、信頼境界の扱い |

**共通点**: 落ちたのはすべて**「言われなければ気づかない仕様」**。
既存コードを読めば推測できるはずだが、そこまで調査していない。

## 07 だけシードで揺れた（4/10 → 6/10）ことの意味

07 は3シードで結果が一定しなかった。閾値の既定値を推論できず、**当てずっぽうになっている**兆候。
ceiling が破れただけでなく、**安定性の差**も測れる問題になっている。

## 判断

- **adversarial トラックはこの方式で増やせる**（既存問題のコピー＋prompt の書き換えのみ。
  holdout は再利用できるので作成コストが極めて低い）
- 上位レーン（Opus / Codex）でも同じ vague 版を回せば、**初めて上位モデル間の弁別ができる**
- v4.1 で挙げた5類型のうち、まず「不完全な仕様から推論」が有効だと確認できた。
  次に安いのは「regression を厚くする」
