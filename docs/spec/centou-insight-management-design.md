## 主な設計判断（v1からの差分）

- SaaS前提の管理概念（テナント等）を**完全削除**。仕切りは product_id のみ
- 呼び名を修正: リサーチクエスチョン／リサーチ（Source）／ファクト／インサイト／根拠リンク（EvidenceLink）／提案（Suggestion）／監査ログ
- SaaS向けの大規模システムアーキテクチャ（モジュラーモノリス・イベントバス・ワーカー群）を**削除**
- AIパイプライン基盤を廃止し、**Claude Codeスキル4本**での実行に変更
- アーキテクチャは**5案を根拠付きで比較**（すべてNotion案・更新Artifact案・Notionなし案を含む）
- 確信度モデルの**根拠を明記**（構成要素は研究手法に根拠あり、式・係数は設計仮説と明示）
- DB設計を簡素化（highlights・fact_highlights・insight_versions を廃止、embeddings は列へ統合。**ベクトル検索の機能自体は変わらず使う**）。各テーブルの用途説明を追加
- レビューは**確認画面**で行う（UXレビューで方針変更。§3.1・§7.2）
- **§7「画面と体験」を新設** — 画面一覧・38件の3群仕分け・取り込み直後のサマリー・確信度の表示ルール・ゼロ状態
- Notion上のコメント・議論は取り込まない方針を明記

## §1 概要

### 1.1 解決したいこと

| 課題 | 解き方 |
|---|---|
| リサーチ結果が議事録のまま散在し、読み返されない | ファクト単位で構造化し、検索できる資産にする |
| 「前に誰かが同じことを聞いた」ことに気づけない | 新しいファクトを既存インサイトと自動照合する |
| インサイトが作った時点で止まり、古くなる | 新しい根拠の到着でAIが更新・反証を提案する |
| 思い込みの強い施策判断 | 確信度と反証を明示し、根拠の弱さを見えるようにする |

### 1.2 中核コンセプト（3つ）

1. **Atomic UX Researchの階層** — リサーチクエスチョン（問い）→ リサーチ（調査1件）→ ファクト（事実の最小単位）→ インサイト（解釈）。Tomer Sharonの枠組みに準拠
2. **更新され続ける資産** — インサイトは新しい根拠の到着で確信度が動き、反証が出たら見直しがかかる
3. **AIは提案まで、確定は人間** — 人間の承認なしにデータ本体を変えない

### 1.3 データソースと利用者

- 取り込み対象: Google Meet議事録（Docs/リンク）、Notion AI文字起こし、Slack・Chatworkスレッド。リンクか本文貼り付けで渡す。CS問い合わせは対象外（将来拡張）
- 実測値: 議事録1本≒ファクト約38件。週2〜3本→年間4,000〜6,000ファクト
- 利用者: 社内チーム。運用の中心はオーナー、他メンバーは閲覧

## §2 ドメインモデル（1つに固定）

どのアーキテクチャ案でもこのモデルは変わらない。心臓部はファクト⇄インサイトを結ぶ**根拠リンク**（stance: supports/contradicts/context、weight 0–1、UNIQUE(fact_id, insight_id)）。

### 2.1 エンティティ一覧

| エンティティ | 意味 | 主な属性 |
|---|---|---|
| **プロダクト**（products） | 社内プロダクトの単位。データの基本的な仕切り | name, status |
| **リサーチクエスチョン**（research_questions） | 「何を明らかにしたいか」という問い | product_id, question, status(open/answered/parked) |
| **リサーチ**（sources） | 調査1件とその生データ（議事録・スレッド・文字起こし） | product_id, research_question_id, type, title, occurred_at, raw_ref, channel(link/paste/auto), ingestion_status |
| **ファクト**（facts） | 解釈を含まない事実1文と、その**原文の引用**（要約ではなく発言そのもの） | product_id, source_id, statement, quote, quote_locator, speaker, origin(ai/human), status |
| **インサイト**（insights） | 解釈。確信度・状態を持つ | product_id(**NULL=全社横断**), statement, description, status, confidence_*, freshness, owner, superseded_by_id |
| **根拠リンク**（evidence_links） | ファクト⇄インサイトの多対多リンク。**心臓部** | stance(supports/contradicts/context), weight, linked_by, rationale（紐付け理由文） |
| **提案**（suggestions） | AIからの提案。その場で答えなかった分・cronが後から作った分の置き場（`/review` でさばく） | type, payload(変更前後の差分), rationale, score, status, expires_at |
| **監査ログ**（audit_logs） | 誰が・いつ・何を・どう変えたか。追記専用 | actor, action, entity_ref, diff, suggestion_id |
| 将来: タグ・機会・レポート・キャンバス | MVPに含めない（必要になってから追加） | — |

> **設計判断**: ①ファクト・インサイトはリサーチクエスチョンに閉じ込めない（隔離すると重複リサーチが再発）。②インサイトのみ product_id NULL可（全社横断の知見）。照合は「同一プロダクト＋全社」を対象。

### 2.2 インサイトの状態遷移

```
draft ──公開──▶ active ◀──解決── needs_review（要見直し）
                  │  ▲                  ▲
                  │  └─（更新承認で復帰）│
                  │  自動トリガー ───────┘
                  │   ①反証リンクの追加提案 ②確信度の大幅変動 ③鮮度の閾値割れ
                  ├──統合──▶ merged（superseded_by で後継へ）
                  └──保管──▶ archived
※ merged / archived は削除しない（監査とリンク整合性のため）
```

### 2.3 確信度・鮮度の計算モデルと、その根拠

```
確信度 = clamp( 根拠の強さ × 多様性 × 鮮度 − 反証の減点 )

根拠の強さ = Σ supports（手法の重み × リンクの重み）を飽和曲線で頭打ちに
             ── 11件目の価値 < 2件目の価値
多様性     = 独立した発言者数・リサーチ数・種別数（同一人物の10発言 ≪ 10人の発言）
鮮度       = 根拠の発生日に半減期付きの減衰（デフォルト12ヶ月・調整可）
反証の減点 = contradicts側の同様の合算。支持/反証比が閾値割れで needs_review へ

表示: 4段階レベル（仮説→兆候→検証済→強固）を主、数値を従。内訳を必ず開示
```

**このモデルは何を根拠にしているか（正直な整理）**

| 構成要素 | 根拠 |
|---|---|
| 件数の頭打ち（飽和曲線） | 定性調査の**データ飽和（saturation）**の知見。少数サンプルで大半の発見が出て追加の新情報は逓減する（Guest et al. 2006、Nielsenの5ユーザーテスト） |
| 多様性（独立ソース重視） | 研究手法の**トライアンギュレーション**（独立した複数の情報源による裏付け）。同一人物の繰り返しは独立した裏付けにならない |
| 鮮度の半減期減衰 | 知識の陳腐化モデル（文献計量学の「引用半減期」と同型）。市場・ユーザー行動は変わるため古い根拠は割り引く |
| 反証の減点・一級市民化 | 反証主義と**確証バイアス対策**。医療のエビデンス評価**GRADE**が「結果の非一貫性」で証拠の質を下げるのと同じ構造 |
| 4段階レベル表示 | GRADEの4段階（High/Moderate/Low/Very low）に倣った離散化 |

> **ただし——式と係数は「設計仮説」**。構成要素の選定には上記の根拠があるが、式の形・手法の重み（面談1.0/Slack 0.6等）・半減期12ヶ月の具体値は実証された標準ではない。だからこそ ①内訳を必ず開示 ②係数は設定で変更可 ③運用実データ（承認率、レビュー時の体感とのズレ）で校正する。スコアが信頼を失ったら数値を隠し4段階レベルだけにする退路も残す。

## §3 AI処理 — Claude Codeのスキルとして実行する

専用パイプライン基盤（キュー・ワーカー・イベントバス）は**作らない**。AI処理はすべてClaude Codeのスキルとして実装し、手動またはcronで起動する。基盤はBQとGCSだけ。

### 3.1 スキル構成（4本）

| スキル | やること | 起動 |
|---|---|---|
| `/research-ingest` | 議事録のリンク/本文を受け取る → 原文をGCS/BQ保存 → ファクト抽出（引用必須）→ どの問いに紐づくか確認（既存から選ぶ / その場で新規登録）→ **確認画面のリンクを返す** | 手動（議事録を渡すとき） |
| `/insight-match` | 新ファクトを既存インサイトと照合（BQ VECTOR_SEARCH → 支持/反証の判定）→ **その場で確認** → リンク追加・新インサイト作成・要見直しフラグを反映 → 確信度再計算 | ingest後に続けて実行 |
| `/review` | その場で答えられなかった分・cronで溜まった提案（suggestions）をまとめて提示し、**まとめて承認/却下** → 反映 | 手動（気が向いたとき） |
| `/insight-report` | 週次まとめ（新規・要見直し・確信度変動）を生成 | cron（週1） |

> **承認はチャットではなく「確認画面」で行う**（UXレビューで方針変更）
> 当初は「スキル実行時にチャットでその場で聞く」としていたが、**38件をチャットのテキストで流し込むのは最も不向きな提示形式**（一覧できない・絞り込めない・後から見返せない）で、実質「見ずに承認」になる。AIを提案までに留める設計が形骸化してしまう。
> 正しくは、スキルは**「38件の確認画面を用意しました」というリンクを返すだけ**にし、承認はArtifactの確認画面（§7.2）で行う。Notionに提案DBを作らない判断は維持したまま、チャットの弱点も避けられる。
> その場で処理しなかったもの、cronが後から作ったもの（新しい根拠による見直し提案など）は `suggestions` テーブルに溜まり、`/review` から同じ確認画面でさばく。

### 3.2 原則（基盤がなくても守るもの）

- **人間の承認なしにデータ本体を変えない**。必ずその場の確認か `/review` を通す
- ファクトは引用必須（原文の引用が取れないファクト文は登録しない）
- すべてのBQ書込は監査ログ追記とセット
- スキルは何度実行しても安全（sourcesのcontent_hashで二重取り込み防止）
- レビュー運用: ファクトは実測38件/本のため**議事録1本＝1回の一括承認**。個別に丁寧に見るのは新インサイト・見直し・反証リンクに集中
- 実行記録は skill_runs テーブルに残す

## §4 アーキテクチャ5案の比較と推奨

ドメインモデル（§2）とスキル構成（§3）は共通。違いは「マスタをどこに置き、画面を何にするか」だけ。

### 案1: すべてNotion 【不採用】

NotionのDB群がマスタ兼画面。Claude CodeはNotion APIだけを読み書き。BQなし。

| メリット | デメリット（根拠付き） |
|---|---|
| ストア1つで同期不要 | **照合ができない** — Notionにベクトル検索がなく「新ファクトと既存インサイトの自動照合」という核が不成立。全件読みの代替は3req/s制限で1回20分超 |
| 最速で開始（今日から） | **確信度計算が表現できない** — 飽和曲線・半減期はNotion数式で実装困難。rollup多用DBは2,000〜3,000行で劣化（裏取り済み） |
| コメント・通知・モバイル内蔵、運用対象ゼロ | **容量が実測で持たない** — 38件/本→年4,000〜6,000件。1〜2年でUI劣化ゾーン |
| | **監査・版管理が弱い** — 構造化された監査ログ・版履歴にならない |

**判定**: 最初の2週間の実験には使えるが、照合と確信度という中核が作れないため本線にできない。

### 案2: BQマスタ × Notion GUI 【推奨案の土台】

Claude Codeのスキルに議事録を渡すと、ファクトを抽出して**BQに登録し、続けてNotionにも登録（投影）する**。人はNotionを見て、必要なら編集する。BQが全量・履歴・計算のマスタ。

```
議事録 ──▶ スキル ──▶ BQ（マスタ・全量）──投影──▶ Notion ──▶ 人が見る
                              ▲                       │
                              └────── 編集を取り込む ──┘  ← ここが双方向
```

| メリット | デメリット（根拠付き） |
|---|---|
| 照合・確信度計算・監査ログがSQLで確実に作れる | **同期の造り込み** — 所有権固定・hash差分・429対策・夜間突合（§6）。運用の複雑さは増える |
| 承認率などの計測が初日からSQL一発 | **ファクト全量の閲覧面がない** — 38件/本により直近30日＋リンク済みしか置けない |
| Notionの閲覧・コメント・通知はそのまま使える | |

**判定**: 中核要件はすべて成立。弱点は「閲覧面の不足」に集約される。

**BQとNotionの責任範囲（案2〜4共通）**

| 担当 | 原本として持つもの | 持たないもの |
|---|---|---|
| **BigQuery** | ファクト・インサイト・根拠リンク・提案・監査ログの**全量**と確信度計算。データの原本はすべてここ | 画面・通知・議論 |
| **Notion** | **何も原本として持たない**。置かれるファクト・インサイトはすべてBQからの写し（投影）で、消えてもBQから再生成できる。Notion上のコメント・議論はNotionにしか存在しないが、システムには取り込まない（§6.4） | データ本体。編集できるのはインサイトの文言と状態のみ（案4に進めばそれも不要） |
| **Claude Codeスキル** | なし。処理の実行役（毎回BQから読み、結果をBQへ書く。自分では保存しない） | — |

### 案3: 案2＋閲覧Artifact（公式BigQueryコネクタ）

案2に、Claude Artifact＋Google公式のマネージドBigQuery MCPコネクタによる**読み取り専用の閲覧画面**を足す。検索・全量ファクト一覧・インサイト詳細（確信度内訳・支持/反証）の閲覧をArtifactが担う。

```
議事録 ──▶ スキル ──▶ BQ（マスタ）──投影──▶ Notion ──▶ 人が見る・編集する
                        │  ▲                  │
                        │  └── 編集を取り込む ─┘  ← 双方向は案2のまま
                        └──読取──▶ 閲覧Artifact ──▶ 人が探す（全量）
```

| 案2に対する追加メリット | 残るデメリット |
|---|---|
| 弱点だった「ファクト全量の閲覧面」が埋まる | Artifact閲覧にclaude.aiログイン＋コネクタ同意が必要 |
| 追加コストは**設定のみ**（コネクタ追加＋閲覧専用権限の付与。公式マネージドMCPのためコード・サーバ運用ゼロ） | 編集・承認はまだArtifactでできない |
| 案4（更新Artifact）へ同じ構成のまま拡張できる | window.claude.mcpの実挙動が未検証（v1a冒頭で確認） |

### 案4: 更新Artifact ＋ Notionは読み取り専用の共有ボード

操作（閲覧・編集・承認・分析キャンバス）は**すべてArtifactで行い**、Notionは**BQから一方向に流し込むだけの読み取り専用ボード**として残す。Notionからは一切編集しない。

```
議事録 ──▶ スキル ──▶ BQ（マスタ）──投影──▶ Notion ──▶ 人が見る・議論する
                        ▲  │                            （編集はしない）
          人が操作する ──┴──┴──▶ Artifact（閲覧・編集・承認・キャンバス）
```

> **案5との違いは「Notionを残すかどうか」だけ。残す理由は2つ**
> ① **議論の場** — インサイトにコメントを付けて会話できる。Artifactにはこの機能がない
> ② **claude.aiを開かない人への共有** — ログインもコネクタ同意も要らず、リンクを送れば読める
> **逆に言えば、この2つが要らないなら案5でよい。** 案4は「Artifactで作業し、Notionで見せて議論する」役割分担であり、*Notionを編集可能にはしない*のが要点。これにより**同期は BQ→Notion の一方向だけ**になり、案2で必要だった逆方向の取り込み（所有権の固定・競合解決・エコー防止）が丸ごと不要になる。


案3のArtifactに**書き込み（更新）**もさせる。インサイトの編集・提案の承認・分析キャンバスの保存までArtifact上で完結させ、Notionは共有と議論に絞る。

> **実現可能性の確認結果 — 更新できる**
> Google公式のBigQuery MCPサーバには目的の異なる2つのSQL実行ツールがある。
> ・`execute_sql_readonly` … SELECTのみ。INSERT/UPDATE/DELETE・DDLは**拒否される**
> ・`execute_sql` … BigQueryが扱えるクエリを実行でき、**INSERT・UPDATE・DELETE等の書き込みに対応**
> したがってArtifactに `execute_sql` を許可し、書き込み権限のあるアカウントで接続すれば*自作サーバなしでBQを更新できる*。閲覧用と更新用でツールを使い分けられるのが重要で、「見るだけの画面」には readonly だけを渡せる。

| メリット | デメリット・リスク |
|---|---|
| **自作MCPサーバが不要になる**（案3のv1bで想定していた開発が消える） | **安全装置がない** — 任意のSQLを実行できるため画面側のバグが直接データを壊し得る。自作MCPなら「このツールはこの更新しかしない」と限定できるが生SQLではその保証がない |
| 編集・承認・分析キャンバスまでArtifactで完結。Notionへの逆方向同期が不要になる | **監査ログが規律頼み** — 更新のたびに監査ログを書く処理を画面側が毎回忘れず実装する必要がある |
| 確信度内訳・支持/反証の並置など、Notionでは作れない画面を自由に作れる | 誤更新の復旧はBigQueryのタイムトラベル（既定7日間）に依存 |

**緩和策**: ①更新は「1操作＝1定型SQL」に限定し画面コードの一箇所に集約 ②更新SQLと監査ログのINSERTを必ず同じ実行にまとめる ③削除は行わずstatus変更のみ ④まず案3（読み取りのみ）で運用を固め、更新は*承認と文言編集の2操作だけ*から始める。

### 案5: BQ ＋ BQ MCP ＋ Artifact（Notionを使わない）【推奨・到達点】

Notionを構成から外し、**閲覧も更新もすべてArtifact上で完結**させる。ストアはBQ1つだけ。画面はArtifact、AI処理はClaude Codeスキル、その橋渡しがBQ MCP。

```
議事録 ──▶ スキル ──▶ BQ（唯一のストア）◀──MCP──▶ Artifact ──▶ 人
                                                （閲覧・編集・承認・キャンバス）
※ 投影する先がないので、同期の実装が存在しない
```

> **更新の危険範囲を絞る方法は2段階。サーバを立てずに始められる**
> **段階1: 権限だけで絞る（サーバ不要・すぐ始められる）**
> 公式マネージドMCP（`bigquery.googleapis.com/mcp`）の `execute_sql` を使い、*接続アカウントに「書き換えてよいテーブル」だけ書込権限を与える*。インサイト・提案・監査ログだけ書込可、ファクトとリサーチは読み取り専用にすれば、画面のバグが壊せる範囲がそこに限定される。任意のSQLは書けるが被害範囲は権限で封じられる。
> **段階2: 操作そのものを限定する（サーバが必要）**
> **MCP Toolbox for BigQuery**（Google公式のオープンソース `googleapis/mcp-toolbox`）は、設定ファイル（tools.yaml）に*ツールを1つずつ定義する*方式。「提案を承認する」「インサイトの文言を更新する」といった**定型SQLとその引数だけ**を公開でき、定義していない操作は実行できない。ただし*これは自分で動かすプログラム*なので、Cloud Run などに常時起動で置き、カスタムコネクタとして登録する必要がある。
> **進め方**: MVPは段階1で始め、更新の種類が増えて「特定の操作だけに固定したい」となった時点で段階2へ移る。*最初からサーバを立てる必要はない。*

| メリット | デメリット |
|---|---|
| **同期がゼロになる** — 本設計で最大の複雑さだった「BQ⇄Notionの双方向同期」が丸ごと消える。所有権マトリクス・hash差分・夜間突合・429対策・投影上限のすべてが不要 | **画面を直せるのは作成者1人だけ**（下記） |
| **ファクト38件/本の制約から解放される** — 投影しないので行数上限もUI劣化も無関係 | **コメント・議論の場がなくなる** — Notionが担っていた協働機能は自作しない限り存在しない |
| **更新の危険範囲を絞れる**（権限で、必要なら定型ツールで） | **閲覧にclaude.aiログインとコネクタ同意が必要** — 気軽な共有は失われる |
| 画面を自由に作れる（確信度内訳・支持/反証の並置・分析キャンバス） | **画面をすべて自分で作る必要がある** — Notionが無料で提供していた一覧・フィルタ・並べ替えを実装することになる |

> **重要な制約 — Artifactを更新できるのは作成者だけ**
> Artifactは**所有者（作成した人）しか更新できない**。他の人は共有されれば閲覧できるが内容を直すことはできない。さらにコネクタを使う（＝BQに接続する）ページは*一般公開の共有ができない*。呼び出しは閲覧者自身の資格情報で実行されるため、各自がBQの権限を持っている必要もある。
> **つまり「画面の改修担当が1人に固定される」**。1人運用なら問題にならないが、チームで画面も一緒に育てたいなら無視できない制約になる。
>
> **緩和策 — Artifactを「成果物」として扱い、正はgitに置く**
> 画面のHTMLをリポジトリで管理し、Artifactはそこから発行した表示用の複製とみなす。こうすれば*誰でもソースを直せる*し、担当者が不在でも別の人が自分のArtifactとして発行し直せる（URLは変わるが内容は失われない）。画面の定義が1人のアカウントに閉じ込められる事態を防げる。

**判定**: 構造的には最もシンプルで、本設計を通じて最大の複雑さだった同期問題が消える。*1人〜少人数で運用するなら最良の選択*。判断すべきは技術ではなく「コメント・議論・気軽な共有を捨てられるか」と「画面の改修が1人に固定されてよいか」の2点。

### 4.4b 「Notionからステータスくらい変えたい」への回答

実運用では「Notionを見ていて、このインサイトはもう古いからアーカイブしたい」と思う場面が必ず来る。ここで**Notionを編集可能にすると、逆方向同期の仕組み一式が戻ってくる**——変更の検知（巡回）・自分の書き込みを拾わない仕組み・競合の解決規則・監査記録。*これは対象がステータス1項目でも、文言まで含めても、必要な仕組みの量はほとんど変わらない*。フィールドを減らしても複雑さは減らない、という点が重要。

| やり方 | 必要になるもの | 評価 |
|---|---|---|
| **A. Notionは読み取り専用にし、ページに「Artifactで開く」リンクを置く** | リンク1つ（投影時に埋め込む） | **推奨**。同期は一方向のまま |
| B. ステータス変更を `/review` スキルでまとめて行う | なし（既存スキルの一機能） | 推奨。定期的な棚卸しと相性がよい |
| C. Notionのステータス欄を編集可能にする | 逆方向同期の一式（巡回・エコー防止・競合規則・監査） | 非推奨。1項目のために仕組みが丸ごと必要 |

**結論**: 案4ではNotionを読み取り専用に保ち、状態の変更はArtifactかスキルで行う。Notion上の各ページに対応するArtifact画面へのリンクを置けば「見ていて気づいた → 1クリックで操作画面へ」の導線になる。

### 4.4c Notionのページを物理削除してよいか

> **結論 — 人は消さない。システムは消す**
> **人による削除は認めない。** Notionのページを人が消してもBQに原本があるため次の投影で復活する。「消したのに戻ってくる」のは混乱のもとで、削除を試みること自体が無意味になる。
> **一方、システムによる削除は積極的に行う。** 投影の対象から外れたもの——アーカイブ済みインサイト、30日を過ぎて根拠リンクも持たないファクト——は*アーカイブではなくページごと削除する*。Notionは行数が増えると表示が重くなるため（2,000〜3,000行で劣化する構成もある）、投影を軽く保つことが性能対策そのものになる。BQに全量が残っているので消しても何も失われない。

### 4.5 比較表と推奨

|---|---|---|---|---|---|

> **推奨 — 案5を到達点に置く。ただし先に決めるべきことが1つある**
> **案1を除外する理由**: 核である照合と確信度計算がNotion単体では成立しない（ベクトル検索の不在・数式の限界・rollup劣化はいずれも裏取り済み）
> **案5を到達点とする理由**: 本設計で一貫して最大の複雑さだったのは*BQとNotionの双方向同期*だった（所有権の固定・差分検知・429対策・夜間突合・投影上限）。案5はこれを**問題ごと消す**。さらにMCP Toolboxで更新を定型ツールに限定すれば、案4で残った「生SQLで壊せる」リスクも同時に解決する
> **案2・案3を通過点にしない理由**: この2つはNotionを編集可能にするため双方向同期が必要になる。案4のようにNotionを読み取り専用と割り切れば、同じNotionの利点（議論・共有）を*一方向の投影だけ*で得られる
> **ただし判断が必要**: 案5はコメント・議論・気軽な共有を失う。ここは技術ではなく運用の選択なので、**先に決めてから作り始めるべき**——*案5に行くと決まっているなら、Notion連携のコードは最初から書く必要がない*から

### 4.6 進め方は「Notionを何に使うか」で2通り

案2・案3（Notionから編集する構成）は**双方向同期という最も壊れやすい部分**を抱える。それを避けたうえで、Notionを残すか外すかの二択になる。

| | A. Notionを使わない → 案5 | B. Notionを読み取り専用で残す → 案4 |
|---|---|---|
| こう選ぶ | 1人〜少人数。議論はSlackで足りる。閲覧者もclaude.aiを使う | **コメントで議論したい**／**claude.aiを開かない人にも見せたい** |
| Notionの役割 | なし | 読み取り専用の共有ボード（編集させない） |
| 同期 | **ゼロ** | **一方向（BQ→Notion）だけ** |
| MVP-0でやること | BQ＋スキル4本＋最小の閲覧Artifact | 左に加えてNotionへの一方向投影 |
| 状態の変更（アーカイブ等） | Artifactまたはスキルで行う | 同左（Notionからは行わない。§4.4b） |

**どちらでも、Notionを編集可能にはしない**のが本設計の判断。これで同期の複雑さの大半が消える。AとBの差は「議論の場と気軽な共有が要るか」だけなので、*先にそこを決めればMVP-0の作るものが確定する*。

## §5 データベース設計（BigQuery）

### 5.1 各テーブルの役割

| テーブル | 何を入れるか | なぜ必要か | 1行の例 |
|---|---|---|---|
| `products` | 社内プロダクトの一覧 | データの仕切り。検索を「このプロダクト内」に絞る | プロダクトX |
| `research_questions` | 明らかにしたい問い | リサーチをぶら下げる先。「何のために調べたか」を残す | なぜ週次レポートの閲覧率が低いのか |
| `sources` | 議事録などの調査1件 | ファクトの出典。原文に戻れるようにする | 2026-08-05 A社定例（Meet議事録） |
| `facts` | 事実1文＋その引用と話者 | インサイトの根拠になる最小単位。**本システムの素材** | 「田中さんは週次レポートを見ていないと述べた」＋原文引用 |
| `insights` | 解釈と確信度 | **資産そのもの**。最終的に読み返すのはここ | 「顧客は定型レポートより異常時の通知を求めている」確信度72 |
| `evidence_links` | どのファクトがどのインサイトを支持／反証するか | 確信度計算の入力。**この表がないと確信度が出せない** | ファクト#123 → インサイト#7 を supports（重み0.8） |
| `suggestions` | AIからの未処理の提案 | その場で答えなかった分・cronが後から作った分の置き場 | 「ファクト#123をインサイト#7の根拠に追加しますか」 |
| `audit_logs` | 変更の履歴（誰が・いつ・何を・どう） | 「なぜこうなってる？」を後から追う。AIが勝手に変えていない証明 | 8/10 14:32 提案#55を承認 → 確信度55→72 |
| `sync_state` | BQのIDとNotionページIDの対応表 | 二重投影と迷子ページの防止。*Notionを使う場合のみ必要* | インサイト#7 = Notionページ abc123 |
| `skill_runs` | スキルの実行記録 | 失敗の検知と再実行の判断 | 8/11 02:00 review 成功 12件処理 |
| `tags` / `taggings` | ペルソナ・テーマなどの分類 | 絞り込み用。*MVPでは使わない（スキーマだけ用意）* | 「新規ユーザー」「オンボーディング」 |

### 5.2 スキーマ

```
-- dataset: core（データ本体）
products(id, name, status)

research_questions(id, product_id, question, status, created_at)

sources(id, product_id, research_question_id, type, title, occurred_at,
        raw_ref,          -- GCS上の原文への参照
        content_hash,     -- 同じ議事録の二重取り込みを防ぐ
        channel,          -- link / paste / auto
        ingestion_status)

facts(id, product_id, source_id,
      statement,          -- 事実1文
      quote,              -- 原文の引用（旧 highlights を統合）
      quote_locator,      -- 原文中の位置（文字位置 or タイムスタンプ）
      speaker,            -- 発言者（匿名化した属性）
      origin,             -- ai / human
      embedding ARRAY<FLOAT64>, embedding_model,   -- 意味検索用
      status, created_at)

insights(id, product_id,  -- NULL = プロダクト横断（全社）の知見
         statement, description, status, owner,
         confidence_score, confidence_level, confidence_breakdown JSON,
         freshness_score, last_evidence_at, superseded_by_id,
         embedding ARRAY<FLOAT64>, embedding_model,
         published_at)

evidence_links(id, fact_id, insight_id,
               stance,    -- supports / contradicts / context
               weight, linked_by, rationale, created_at)
               -- UNIQUE(fact_id, insight_id)

suggestions(id, product_id, type, payload JSON, rationale, score,
            status, reviewed_at, expires_at, created_at)

tags(id, name, facet)                        -- MVPでは使わない（定義のみ）
taggings(tag_id, entity_type, entity_id)     -- 同上

-- dataset: ops（運用データ）
audit_logs(id, actor_type, actor_id, action, entity_type, entity_id,
           diff JSON, created_at)         -- 追記専用
sync_state(entity_type, entity_id, notion_page_id,
           content_hash, last_synced_at)  -- Notionを使う場合のみ
skill_runs(id, skill, started_at, finished_at, status, stats JSON)
```

### 5.3 v1から変えたところ

> **重要な確認 — ベクトル検索（embedding）は使う。やめたのは「テーブルを分けること」だけ**
> **embedding（埋め込み）＝文章の意味を数百個の数値の並びに変換したもの。** 数値が近い＝意味が近いので「言葉は違うが同じことを言っているファクト」を探せる。BigQueryの `ML.GENERATE_EMBEDDING` で作り `VECTOR_SEARCH` で近いものを探す。*これが「新しいファクトを既存インサイトと自動照合する」という本システムの核そのもの*で、当然使う。
> v3で変えたのは置き場所だけ——`embeddings` という**別テーブルを作るのをやめ、facts / insights の列にした**。BigQueryは列指向（使わない列は読み込まれない）なので分けても速度の利点がなく、結合が増える分むしろ扱いにくいため。**機能は1ミリも減っていない。**

| 変更 | 理由 |
|---|---|
| `highlights` → **facts に統合** | 実態は「1ファクト＝1引用」であり、引用だけを独立して検索することがない。`facts.quote` と `quote_locator` で足りる |
| `fact_highlights` → **廃止** | ファクトと引用を多対多にする必要がなかった。複数箇所を引くケースは facts 側の配列で持てる |
| `insight_versions` → **廃止** | **audit_logs と重複**。監査ログが変更前後の差分を持つので過去の文言はそこから復元できる。同じ情報を2箇所に持つのは事故のもと |
| `embeddings` → **facts / insights の列へ移動** | 上記のとおり。*ベクトル検索の機能自体は変わらず使う* |
| `tags` / `taggings` → **残すがMVPでは使わない** | ペルソナ・テーマなどでの絞り込みは将来必要になる。スキーマは定義しておき、投入と画面はMVPの後に回す |

**設計メモ**
- データの仕切りは **product_id のみ**。主要テーブルは product_id でクラスタリング
- `audit_logs` は追記専用（UPDATE/DELETE権限を発行しない）
- 確信度の再計算は evidence_links の変化時＋日次の減衰更新（スケジュールドクエリ）
- キャンバス系テーブルは案4で分析キャンバスを作るときに追加する。今は作らない

## §6 Notion側の設計（投影・レビュー・429対策）

この節は**案4（Notionを読み取り専用の共有ボードとして残す）**を採る場合の設計。案5（Notionを使わない）なら、この節はまるごと不要になる。

### 6.1 DB構成（3つ）と投影規約

Notionは**完全に読み取り専用**とする（§4.4b）。レビューはスキル実行時、編集・状態変更はArtifactかスキルで行う。

| DB | 置くもの | 編集 |
|---|---|---|
| インサイトDB | active＋needs_review のみ（archived/mergedは投影対象外）。各ページに**Artifactの該当画面へのリンク**を埋める | 不可 |
| ファクトDB | 直近30日＋根拠リンク済みのみ（全量はArtifactで見る） | 不可 |
| リサーチDB | メタデータのみ（タイトル・種別・日付・GCSリンク） | 不可 |

> **なぜ編集できるものをこの3つに絞るのか**
> 2つのストアの両方で編集できるフィールドが1つでもあると、同期のたびにどちらが正か決められず壊れる。そこで「人間の判断そのもの」だけをNotion側の編集に割り当てた——①インサイトの文言・説明（解釈は人間のもの）②インサイトの状態（公開・保管の判断）③提案のstatus（承認は人間の行為）。逆にファクトは原文由来なので編集ではなく修正提案で直し、確信度は計算値なので人間は触らない。編集可を増やす変更は同期の破綻リスクと直結するため、必ず設計判断として扱う。

- Notion上のコメント・議論は**取り込まない**（§6.4）
- 計算値はBQの結果を「ただの数値・セレクト」として書く。**rollup・formulaは使わない**（2,000〜3,000行からの劣化要因）。ビューには必ずフィルタ＋読み込み上限
- 投影上限の目安: インサイト≤1,000行／ファクト≤2,000行。超えたら古いものを外す（BQに全量あり）

### 6.2 429対策

- Notion APIは平均3req/s。書込は単一の流れに直列化し1件350ms間隔。429は Retry-After 秒停止→再発で待ち倍増
- content_hash が変わったレコードだけ書く。議事録1本≒90〜120リクエスト≒40秒、バックフィル50本≒30分（夜間）

### 6.3 逆方向同期は行わない

Notionは読み取り専用なので、**Notion→BQの取り込みは実装しない**。案2で必要だった変更の巡回検知・エコー防止・競合解決・同期ステータス表示は、すべて不要になる。

ただし人が誤ってNotion上で編集してしまう可能性は残るため、**夜間の突合でBQの値に戻す**（差分があれば上書き投影）。戻したことは監査ログに `notion_manual_edit` として記録し、無言で消さない。

### 6.4 コメント・議論は取り込まない

Notion上のコメント・議論は**システムに取り込まない**（当初は夜間バックアップを想定していたが取りやめ）。理由は2つ。

- **技術的に完全には取れない** — コメント取得APIが返すのは未解決（open）のものだけで、解決済みは取得手段がない。取りこぼしが構造的に起きるものを「保存してある」と扱うのは危険。また全件一覧のAPIがなくページ単位でしか取得できないため、集めるだけで毎晩1,000件規模のリクエストを要し、投影と同じレート枠を食い合う
- **そもそも失われない** — 投影は sync_state のページIDで*既存ページを更新する方式*であり、通常運用でページを作り直さない。したがってコメントは消えない

そのうえで「議論の結論だけは残したい」場合は、**結論をインサイトの description に書く**運用で対応する。人間の判断としてBQに入り、監査ログにも残る。取り込み機構を作るより、結論を書く運用のほうが実際に読み返される。

## §7 画面と体験（UX）

UXレビュー（2026-08-11）を受けて追加。アーキテクチャの選択（案4/案5）に関わらず、**この画面群は必ず必要**。動作するプロトタイプは Claude Artifact を参照。

### 7.1 MVP-0で作る画面

| # | 画面 | 目的 | 主な利用者 |
|---|---|---|---|
| 1 | ホーム（週次まとめ） | 「今週なにがわかったか」から始める入口 | 閲覧者 |
| 2 | **取り込み確認 ★** | 38件を見ずに承認させない（7.2） | オーナー |
| 3 | インサイト一覧 | 今わかっていることの全体像。検索・絞り込み | 全員 |
| 4 | インサイト詳細 | 確信度の内訳、支持／反証の並置、変更履歴 | 全員 |
| 5 | 問い（リサーチクエスチョン） | 「前に同じことを調べていないか」の確認（7.5） | 全員 |
| 6 | ファクト一覧（全量） | 年4,000〜6,000件を検索。Notionには置けない | オーナー中心 |
| 7 | ゼロ状態（各画面） | データが少ない時期の見せ方（7.6） | 全員 |

### 7.2 取り込み確認画面 — 38件を3群に仕分ける

実測38件/本を平坦に並べると必ず読み飛ばされる。`insight-match` が既に計算している照合スコアをそのまま使い、**AIが自動で3群に仕分けて提示**する（追加の計算コストはゼロ）。

```
要確認（3〜5件）  ← 新インサイト候補・既存への反証・統合候補
                    1件ずつカードで表示し、個別に承認/保留/却下
既存の裏付け（20件）← 既存インサイトを支持するだけ
                    折りたたみ。初期状態は「まとめて承認」
関連が弱い（15件） ← どれとも弱くしか結びつかない
                    折りたたみ。初期状態は「保留」（破棄しない）
```

- 人間の注意力を「要確認」の数件に集中させ、残りは**開けば見られる**状態にする
- 確定後に取り消せることを画面に明記する（一括承認の心理的ハードルはUndoの可視性で下げる）
- 保留にしたファクトもBQには残る。後で別のインサイトの根拠になりうるため

### 7.3 取り込み直後に返すサマリー（継続の要）

最大の事業リスクは「取り込む習慣が続かないこと」（§9）。投入の摩擦を下げるだけでは続かず、**入れた直後に価値が返ること**が必要。`/research-ingest` → `/insight-match` の完了時に必ず次を返す。

```
今回の取り込みでわかったこと
✓ 新しいインサイト候補が1件生まれました
✓ 「週次レポートは最初の画面で離脱している」の確信度が 兆候 → 検証済 に上がりました
⚠ 「オンボーディングの設定項目が多すぎる」に反証が1件 → 要見直しになりました
```

**「38件処理しました」ではなく「これがわかった」を主語にする。** 件数はシステムの都合であり、継続の理由にならない。あわせて週次まとめに「今週まだ取り込まれていません」という不在の可視化を入れる。

### 7.4 確信度の表示ルール

| 場所 | 出すもの | 出さないもの |
|---|---|---|
| 一覧 | 4段階バッジ（仮説/兆候/検証済/強固）＋段階ドット、根拠件数・発言者数 | **数値を出さない** |
| 詳細 | 数値＋メーター＋**内訳とセット**（支持12件・発言者9名・反証1件・最終更新3週間前） | — |

- 一覧に「72」と出すと自動的に順位比較の道具になるが、**式はまだ未検証の仮説**（§2.3）。検証されていない精度を信じさせるのは、課題4番目の「思い込みの強い施策判断」を自分で作り出すことになる
- 色だけで段階を伝えない。ラベル＋ドット（●●●○）を併記する
- `needs_review` は確信度のバッジとは**別軸**で警告表示する（レベルが低いことと、見直しが必要なことは別の情報）
- 詳細には確信度の推移（履歴）を出す。「仮説だったものが検証済に上がった」変化が信頼形成に効く

### 7.5 リサーチクエスチョンの登録 — 画面とスキルの両方

課題認識の1番目「前に誰かが同じことを聞いたことに気づけない」に直接応える画面。**これが無いとその課題は解決しない。**

登録の経路は2つ。**専用スキルは作らない。**

1. **議事録を渡すとき（主）** — `/research-ingest` の中で「この議事録はどの問いに紐づきますか」と聞き、既存から選ぶか、その場で新規登録する。問いの登録頻度は月に数件程度なので、独立した操作にする必要がない
2. **問い一覧画面から** — 一覧・状態管理（進行中/回答済み/保留）と、新規登録

登録時は**似た問いを自動照合して警告する**（「なぜ週次レポートの閲覧率が低いのか という問いが既にあります」）。これが重複リサーチの防止そのもの。

### 7.6 ゼロ状態（最初の1〜2週間）

立ち上げ直後はインサイトの大半が「仮説」で確信度も低い。これは正常だが、説明がないと「大した発見をしていない」という誤った第一印象になり、そのまま離脱につながる。**低いことを失敗に見せない**のがここの仕事。

- インサイトが空/少数: 「まだ育てている途中です。議事録を3〜5本取り込むと照合が効き始めます」
- 問いが0件: 「最初に明らかにしたいことを1つ決めましょう」＋登録導線
- 検索0件: 「一致するインサイトはありません。**まだ誰も調べていないテーマかもしれません**」→ 問いとして登録する導線（重複検知の価値と表裏なので、ポジティブな空状態にする）

### 7.7 引用とエラーの扱い

- **引用**: 一覧では事実文（statement）を主に見せ、引用は折りたたみ。開くと前後の文脈を数行含め、`quote_locator` から元の議事録へのリンクを併記する。引用は捏造防止の担保なので、画面上で検証可能でなければ意味がない
- **エラー**: 無言で失敗させない。①リンクが読めない →「共有設定をご確認いただくか、本文を貼り付けてください」 ②ファクト0件 →「事実らしい発言が見つかりませんでした。形式が対象外の可能性があります」 ③重複 →「この議事録は8/5に取り込み済みです」

### 7.8 閲覧者とオーナーで見せるものを分ける

- 閲覧者のホームは**週次まとめ**。未承認の提案・draft状態のインサイトは**見せない**（未確定情報はノイズになる）
- インサイト詳細には「誰が・いつ確定させたか」（監査ログの情報）を閲覧者にも見せる。AIが生成する仕組みである以上、人が確認した痕跡が見えることが信頼の条件

## §9 リスクと未決事項

### リスク

| リスク | 緩和策 |
|---|---|
| **取り込み習慣が続かない**（最大の事業リスク） | 「リンクを貼るだけ」の1アクションに絞る。v2で自動化 |
| レビュー負荷（実測38件/本） | 議事録1本＝1レビューの一括承認。個別レビューはインサイト系のみ |
| 確信度が信頼されない | 内訳の完全開示・係数調整可・4段階主表示。承認率とのズレで校正 |
| 同期ドリフト（BQ⇄Notion） | 所有権固定・hash差分・夜間突合・同期ステータス可視化 |
| window.claude.mcp 実挙動未検証 | v1a冒頭で「検索1画面」の縦スライスで確認してから広げる |
| **Artifactからの誤更新** | 案5のようにMCP Toolboxで定型ツールだけを公開する（任意SQLを許可しない）／監査ログの記録をツール定義に含める／削除せずstatus変更のみ／BQのタイムトラベル（既定7日）で復旧 |
| **案5の場合: 議論の場がない** | 議論はSlackで行い結論をインサイトの説明欄に書く運用にする。Notionを使うか（§4.6）は着手前に決める |
| **案3〜5: 画面を直せるのが作成者1人** | 画面のHTMLをgitで管理し、Artifactは発行した複製として扱う。担当者が不在でも別の人がソースから発行し直せる |
| 抽出粒度（38件は多すぎる可能性） | 最初の数本で「根拠リンクに使われた率」を測り重要度フィルタを校正 |

### 未決事項

- 確信度の係数（手法の重み・半減期）の初期値（§2.3の仮説を最初の1ヶ月で校正）
- Slack・Chatworkスレッドの「1リサーチ」の切り方（スレッド単位か期間単位か）
- 発言者の匿名化レベル（speaker_attrs の範囲）
- **Notionを使うか（§4.6のA/B）。着手前に決める必要がある** — 決めないとNotion連携の実装が無駄になる可能性がある
- MCP Toolbox に移る判断基準（段階1の権限管理で足りるか、操作単位の限定が必要になるか）
