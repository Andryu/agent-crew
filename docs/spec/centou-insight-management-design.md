- **v8: MVPでは専用画面（Artifact）を作らない**（§7.1）。7画面すべてNotionのビューで成立する
- **v8: 移行を安く保つ5つの制約**（§4.11）を段階1の時点から守る。列名の一致・数式を使わない・不変属性の写し・自前のID・読み書きの1ファイル集約

## §1 概要

### 1.1 解決したいこと

| 課題 | 解き方 |
|---|---|
| リサーチ結果が議事録のまま散在し、読み返されない | ファクト単位で構造化し、検索できる資産にする |
| 「前に誰かが同じことを聞いた」ことに気づけない | 新しいファクトを既存インサイトと自動照合する |
| インサイトが作った時点で止まり、古くなる | 新しい根拠の到着でAIが更新・反証を提案する |
| 思い込みの強い施策判断 | 確信度と反証を明示し、根拠の弱さを見えるようにする |

### 1.2 中核コンセプト（3つ）

1. **Atomic UX Researchの階層** — リサーチクエスチョン（問い）→ リサーチ（調査1件）→ ファクト（事実の最小単位）→ インサイト（解釈）。Tomer Sharonの枠組みに準拠
2. **更新され続ける資産** — インサイトは新しい根拠の到着で確信度が動き、反証が出たら見直しがかかる
3. **AIは提案まで、確定は人間** — 人間の承認なしにデータ本体を変えない

### 1.3 データソースと利用者

- 取り込み対象: Google Meet議事録（Docs/リンク）、Notion AI文字起こし、Slack・Chatworkスレッド。リンクか本文貼り付けで渡す。CS問い合わせは対象外（将来拡張）
- 実測値: 議事録1本≒ファクト約38件。週2〜3本→年間4,000〜6,000ファクト
- 利用者: 社内チーム。運用の中心はオーナー、他メンバーは閲覧

## §2 ドメインモデル（1つに固定）

どのアーキテクチャ案でもこのモデルは変わらない。心臓部はファクト⇄インサイトを結ぶ**根拠リンク**（stance: supports/contradicts/context、weight 0–1、UNIQUE(fact_id, insight_id)）。

### 2.1 エンティティ一覧

| エンティティ | 意味 | 主な属性 |
|---|---|---|
| **プロダクト**（products） | 社内プロダクトの単位。データの基本的な仕切り | name, status |
| **リサーチクエスチョン**（research_questions） | 「何を明らかにしたいか」という問い | product_id, question, status(open/answered/parked) |
| **リサーチ**（sources） | 調査1件とその生データ（議事録・スレッド・文字起こし） | product_id, research_question_id, type, title, occurred_at, raw_ref, channel(link/paste/auto), ingestion_status |
| **ファクト**（facts） | 解釈を含まない事実1文と、その**原文の引用**（要約ではなく発言そのもの） | product_id, source_id, statement, quote, quote_locator, speaker, origin(ai/human), **status(active/retracted)** |
| **インサイト**（insights） | 解釈。確信度・状態を持つ | product_id(**NULL=全社横断**), statement, description, status, confidence_*, freshness, owner, superseded_by_id, **falsification_condition**（反証条件・任意）, **last_referenced_at / reference_count** |
| **根拠リンク**（evidence_links） | ファクト⇄インサイトの多対多リンク。**心臓部** | stance(supports/contradicts/context), weight, linked_by, rationale（紐付け理由文） |
| **提案**（suggestions） | AIからの提案。その場で答えなかった分・cronが後から作った分の置き場（`/review` でさばく） | type, payload(変更前後の差分), rationale, score, status, expires_at |
| **監査ログ**（audit_logs） | 誰が・いつ・何を・どう変えたか。追記専用 | actor, action, entity_ref, diff, suggestion_id, **reason**（なぜそうしたか一文） |
| **フィードバック**（feedbacks） | 人からの指摘1件（§8.1） | target_type, target_id, kind, summary, applied |
| **学習ルール**（learnings） | 繰り返した指摘から作った改善ルール（§8.2） | category, observation, rule, status, feedback_ids |
| 将来: タグ・レポート・キャンバス | MVPに含めない（必要になってから追加） | — |

> **「機会（Opportunity）」は作らない。** インサイトから仮説を立てて検証する役割は、**既にNotionにある組織の課題仮説DB**が担っている。同じものをBQに持つと二重管理になる。境界は「本システム＝問い→リサーチ→ファクト→インサイト」「既存の課題仮説DB＝課題仮説→検証→結果」（§6.5）。

> **設計判断**: ①ファクト・インサイトはリサーチクエスチョンに閉じ込めない（隔離すると重複リサーチが再発）。②インサイトのみ product_id NULL可（全社横断の知見）。照合は「同一プロダクト＋全社」を対象。

### 2.2 インサイトの状態遷移

```
draft ──公開──▶ active ◀──解決── needs_review（要見直し）
                  │  ▲                  ▲
                  │  └─（更新承認で復帰）│
                  │  自動トリガー ───────┘
                  │   ①反証リンクの追加提案 ②確信度の大幅変動 ③鮮度の閾値割れ
                  ├──統合──▶ merged（superseded_by で後継へ）
                  └──保管──▶ archived
※ merged / archived は削除しない（監査とリンク整合性のため）
```

**ファクトの撤回とその伝播**

発言の取り消し・前提の誤りは起こる。引用必須で捏造は防げるが、**後から誤りと判明したファクト**への対処が必要。

```
facts.status: active ──撤回──▶ retracted
   ↓ 撤回した瞬間に自動で
   ① そのファクトを参照する evidence_links を無効化
   ② 対象インサイトの確信度を再計算（既存のトリガーをそのまま使う）
   ③ 確信度が大きく下がったインサイトは needs_review へ
```

ファクト自体は削除せず `retracted` にする（監査のため）。再計算の経路は evidence_links 変更時のトリガーが既にあるので、それを流用する。

### 2.3 確信度・鮮度の計算モデルと、その根拠

```
確信度 = clamp( 根拠の強さ × 多様性 × 鮮度 − 反証の減点 )

根拠の強さ = Σ supports（手法の重み × リンクの重み）を飽和曲線で頭打ちに
             ── 11件目の価値 < 2件目の価値
多様性     = 独立した発言者数・リサーチ数・種別数（同一人物の10発言 ≪ 10人の発言）
鮮度       = 根拠の発生日に半減期付きの減衰（デフォルト12ヶ月・調整可）
反証の減点 = contradicts側の同様の合算。支持/反証比が閾値割れで needs_review へ

表示: 4段階レベル（仮説→兆候→検証済→強固）を主、数値を従。内訳を必ず開示
```

**このモデルは何を根拠にしているか（正直な整理）**

| 構成要素 | 根拠 |
|---|---|
| 件数の頭打ち（飽和曲線） | 定性調査の**データ飽和（saturation）**の知見。少数サンプルで大半の発見が出て追加の新情報は逓減する（Guest et al. 2006、Nielsenの5ユーザーテスト） |
| 多様性（独立ソース重視） | 研究手法の**トライアンギュレーション**（独立した複数の情報源による裏付け）。同一人物の繰り返しは独立した裏付けにならない |
| 鮮度の半減期減衰 | 知識の陳腐化モデル（文献計量学の「引用半減期」と同型）。市場・ユーザー行動は変わるため古い根拠は割り引く |
| 反証の減点・一級市民化 | 反証主義と**確証バイアス対策**。医療のエビデンス評価**GRADE**が「結果の非一貫性」で証拠の質を下げるのと同じ構造 |
| 4段階レベル表示 | GRADEの4段階（High/Moderate/Low/Very low）に倣った離散化 |

> **ただし——式と係数は「設計仮説」**。構成要素の選定には上記の根拠があるが、式の形・手法の重み（面談1.0/Slack 0.6等）・半減期12ヶ月の具体値は実証された標準ではない。だからこそ ①内訳を必ず開示 ②係数は設定で変更可 ③運用実データ（承認率、レビュー時の体感とのズレ）で校正する。スコアが信頼を失ったら数値を隠し4段階レベルだけにする退路も残す。

### 2.4 剪定 — いつアーカイブするか

状態に `archived` はあるが、**いつ・誰が・どの基準で**が未定義だと、インサイトは増える一方になる。

**なぜ剪定するのか（理由を正確に）**: 保存容量が理由ではない。剪定が要る本当の理由は2つ:

1. **人が一覧を読めなくなる** — インサイトが数百件になると、そこから選べない
2. **照合にノイズが増える** — 関連の薄いインサイトが候補に混ざり、提案の質が落ちる

**アーカイブ候補の条件**（cronで週次に判定し、`/review` に提案として出す。自動でアーカイブはしない）

| 対象 | 条件 |
|---|---|
| インサイト | 確信度が「仮説」のまま × 90日間参照ゼロ × 鮮度切れ（新しい根拠が来ていない） |
| ファクト | どのインサイトにもリンクされていない × 180日経過 |

`last_referenced_at` / `reference_count` は詳細画面を開いた回数を記録する。**これは「使われた」証明にはならないが、「使われていない」の検出には十分**（開かれてすらいないものは確実に使われていない）。剪定の材料としてのみ使い、価値の指標には使わない。

**「使われたか」は課題仮説リレーションで測る。** 既存のNotionインサイトDBには課題仮説へのリレーションが張られている（§6.5）。**そこにリレーションが付いたインサイト＝実際に仮説の根拠として使われた**ということ。週次で読むだけ（書き込みはしない）で、閲覧回数より遥かに正確な使用実態が得られる。

将来、仮説の**検証結果**（当たった／外れた）まで読めば、「確信度が高いインサイトから立てた仮説は本当に当たりやすいか」が測れる。これは§2.3で「未検証の仮説」と断った確信度モデルの、最も強い校正材料になる（§8.4）。

## §3 AI処理 — Claude Codeのスキルとして実行する

専用パイプライン基盤（キュー・ワーカー・イベントバス）は**作らない**。AI処理はすべてClaude Codeのスキルとして実装し、手動またはcronで起動する。基盤は段階1（案1）ではNotionだけ、段階2（案5）ではBigQueryだけ（§4）。

下の表は段階1（すべてNotion）の動作。段階2に移ると、読み書きの相手がNotion MCPからBigQuery MCPに変わるだけで、やることは同じ。

### 3.1 スキル構成（4本）

| スキル | やること | 起動 |
|---|---|---|
| `/research-ingest` | 議事録のリンク/本文を受け取る → リサーチDBに1行作る（原文はリンクで参照）→ ファクト抽出（引用必須）→ どの問いに紐づくか確認（既存から選ぶ / その場で新規登録）→ ファクトDBへ書き込み → **確認ビューのリンクを返す** | 手動（議事録を渡すとき） |
| `/insight-match` | 新ファクトを既存インサイトと照合（インサイトDBを意味検索で絞る、数十件なら全件読む → 支持/反証を判定）→ 各ファクトの `review_status` を3群に振り分け → 根拠リンクを作り、確信度を計算して書く | ingest後に続けて実行 |
| `/review` | 「要確認」に残っているファクト、見直しが必要なインサイトをまとめて提示し、**まとめて承認/却下** → 反映。状態変更（アーカイブ等）もここで行う | 手動（気が向いたとき） |
| `/insight-report` | 週次まとめ（新規・要見直し・確信度変動）をNotionページとして生成。あわせて**アーカイブ候補**（§2.4）と**ルール化の提案**（§8.2）を出す | cron（週1） |

> **承認はチャットではなく「確認ビュー」で行う**（UXレビューで方針変更）
> 当初は「スキル実行時にチャットでその場で聞く」としていたが、**38件をチャットのテキストで流し込むのは最も不向きな提示形式**（一覧できない・絞り込めない・後から見返せない）で、実質「見ずに承認」になる。AIを提案までに留める設計が形骸化してしまう。
> 正しくは、スキルは**「38件を仕分けました」というビューのリンクを返すだけ**にし、承認はファクトDBのボードビュー（§7.2）で行う。MVPではNotionの標準機能だけで作れるので、専用画面は要らない。
> その場で処理しなかったものは `review_status` が「要確認」のまま残り、`/review` から同じビューでさばく。

**リサーチクエスチョンの登録**

問いDBは**1つだけ**置く。下書き用と確定用に分けない（分けると同じ問いが2箇所に存在して混乱する）。

- 人はNotionの問いDBに行を追加するだけ。**`id` 列が空＝まだスキルに認識されていない**
- `/research-ingest` の実行時に問いDBを**1回クエリ**し、`id` が空の行にIDを振って書き戻す（問いは数十件規模なので1リクエストで済む。巡回cronもURL貼り付けも不要）
- IDが入った行にはリサーチ数・インサイト数がスキルから書かれ始める。これが「認識された」ことの表示を兼ねる

これは編集の同期ではなく**新規作成の検知**なので競合が起きない。段階2に移っても同じやり方をそのまま使える。

### 3.2 原則（基盤がなくても守るもの）

- **人間の承認なしにデータ本体を変えない**。必ずその場の確認か `/review` を通す
- ファクトは引用必須（原文の引用が取れないファクト文は登録しない）
- 段階1では構造化された監査ログを持たない（案1の項）。代わりに**インサイトの変更には必ず `update_reason` を1文書く**。段階2で監査ログを導入したら、書き込みと監査ログ追記を必ずセットにする
- **Notionへの読み書き処理は1ファイルに集約する**（§4.11-5）。段階2で差し替えるのはそこだけにする
- スキルは何度実行しても安全（リサーチDBの `content_hash` で二重取り込みを防ぐ）
- レビュー運用: ファクトは実測38件/本のため**議事録1本＝1回の一括承認**。個別に丁寧に見るのは新インサイト・見直し・反証リンクに集中
- **人の指摘は必ず記録する** — 修正・削除・追加・不調の報告を受けたら、要約1文にして確認を取りフィードバックDBに入れる（§8.1）。会話の全文は保存しない
- スキルファイルは**150行を目安**に保つ。ルールを1つ足すときは効いていないものを1つ削るか統合する（§8.3）

## §4 アーキテクチャ — 5案と、採用する2段

ドメインモデル（§2）とスキル構成（§3）は、どの案でも変わらない。違うのは「**マスタをどこに置き、画面を何にするか**」だけ。5案をすべて残したうえで、採用する道筋を決める。

### 4.1 決定 — 案1で始めて、案5へ移る

| | 段階1（MVP）**案1: すべてNotion** | 段階2（移行先）**案5: BQ ＋ BQ MCP ＋ Artifact** |
|---|---|---|
| ストア | Notionだけ（7つのDB） | BigQueryだけ |
| 画面 | NotionのDBビュー | Claude Artifact |
| Claudeの接続先 | Notion MCP | **公式BigQuery MCP** |
| 同期のコード | **0行**（ストアが1つなので同期という概念がない） | **0行**（投影する先がない） |
| いつ | 今すぐ着手 | §4.10のトリガーに当たったとき |

```
段階1（MVP）: すべてNotion
  議事録 ──▶ Claude Codeスキル ──▶ Notion（問い・リサーチ・ファクト・インサイト・根拠リンク）
                                      ▲
                                      └── 人が見る・書く（既存の課題仮説DBへのリレーションもここ）

段階2: BQ ＋ BQ MCP ＋ Artifact（Notionを使わない）
  議事録 ──▶ Claude Codeスキル ──▶ BigQuery（唯一のストア）
                                      ▲
                                      │ 公式BigQuery MCP
                                      ▼
                                   Artifact（閲覧・編集・承認・分析キャンバス）──▶ 人
```

**この2段にした理由**

- **どちらの段階も同期のコードが0行。** 本設計で一番壊れやすかったのは「2つのストアの間で同じデータをどう合わせるか」だった。案1はストアが1つ、案5も投影する先がないので、その問題がどちらにも存在しない。**案2〜案4は必ず同期を抱える**ため、通過点にしない
- **BigQuery MCPはArtifactとセットで使う。** BQに置いたデータをClaude ArtifactからMCP経由で読み書きする形であって、Notionと組み合わせるものではない
- **移行しても自作プログラムが要らない。** Googleの公式マネージドMCPサーバ（`bigquery.googleapis.com/mcp`）を使うので、同期サーバもカスタムコネクタも立てない

> **用語**: **MCP** ＝ Claudeが外部サービスを読み書きするための接続の規格。**BigQuery MCP** ＝ Googleが運用している公式のMCPサーバで、自分でサーバを立てずにClaudeやArtifactからBigQueryへSQLを実行できる。`execute_sql_readonly`（SELECTのみ）と `execute_sql`（INSERT/UPDATEもできる）の2つの窓口がある。

### 案1: すべてNotion 【段階1で採用】

NotionのDB群がマスタ兼画面。Claude CodeはNotion MCPだけを読み書きする。BQなし。

```
議事録 ──▶ スキル ──▶ Notion（マスタ兼画面）──▶ 人が見る・書く
```

| メリット | デメリット |
|---|---|
| **ストアが1つで同期が不要**（本設計で最大の複雑さが存在しない） | **行数** — ファクトが年4,000〜6,000件（実測38件/議事録）。3年で1.5万〜2万件 |
| **最速で始められる**（DBを作れば今日から） | **横断集計ができない** — 現在のプラン（Business ＋ Notion AI）ではSQLは1つのDBの中だけ |
| コメント・通知・モバイルが最初からある。運用対象ゼロ | **構造化された監査ログを置けない** — 監査ログはファクト以上に行数が増える |
| **既存のインサイトDB・課題仮説DBのリレーションがそのまま使える**（§6.5） | 分析キャンバス・確信度の内訳の図は作れない |

> **過去の「不採用」判断を訂正する**
> v2〜v7ではこの案を不採用としていた。その根拠2つは**調べ直した結果、誤りだった**。
> ① 「Notionには意味検索がないので自動照合ができない」→ **できる。** Notion MCPの検索は対象DBを指定した意味検索に対応している（このセッションで動作を確認）。さらに**照合の相手はインサイト（数十〜百件）であってファクト全件ではない**ので、数十件ならClaudeがまとめて読んで支持/反証を判定できる
> ② 「飽和曲線や半減期をNotionの数式で書けないので確信度が計算できない」→ **Notionが計算する必要がない。** 計算するのはClaude。Notionは結果の数値を1列持つだけ。むしろ数式・ロールアップを**使わないこと**がNotionを重くしない条件そのもの（劣化の主因は行数ではなく数式・ロールアップの多用）

**判定**: 中核である照合と確信度は成立する。弱点は行数・横断集計・監査ログの3つに絞られ、いずれも**MVPの間は困らない**。**段階1として採用する。**

**段階1のDB構成（7つ。うち1つは既存）**

| Notion DB | 中身 | 年間の行数 | 新規/既存 |
|---|---|---|---|
| 問いDB | リサーチクエスチョン | 数十 | 新規 |
| リサーチDB | 議事録などの調査1件 | 約150 | 新規 |
| **ファクトDB** | 事実1文＋引用＋話者＋仕分けステータス | **4,000〜6,000** | 新規 |
| インサイトDB | 解釈・確信度・状態 | 数十〜百 | **既存を使う**（§6.5） |
| **根拠リンクDB** | どのファクトがどのインサイトを支持/反証するか | **約3,000** | 新規 |
| フィードバックDB | 人からの指摘の要約1文（§8.1） | 数百 | 新規 |
| 学びDB | 繰り返した指摘から作った改善ルール（§8.2） | 数十 | 新規 |
| （課題仮説DB） | 組織の既存DB。**読むだけ・一切書かない** | — | 既存 |

行数の95%はファクトDBと根拠リンクDBに集中する。

> **横断集計ができない問題への対処 — 根拠リンクDBにファクトの属性を写しておく**
> 確信度の計算には「そのインサイトを支持する根拠が、いくつの独立したリサーチから、どの手法で、いつ得られたか」が要る。本来はファクトDBと結合して取るが、複数DBをまたぐ集計が書けない。
> そこで**根拠リンクDBに、ファクト側の変わらない属性を最初から書き写しておく**（発言者の属性・リサーチの種別・発生日）。後から変わらない値なので写しがずれない。これで「インサイトXの根拠リンクを全部取る」という**1つのDBへの絞り込みだけ**で計算材料が揃う。件数も数十件なのでSQLすら要らずClaudeが読んで計算できる。

> **段階1で「できないこと」を先に認める**
> ・**構造化された監査ログ** — 作らない。Notionのページ更新履歴で「誰がいつ」は追える。「なぜ」はインサイトの `update_reason` に1文書く。検索・集計できる監査ログは段階2で導入する
> ・**全ファクトを横断した分析** — 段階2で行う。MVPで必要になる場面がない
> ・**埋め込み（ベクトル）を自分で持って閾値を調整する** — Notionの検索に任せる。校正は段階2から

### 案2: BQマスタ × Notion GUI 【採らない】

Claude Codeのスキルに議事録を渡すと、ファクトを抽出して**BQに登録し、続けてNotionにも登録（投影）する**。人はNotionを見て、必要なら編集する。BQが全量・履歴・計算のマスタ。

```
議事録 ──▶ スキル ──▶ BQ（マスタ・全量）──投影──▶ Notion ──▶ 人が見る
                              ▲                       │
                              └────── 編集を取り込む ──┘  ← ここが双方向
```

| メリット | デメリット |
|---|---|
| 照合・確信度計算・監査ログがSQLで確実に作れる | **同期の造り込み** — 所有権固定・hash差分・429対策・夜間突合（§6）。運用の複雑さが増える |
| 承認率などの計測が初日からSQL一発 | **ファクト全量の閲覧面がない** — 38件/本により直近30日＋リンク済みしか置けない |
| Notionの閲覧・コメント・通知はそのまま使える | 開始時点で投影の実装が必要になる |

> **案2を採るなら、Notionから直接編集させず「更新もスキル経由」にする**
> 人がNotionのページを直接書き換えると、その変更をBQへ取り込む仕組みが必要になる——巡回して差分を見つける、自分の書き込みを拾わないようにする、競合したときどちらを正とするか決める、監査に残す。**これは対象がステータス1項目でも、文言まで含めても、必要な仕組みの量はほとんど変わらない。**
> 一方、更新を `/review` などの**スキル経由**にすれば、書き込みは常に BQ→Notion の一方向だけになり、逆方向の取り込みが丸ごと不要になる。**案2の最大の弱点がこれで消える**（残るのは投影の実装だけ）。
> **判断するのは技術ではなく気持ちの強さ。** 「見ていて気づいたその場でNotionから直したい」という要望が実際に強いかどうかで決める。強くなければ更新はスキル経由にする。強ければ双方向同期のコストを払うか、案4（Notionは読み取り専用にして操作はArtifact）へ寄せる。詳しくは§4.8。

**判定**: 中核要件はすべて成立する。**更新をスキル経由にすれば双方向同期は消える**ので、この案の弱点は「投影の実装が必要なこと」と「ファクト全量の閲覧面がないこと」に絞られる。それでも案1で始めれば投影すら書かずに済むため、**通過点にはしない。**

案2に、Claude Artifact＋公式BigQuery MCPによる**読み取り専用の閲覧画面**を足す。検索・全量ファクト一覧・インサイト詳細の閲覧をArtifactが担う。

議事録 ──▶ スキル ──▶ BQ（マスタ）──投影──▶ Notion ──▶ 人が見る・編集する

                        │  └── 編集を取り込む ─┘  ← 双方向は案2のまま

### 案4: 更新Artifact ＋ Notionは読み取り専用の共有ボード 【採らない・ただし退避先】

操作（閲覧・編集・承認・分析キャンバス）は**すべてArtifactで行い**、Notionは**BQから一方向に流し込むだけの読み取り専用ボード**として残す。Notionからは一切編集しない。

```
議事録 ──▶ スキル ──▶ BQ（マスタ）──投影──▶ Notion ──▶ 人が見る・議論する
                        ▲  │                            （編集はしない）
          人が操作する ──┴──┴──▶ Artifact（閲覧・編集・承認・キャンバス）
```

**案5との違いは「Notionを残すかどうか」だけ。残す理由は2つ**——① **議論の場**（インサイトにコメントを付けて会話できる。Artifactにこの機能はない）② **claude.aiを開かない人への共有**（ログインもコネクタ同意も要らない）。逆に言えばこの2つが要らないなら案5でよい。

| メリット | デメリット |
|---|---|
| 同期が**一方向（BQ→Notion）だけ**になる。案2で必要だった逆方向の取り込み（所有権の固定・競合解決・エコー防止）が丸ごと不要 | それでも**投影の実装は要る**（差分検知・429対策・投影上限） |
| コメント・気軽な共有を保ったまま、操作性はArtifactで得られる | Notionの行数制約は残る（投影対象を絞る必要がある） |
| **既存の課題仮説リレーションを保てる**（§4.12） | 画面を全部Artifactで作る手間は案5と同じ |

**判定**: 採らない。ただし**§4.12の「案5に移ると失うもの」が実際に問題になったときの退避先**として残す。案5から案4へは、インサイトDBへの一方向投影を足すだけで移れる。

### 案5: BQ ＋ BQ MCP ＋ Artifact（Notionを使わない）【段階2で採用】

Notionを構成から外し、**閲覧も更新もすべてArtifact上で完結**させる。ストアはBQ1つだけ。画面はArtifact、AI処理はClaude Codeスキル、その橋渡しがBigQuery MCP。

```
議事録 ──▶ スキル ──▶ BQ（唯一のストア）◀──BQ MCP──▶ Artifact ──▶ 人
                                                （閲覧・編集・承認・キャンバス）
※ 投影する先がないので、同期の実装が存在しない
```

| メリット | デメリット |
|---|---|
| **同期がゼロ** — 所有権マトリクス・hash差分・夜間突合・429対策・投影上限のすべてが不要 | **画面をすべて自分で作る** — Notionが無料で提供していた一覧・フィルタ・並べ替えを実装することになる |
| **行数の制約から解放される** — 投影しないのでUI劣化も投影上限も無関係 | **コメント・議論の場がなくなる**（§4.12） |
| **確信度の内訳の図・支持/反証の並置・分析キャンバス**など、Notionでは作れない画面を自由に作れる | **閲覧にclaude.aiログインとコネクタ同意が必要** — 気軽な共有は失われる |
| 監査ログ・横断集計・ベクトル検索がSQLで確実に使える | **画面を直せるのは作成者1人**（下記） |

> **更新の危険範囲を絞る方法は2段階。サーバを立てずに始められる**
> **段階1: 権限だけで絞る（サーバ不要）** — 公式マネージドMCPの `execute_sql` を使い、*接続アカウントに「書き換えてよいテーブル」だけ書込権限を与える*。インサイト・提案・監査ログだけ書込可、ファクトとリサーチは読み取り専用にすれば、画面のバグが壊せる範囲がそこに限定される。
> **段階2: 操作そのものを限定する（サーバが必要）** — **MCP Toolbox for BigQuery**（Google公式OSS `googleapis/mcp-toolbox`）は、設定ファイルに*ツールを1つずつ定義する*方式。「提案を承認する」「インサイトの文言を更新する」といった**定型SQLとその引数だけ**を公開でき、定義していない操作は実行できない。ただし*これは自分で動かすプログラム*なので、Cloud Runなどに常時起動で置きカスタムコネクタとして登録する必要がある。
> **進め方**: まず権限で絞って始め、更新の種類が増えて「特定の操作だけに固定したい」となった時点でToolboxへ移る。*最初からサーバを立てる必要はない。*

> **重要な制約 — Artifactを更新できるのは作成者だけ**
> Artifactは**所有者（作成した人）しか更新できない**。他の人は共有されれば閲覧できるが内容を直せない。さらにコネクタを使う（＝BQに接続する）ページは*一般公開の共有ができない*。呼び出しは閲覧者自身の資格情報で実行されるため、各自がBQの権限を持っている必要もある。**つまり画面の改修担当が1人に固定される。** 1人運用なら問題にならない。
> **緩和策**: 画面のHTMLをリポジトリで管理し、Artifactはそこから発行した表示用の複製とみなす。こうすれば*誰でもソースを直せる*し、担当者が不在でも別の人が自分のArtifactとして発行し直せる（URLは変わるが内容は失われない）。

**判定**: 構造的に最もシンプルで、同期の問題が存在しない。段階1で溜めたデータをそのまま活かせる。**段階2として採用する。** ただし移行時に§4.12を必ず判断すること。

### 4.8 「Notionから直接更新したい」への回答

実運用では「Notionを見ていて、このインサイトはもう古いからアーカイブしたい」と思う場面が必ず来る。**ここでNotionを編集可能にすると、逆方向同期の仕組み一式が戻ってくる**——変更の検知（巡回）・自分の書き込みを拾わない仕組み・競合の解決規則・監査記録。*フィールドを1つに減らしても複雑さは減らない*という点が重要。

| やり方 | 必要になるもの | 評価 |
|---|---|---|
| **A. 更新はスキル経由にする**（`/review` で「アーカイブしたいものある？」と聞く） | なし（既存スキルの一機能） | **推奨**。定期的な棚卸しと相性がよい |
| B. Notionのページに「操作画面を開く」リンクを置く（案4・案5） | リンク1つ | 推奨。「見ていて気づいた → 1タップで操作画面へ」の導線になる |
| C. Notionのプロパティを編集可能にする | 逆方向同期の一式（巡回・エコー防止・競合規則・監査） | 非推奨。1項目のために仕組みが丸ごと必要になる |

> **Cを選ぶかどうかは「気持ちの強さ」で決める**
> これは技術の優劣ではなく運用の選択。**「その場でNotionから直したい」という要望が実際に強いか**を確かめてから決める。
> ・強くない（月に数回、まとめて棚卸しできれば十分）→ **A**。同期は一方向のままで済む
> ・強い（気づいたその瞬間に直せないと使われなくなる）→ 双方向同期のコストを払うか、**案4**（Notionは読み取り専用にして操作はArtifact）へ寄せる
> **段階1（案1）ではこの問題が起きない。** ストアがNotion1つなので、Notionから直接直しても取り込む先がなく、それがそのまま正しい値になる。この判断が必要になるのは案2〜案4を検討するときだけ。

### 4.9 Notionのページを物理削除してよいか

> **段階1（案1）— 人もシステムも消さない**
> Notionが原本なので、消したものは戻らない。ファクトは `status=retracted`（撤回）、インサイトはアーカイブ、古いファクトは `review_status=保管` で既定ビューから外すだけにする（§6.2）。**削除の代わりに「見えなくする」**のが原則。

> **案2〜案4（BQが原本）— 人は消さない。システムは消す**
> **人による削除は認めない。** Notionのページを人が消してもBQに原本があるため次の投影で復活する。「消したのに戻ってくる」のは混乱のもとで、削除を試みること自体が無意味になる。
> **一方、システムによる削除は積極的に行う。** 投影の対象から外れたもの——アーカイブ済みインサイト、30日を過ぎて根拠リンクも持たないファクト——は*アーカイブではなくページごと削除する*。Notionは行数が増えると表示が重くなるため、投影を軽く保つことが性能対策そのものになる。BQに全量が残っているので消しても何も失われない。

### 4.10 いつ案5へ移るか（移行トリガー）

次のどれか1つに当たったら移行を検討する。**当たるまでは移さない。**

| トリガー | 判定のしかた |
|---|---|
| ファクトDBの表示が体感で待たされる | ビューを開いてから一覧が出るまで、日常的に3秒以上かかる |
| ファクトDBが1万行を超えた | 行数を月1で確認（§4.13の実測で前倒しの必要が分かる場合もある） |
| 取り込み1本あたりの書き込み時間が邪魔になった | 議事録1本＝38件の書き込みに40秒前後かかる。これが待てなくなったとき |
| 横断集計・監査ログの検索・分析キャンバスが必要になった | 抽出粒度の校正や複数プロダクトの傾向分析を実際にやりたくなったとき |

**移行の手順と手間（見積り: データ移行2〜3日＋画面開発）**

1. NotionのDB7つを全件取得（100件/リクエスト。6,000行なら60リクエスト＝約20秒）
2. BigQueryのテーブル（§5）へ読み込む。IDはNotionのページIDではなく**スキルが振った安定ID**をそのまま使う（§4.11-4）
3. 埋め込みを一括生成（`ML.GENERATE_EMBEDDING`）
4. スキル4本の読み書き先をNotion MCPからBigQuery MCPへ差し替える（§4.11-5で1箇所に集約してあるため差し替え箇所は少ない）
5. Artifactの画面を作る（§7.1の7画面。ここが移行作業の大半）
6. NotionのDBはアーカイブして参照専用にする（消さずに1ヶ月置く）

### 4.11 移行を安く保つために、段階1の時点で守る5つの制約

これを守らないと移行が「作り直し」になる。**案1で始めることと、この5つを守ることはセット。**

1. **Notionの列は、将来のBigQueryのカラムと1対1に対応させる**（§5のスキーマの列名をそのままNotionのプロパティ名にする）
2. **数式・ロールアップ・DB間の集計を使わない。** 値はすべてスキルが計算して書いた「ただの数値・テキスト・セレクト」にする。Notion上でしか再現できない計算を作らない（性能対策と移行容易性が同じ答えになる）
3. **根拠リンクDBにはファクトの不変属性を写しておく**（案1の項）。移行後もこの形のまま使える
4. **IDは自分で振る。** NotionのページIDに依存せず、スキルが採番した安定ID（例: `fact_20260811_001`）を必ず列として持つ。参照関係をこのIDで持てば、移行時に参照が壊れない
5. **Notionへの読み書き処理はスキルの1ファイルに集約する。** 移行時に差し替えるのはそのファイルだけにする

### 4.12 案5に移ると失うもの — 移行時に必ず判断する

案5はNotionを使わないため、**段階1で使えていた3つが失われる**。技術ではなく運用の選択なので、移行のタイミングで判断する。

| 失うもの | 影響 | 対処の選択肢 |
|---|---|---|
| **インサイト → 課題仮説のリレーション** | 組織で既に動いているワークフローが切れる（§6.5）。**これが一番重い** | ① **インサイトDBだけNotionに残し、BQから一方向投影する**（＝案4の形。投影対象は数十〜百行なので軽い）② 課題仮説の運用ごとArtifactへ移す ③ リレーションを諦める |
| コメント・議論の場 | インサイトに対する会話ができなくなる | 議論はSlackで行い、**結論をインサイトの説明欄に書く**運用にする |
| 気軽な閲覧・共有 | claude.aiログイン＋コネクタ同意が必要になる | 週次まとめだけはMarkdownやメールで配る |

> **推奨は①。** 課題仮説DBは組織共有のもので、こちらの都合で運用を変えられない。インサイトDB（数十〜百行）だけをNotionに残せば、リレーションを保ったまま案5の利点（同期ゼロに近い・行数制約なし・自由な画面）をほぼ得られる。この形は**案4そのもの**なので、案4を「退避先」として残してある。
> ただし**MVPの間はこの判断をしなくてよい**。段階1ではNotionにインサイトがあり、リレーションはそのまま使えている。

### 4.13 着手前にやること — 1万件の実測（1日）

案1の唯一の未検証点は「ファクトDBが1万〜1.5万行になったとき、実際にどれくらい重いか」。ここに実測データがない。

- ダミーのファクト1万件をNotionのDBへ投入する（数式・ロールアップなしの、本番と同じ列構成で）
- 測るのは3つ: ①既定ビュー（登録日の降順・直近30日フィルタ）が表示されるまでの時間 ②DB内の検索の応答時間 ③スキルから100件取得するときの時間
- 3秒を超えるようなら、**MVPの時点で案5から始める**

この1日で、案1で始めてよいかどうかが確定する。

## §5 データ設計（段階1・段階2で共通の列定義）

ここに書く列の定義は、**段階1ではNotionのプロパティ名、段階2ではBigQueryのカラム名**としてそのまま使う（§4.11-1）。同じ名前を両方で使うことが、移行を安く保つ条件になる。

| | 段階1（Notion） | 段階2（BigQuery） |
|---|---|---|
| 置き場所 | すべてNotionのDB | すべてBigQuery（§4.12で①を選んだ場合はインサイトのみNotionにも投影） |
| 型 | セレクト・数値・テキスト・日付（**数式とロールアップは使わない**） | 下のスキーマのとおり |
| 段階1で使わないもの | `embedding` / `audit_logs` / `suggestions` / `sync_state`（案1の項） | すべて使う |

### 5.1 各テーブル（DB）の役割

| テーブル | 何を入れるか | なぜ必要か | 1行の例 |
|---|---|---|---|
| `products` | 社内プロダクトの一覧 | データの仕切り。検索を「このプロダクト内」に絞る | プロダクトX |
| `research_questions` | 明らかにしたい問い | リサーチをぶら下げる先。「何のために調べたか」を残す | なぜ週次レポートの閲覧率が低いのか |
| `sources` | 議事録などの調査1件 | ファクトの出典。原文に戻れるようにする | 2026-08-05 A社定例（Meet議事録） |
| `facts` | 事実1文＋その引用と話者 | インサイトの根拠になる最小単位。**本システムの素材** | 「田中さんは週次レポートを見ていないと述べた」＋原文引用 |
| `insights` | 解釈と確信度 | **資産そのもの**。最終的に読み返すのはここ | 「顧客は定型レポートより異常時の通知を求めている」確信度72 |
| `evidence_links` | どのファクトがどのインサイトを支持／反証するか | 確信度計算の入力。**この表がないと確信度が出せない** | ファクト#123 → インサイト#7 を supports（重み0.8） |
| `suggestions` | AIからの未処理の提案 | cronが後から作った提案の置き場。*段階2から。段階1はファクトの `review_status`＝要確認 とインサイトの状態＝要見直し で代替* | 「ファクト#123をインサイト#7の根拠に追加しますか」 |
| `audit_logs` | 変更の履歴（誰が・いつ・何を・どう・**なぜ**） | 「なぜこうなってる？」を後から追う。AIが勝手に変えていない証明。*段階2から。段階1はNotionのページ履歴＋`update_reason` で代替*（§4.1） | 8/10 14:32 確信度55→72（理由: 3社で同じ話が出たため） |
| `sync_state` | BQのIDとNotionページIDの対応表 | *§4.12で①（インサイトDBだけNotionに残す）を選んだ場合のみ必要* | インサイト#7 = Notionページ abc123 |
| `feedbacks` | 人からの指摘1件（要約1文） | 改善の材料。繰り返したらルールに昇格 | 「日程調整の発言はファクトにしないで」 |
| `learnings` | 繰り返した指摘から作った改善ルール | スキルが実行時に読んでプロンプトに入れる | 「進行・日程に関する発言はファクトにしない」 |
| `tags` / `taggings` | ペルソナ・テーマなどの分類 | 絞り込み用。*MVPでは使わない（スキーマだけ用意）* | 「新規ユーザー」「オンボーディング」 |

### 5.3 v1から変えたところ

> **重要な確認 — ベクトル検索（embedding）は使う。やめたのは「テーブルを分けること」だけ**
> **embedding（埋め込み）＝文章の意味を数百個の数値の並びに変換したもの。** 数値が近い＝意味が近いので「言葉は違うが同じことを言っているファクト」を探せる。BigQueryの `ML.GENERATE_EMBEDDING` で作り `VECTOR_SEARCH` で近いものを探す。*これが「新しいファクトを既存インサイトと自動照合する」という本システムの核そのもの*で、当然使う。
> **段階1（すべてNotion）では、この埋め込みを自分では持たない。** 照合はNotionのDB内の意味検索に任せ、相手はインサイト（数十〜百件）なので十分に成立する（案1の項）。自分で埋め込みを持って近さの閾値を調整できるようになるのは段階2から。
> v3で変えたのは置き場所だけ——`embeddings` という**別テーブルを作るのをやめ、facts / insights の列にした**。BigQueryは列指向（使わない列は読み込まれない）なので分けても速度の利点がなく、結合が増える分むしろ扱いにくいため。**機能は1ミリも減っていない。**

| 変更 | 理由 |
|---|---|
| `highlights` → **facts に統合** | 実態は「1ファクト＝1引用」であり、引用だけを独立して検索することがない。`facts.quote` と `quote_locator` で足りる |
| `fact_highlights` → **廃止** | ファクトと引用を多対多にする必要がなかった。複数箇所を引くケースは facts 側の配列で持てる |
| `insight_versions` → **廃止** | **audit_logs と重複**。監査ログが変更前後の差分を持つので過去の文言はそこから復元できる。同じ情報を2箇所に持つのは事故のもと |
| `embeddings` → **facts / insights の列へ移動** | 上記のとおり。*ベクトル検索の機能自体は変わらず使う* |
| `tags` / `taggings` → **残すがMVPでは使わない** | ペルソナ・テーマなどでの絞り込みは将来必要になる。スキーマは定義しておき、投入と画面はMVPの後に回す |

**設計メモ**
- データの仕切りは **product_id のみ**。主要テーブルは product_id でクラスタリング
- `audit_logs` は追記専用（UPDATE/DELETE権限を発行しない）
- 確信度の再計算は evidence_links の変化時＋日次の減衰更新（スケジュールドクエリ）
- キャンバス系テーブルは案4で分析キャンバスを作るときに追加する。今は作らない
- **`skill_runs`（スキルの実行記録）は作らない。** 用途のほとんどが他テーブルで足りることを確認済み: 取り込み失敗は `sources.ingestion_status`／二重取り込みは `content_hash`／承認率は `suggestions.status`／処理件数の分母は `SELECT COUNT(*) FROM facts WHERE source_id = X`／不在の可視化は `sources.occurred_at`。cronスキルが3本以上に増えたとき、またはAI利用コストを月次で把握したくなったときに追加する

## §6 Notion側の設計（DB構成・性能・既存資産との接続）

この節は**段階1（案1: すべてNotion）**の設計。Notionが**データの原本そのもの**になる。

段階2（案5: Notionを使わない）へ移ると、この節の大半は不要になる。ただし**列構成はそのままBigQueryのテーブル定義になる**ので、ここで決めた列名がそのまま引き継がれる（§4.11-1）。

### 6.1 DB構成と列

列名は§5のBigQueryのカラム名と1対1に対応させる。**数式・ロールアップ・DB間集計は1つも使わない**（§4.11-2）。

| DB | 主な列 | 書く人 |
|---|---|---|
| 問いDB | `id` / `product_id` / `question` / `status` / `created_at` | 人が新規行を作る → スキルが `id` を書き戻す |
| リサーチDB | `id` / `product_id` / `research_question_id` / `type` / `title` / `occurred_at` / `raw_ref`（原文リンク） / `content_hash` | スキルのみ |
| ファクトDB | `id` / `product_id` / `source_id` / `statement` / `quote` / `quote_locator` / `speaker` / `origin` / `status`（active/retracted） / **`review_status`**（要確認/裏付け/低関連/確定/却下） / `created_at` | スキルが書き、人は確認画面で `review_status` だけ変える |
| インサイトDB（既存） | `id` / `product_id` / `statement` / `description` / `status` / `owner` / `confidence_score` / `confidence_level` / `confidence_breakdown` / `last_evidence_at` / `falsification_condition` / `update_reason` ／ **課題仮説リレーション（既存）** | 下表のとおり列ごとに分ける |
| 根拠リンクDB | `id` / `fact_id` / `insight_id` / `stance` / `weight` / `linked_by` / `rationale` / `created_at` ＋**ファクトからの写し**（`fact_speaker` / `fact_source_type` / `fact_occurred_at`） | スキルのみ |
| フィードバックDB | `id` / `target_type` / `target_id` / `kind` / `summary` / `applied` / `created_at` | スキルが人の指摘を要約して書く |
| 学びDB | `id` / `category` / `observation` / `rule` / `status` / `feedback_ids` / `activated_at` | スキルが提案し、人が「適用中」にする |

`id` は**スキルが採番した安定ID**（`fact_20260811_001` など）で、NotionのページIDとは別に列として持つ（§4.11-4）。DB間の参照はこのIDの文字列で持ち、Notionのリレーション機能は原則使わない（例外は既存の課題仮説リレーション）。

> **なぜリレーションではなく文字列のIDで繋ぐのか**
> リレーションは件数が増えるとページの読み込みを重くする要因になり、さらに移行時にIDを付け替える手間が生まれる。文字列のIDならNotionでもBigQueryでも同じ意味を持つ。**画面上で辿る必要があるのは「インサイト → その根拠」だけ**で、これは根拠リンクDBを `insight_id` で絞れば済む。

### 6.2 性能を保つ3つのルール

1. **数式・ロールアップを使わない。** 表示の重さの主因は行数そのものより、行ごとに計算が走る列。確信度も根拠件数もスキルが計算して数値として書く
2. **既定ビューには必ずフィルタと並び順を付ける。** ファクトDBの既定ビューは「直近30日」＋「登録日の降順」。全件を開くビューは作らない（必要なときだけ検索で辿る）
3. **古いファクトは既定ビューから外す。** 削除はしない（原本なので消せない）。90日を過ぎ、根拠リンクを1つも持たないファクトは `review_status` を「保管」にして既定ビューの対象外にする

### 6.3 レート制限（429）対策

- Notion APIは平均3リクエスト/秒。書き込みは1つの流れに直列化し、1件あたり350ms間隔を空ける
- 429が返ったら `Retry-After` の秒数だけ止め、再発したら待ち時間を倍にする
- 議事録1本（ファクト38件＋根拠リンク）で**90〜120リクエスト＝約40秒**。この待ち時間が邪魔になったら移行トリガー（§4.10）

### 6.4 コメント・議論は取り込まない

Notion上のコメント・議論は**システムに取り込まない**。理由は2つ。

- **技術的に完全には取れない** — コメント取得APIが返すのは未解決のものだけで、解決済みは取得手段がない。取りこぼしが構造的に起きるものを「保存してある」と扱うのは危険。また全件一覧のAPIがなくページ単位でしか取得できないため、集めるだけで大量のリクエストを要し、書き込みと同じレート枠を食い合う
- **そもそも失われない** — 段階1ではNotionが原本なのでページを作り直さない。段階2でもインサイトのページは更新方式で扱うため、コメントは消えない

「議論の結論だけは残したい」場合は、**結論をインサイトの説明欄に書く**運用で対応する。取り込む仕組みを作るより、結論を書く運用のほうが実際に読み返される。

### 6.5 既存のインサイトDBと課題仮説DBへの接続

**新しいインサイトDBを作らない。既にあるDBをそのまま使う。**

Notionには既にインサイトDBがあり、そこから組織の課題仮説DBへリレーションが張られている。別のDBを作ると**その繋がりが切れる**うえ、繋ぎ直すには課題仮説DB側にプロパティを追加することになる（組織共有のDBなので避けたい）。

```
ファクトDB ──┐
             ├─ 根拠リンクDB ──▶ 既存のインサイトDB ──リレーション──▶ 課題仮説DB
リサーチDB ──┘                    （新規作成しない）      （人が張る・スキルは触らない）
```

**列ごとに書く人を分ける**

避けたいのは「**同じ列**を人とスキルの両方が書く」こと。**別々の列をそれぞれが持つ**なら競合しない。

| 列 | 書く人 |
|---|---|
| `confidence_score` / `confidence_level` / `confidence_breakdown` / `last_evidence_at` / 根拠件数 | **スキル**（計算結果を書く。人は編集しない） |
| `statement` / `description` / `status` / `update_reason` | **人**（解釈と公開・保管の判断は人のもの。スキルは提案するだけ） |
| **課題仮説リレーション** | **人（PdM）。スキルは絶対に触らない** |
| 既存インサイトDBに元からある他の列 | 触らない |

スキルは担当列だけを更新し、それ以外の列には書き込まない。

**段階2（案5）へ移ると、このリレーションが切れる。** どう扱うかは§4.12で移行時に判断する（推奨はインサイトDBだけNotionに残して一方向投影する形）。

**初期移行**

既存インサイトは2件のみ・作成者は1人なので、**手で列を埋める**。移行スクリプトは作らない。順番は ①既存2件に `id` と確信度の列を追加して手で埋める → ②新しいDB（問い・リサーチ・ファクト・根拠リンク）を作る → ③スキルを動かし始める。

**課題仮説DBは読むだけ**

スキルは課題仮説DBに一切書き込まない。週次で読んで「どのインサイトにリレーションが張られたか」を集め、実際に使われているかの把握に使う（§2.4）。組織のワークフローには影響しない。

## §7 画面と体験（UX）

UXレビュー（2026-08-11）を受けて追加。アーキテクチャの段階（§4）に関わらず、**この体験は必ず必要**。動作するプロトタイプは Claude Artifact を参照（画面の理想形として作ったもので、MVPではこれをNotionのビューで代替する）。

### 7.1 MVPで作る画面 — すべてNotionのビューで用意する

**MVPでは専用画面（Artifact）を作らない。** 下の7つはすべてNotionのDBビューとして成立する。

| # | 画面 | MVPでの作り方（Notion） | 主な利用者 |
|---|---|---|---|
| 1 | ホーム（週次まとめ） | `/insight-report` が週次でNotionページを1枚生成する | 閲覧者 |
| 2 | **取り込み確認 ★** | ファクトDBの**ボードビュー**（`review_status` でグループ化）。7.2 | オーナー |
| 3 | インサイト一覧 | 既存インサイトDBのテーブルビュー（確信度で並べ替え・状態でフィルタ） | 全員 |
| 4 | インサイト詳細 | インサイトのページ。確信度の内訳は本文に書き、根拠は根拠リンクDBを `insight_id` で絞ったビューを埋め込む | 全員 |
| 5 | 問い（リサーチクエスチョン） | 問いDBのビュー。人が新規行を足す場所でもある（7.5） | 全員 |
| 6 | ファクト一覧 | ファクトDBの既定ビュー（直近30日・登録日の降順）＋DB内検索 | オーナー中心 |
| 7 | ゼロ状態 | 各ビューの説明欄に「次にやること」を書いておく（7.6） | 全員 |

> **専用画面（Artifact）が要るのはどこか**
> Notionで作れないのは3つだけ。①確信度の内訳を図で見せる ②支持と反証を左右に並べる ③分析キャンバス（付箋を動かす）。**どれもMVPの必須ではない**。段階2（案5）へ移るときに、この7画面をすべてArtifactで作り直すことになる——それが移行作業の大半を占める。

### 7.2 取り込み確認画面 — 38件を3群に仕分ける

実測38件/本を平坦に並べると必ず読み飛ばされる。`/insight-match` が既に計算している照合スコアをそのまま使い、**AIが自動で3群に仕分けて提示**する（追加の計算コストはゼロ）。仕分けの結果はファクトDBの `review_status` に書く。

```
ファクトDBのボードビュー（review_status でグループ化）

[要確認 3〜5件]      [裏付け 20件]        [関連が弱い 15件]     [確定]      [却下]
 新インサイト候補     既存を支持するだけ    どれとも弱い
 反証・統合候補       ↓                    ↓
 ↓                    まとめて選んで        そのまま置く
 1件ずつ開いて判断     「確定」へ移す        （破棄しない）
```

- 人の注意力を「要確認」の数件に集中させ、残りは**開けば見られる**状態にする
- 一括承認はNotionの標準機能で足りる（複数選択 → `review_status` をまとめて変更）
- **取り消せる。** 状態を戻すだけでよく、データは消えない。このことを画面の説明欄に書いておく
- 「関連が弱い」も破棄しない。後で別のインサイトの根拠になりうるため

### 7.3 取り込み直後に返すサマリー（継続の要）

最大の事業リスクは「取り込む習慣が続かないこと」（§9）。投入の摩擦を下げるだけでは続かず、**入れた直後に価値が返ること**が必要。`/research-ingest` → `/insight-match` の完了時に必ず次を返す。

```
今回の取り込みでわかったこと
✓ 新しいインサイト候補が1件生まれました
✓ 「週次レポートは最初の画面で離脱している」の確信度が 兆候 → 検証済 に上がりました
⚠ 「オンボーディングの設定項目が多すぎる」に反証が1件 → 要見直しになりました
```

**「38件処理しました」ではなく「これがわかった」を主語にする。** 件数はシステムの都合であり、継続の理由にならない。あわせて週次まとめに「今週まだ取り込まれていません」という不在の可視化を入れる。

### 7.4 確信度の表示ルール

| 場所 | 出すもの | 出さないもの |
|---|---|---|
| 一覧 | 4段階バッジ（仮説/兆候/検証済/強固）＋段階ドット、根拠件数・発言者数 | **数値を出さない** |
| 詳細 | 数値＋メーター＋**内訳とセット**（支持12件・発言者9名・反証1件・最終更新3週間前） | — |

- 一覧に「72」と出すと自動的に順位比較の道具になるが、**式はまだ未検証の仮説**（§2.3）。検証されていない精度を信じさせるのは、課題4番目の「思い込みの強い施策判断」を自分で作り出すことになる
- 色だけで段階を伝えない。ラベル＋ドット（●●●○）を併記する
- `needs_review` は確信度のバッジとは**別軸**で警告表示する（レベルが低いことと、見直しが必要なことは別の情報）
- 詳細には確信度の推移（履歴）を出す。「仮説だったものが検証済に上がった」変化が信頼形成に効く

### 7.5 リサーチクエスチョンの登録 — 画面とスキルの両方

課題認識の1番目「前に誰かが同じことを聞いたことに気づけない」に直接応える画面。**これが無いとその課題は解決しない。**

登録の経路は2つ。**専用スキルは作らない。**

1. **議事録を渡すとき（主）** — `/research-ingest` の中で「この議事録はどの問いに紐づきますか」と聞き、既存から選ぶか、その場で新規登録する。問いの登録頻度は月に数件程度なので、独立した操作にする必要がない
2. **問い一覧画面から** — 一覧・状態管理（進行中/回答済み/保留）と、新規登録

登録時は**似た問いを自動照合して警告する**（「なぜ週次レポートの閲覧率が低いのか という問いが既にあります」）。これが重複リサーチの防止そのもの。

### 7.6 ゼロ状態（最初の1〜2週間）

立ち上げ直後はインサイトの大半が「仮説」で確信度も低い。これは正常だが、説明がないと「大した発見をしていない」という誤った第一印象になり、そのまま離脱につながる。**低いことを失敗に見せない**のがここの仕事。

- インサイトが空/少数: 「まだ育てている途中です。議事録を3〜5本取り込むと照合が効き始めます」
- 問いが0件: 「最初に明らかにしたいことを1つ決めましょう」＋登録導線
- 検索0件: 「一致するインサイトはありません。**まだ誰も調べていないテーマかもしれません**」→ 問いとして登録する導線（重複検知の価値と表裏なので、ポジティブな空状態にする）

### 7.7 引用とエラーの扱い

- **引用**: 一覧では事実文（statement）を主に見せ、引用は折りたたみ。開くと前後の文脈を数行含め、`quote_locator` から元の議事録へのリンクを併記する。引用は捏造防止の担保なので、画面上で検証可能でなければ意味がない
- **エラー**: 無言で失敗させない。①リンクが読めない →「共有設定をご確認いただくか、本文を貼り付けてください」 ②ファクト0件 →「事実らしい発言が見つかりませんでした。形式が対象外の可能性があります」 ③重複 →「この議事録は8/5に取り込み済みです」

### 7.8 閲覧者とオーナーで見せるものを分ける

- 閲覧者のホームは**週次まとめ**。未承認の提案・draft状態のインサイトは**見せない**（未確定情報はノイズになる）
- インサイト詳細には「誰が・いつ確定させたか」（監査ログの情報）を閲覧者にも見せる。AIが生成する仕組みである以上、人が確認した痕跡が見えることが信頼の条件

## §8 改善ループ — システム自体を良くする

### 8.0 2つのループを混同しない

| | インサイトの更新ループ | **システムの改善ループ（この節）** |
|---|---|---|
| 何が良くなるか | 個々のインサイトの確信度・鮮度 | AIの抽出・照合の精度、スキルの挙動 |
| きっかけ | 新しい根拠・反証の到着 | **人からの指摘**（修正・削除・追加・不調） |
| 仕組み | §2.2 の状態遷移（既にある） | この節（足りていなかった部分） |

前者は設計済み。**足りていなかったのは後者**——「提案の承認率が低いスキルをどう直すか」「確信度の係数をどう校正するか」の具体的な手順。

### 8.1 人の指摘を溜める（feedbacks）

ファクトやインサイトを見た人は必ず言う。「そこは登録しなくていい」「この解釈はこうだよ」「スキルの挙動がおかしい」。**これが改善の唯一の材料**なので、その場の修正で終わらせず記録する。

- **会話の全文は保存しない。** AIが**1文に要約して、その場で人に確認を取ってから**入れる
  > 「日程調整に関する発言はファクトにしない」という指摘として記録します。よろしいですか？
- 記録するのは: 対象（ファクト/インサイト/提案/スキル）・種別（修正/削除/追加/不調）・要約1文・その場で適用したか
- 「修正前後のdiffと理由の一文」があれば、生ログの価値のほとんどは取れる（diffは `audit_logs`、理由は `audit_logs.reason`）

### 8.2 繰り返したらルールに昇格させる（learnings）

**1回目の指摘は「その場の修正」にしか見えない。2回目・3回目で初めてパターンだと分かる。** ここを人の記憶に頼らず仕組みにする。

- 同じ趣旨のフィードバックが**3件**溜まったら、`/review` と週次まとめで提案する
  > 似た指摘が3件たまっています。ルールにしますか？
  > 「日程調整・会議進行に関する発言はファクトにしない」（8/5・8/12・8/19の指摘より）
- 類似判定は**既にある埋め込みをそのまま使う**（`feedbacks.embedding`）。追加コストはほぼゼロ
- 承認されたら `learnings` に登録し、`status=適用中` に。**スキルは実行時に「適用中」のルールを読んでプロンプトに入れる**

これは本システムのドメインモデルと同じ形（ファクトが複数集まってインサイトになる ＝ 指摘が複数集まってルールになる）。ただし実装は別テーブルにする（product_id や source が噛み合わないため、無理に統一しない）。

### 8.3 効き目の測定と剪定（総量固定）

**ルールを書くだけでは改善しない。** 過去に同種の運用でルール集が983行まで膨れ、全ルールが薄まって効かなくなった実例がある。最初から剪定を設計に入れる。

- **効き目**: ルールを `適用中` にした日以降、同じ趣旨のフィードバックが減ったか。`learnings.activated_at` と `feedbacks.created_at` の突合で見る。段階1ではNotionの2つのDBを読んで手で突き合わせる（件数が少ないので足りる）。段階2に移ったら1本のSQLで出せるようになる
- **判定**: 3ヶ月フィードバックが来ない → `効果確認済`。適用しても減らない → `廃止` にするか、**プロンプトより強い手段（コード側で機械的に除外）へ格上げ**する
- **総量固定**: ルールを1つ足すときは、効いていないものを1つ削るか統合する。スキルファイルは**150行を目安**に保つ。上限を宣言するだけでは守れないので、「足すときに削る」を運用ルールにする

### 8.4 確信度の係数を校正する

§2.3で「式と係数は設計仮説であり、運用の実データで校正する」と書いた。その具体的な手順。

- **月次で、後から反証が出たインサイトのレベル分布を見る。** 「強固」「検証済」だったものに反証が出る率が高ければ、**係数が甘い**（多様性の重みを上げる、半減期を短くする等）
- **レビュー時の体感とのズレを拾う。** 「これが検証済のはずがない」という指摘は `feedbacks` に `category=確信度` で記録し、3件溜まったら係数を見直す（8.2と同じ仕組みに乗せる）
- 係数を変えたら `audit_logs` に `actor_type=system, reason=係数校正` で記録し、前後の分布を比較できるようにする

## §10 リスクと未決事項

### リスク

| リスク | 緩和策 |
|---|---|
| **取り込み習慣が続かない**（最大の事業リスク） | 「リンクを貼るだけ」の1アクションに絞る。v2で自動化 |
| レビュー負荷（実測38件/本） | 議事録1本＝1レビューの一括承認。個別レビューはインサイト系のみ |
| 確信度が信頼されない | 内訳の完全開示・係数調整可・4段階主表示。承認率とのズレで校正 |

| **Notionの表示速度が想定より早く劣化する** | 着手前に1万件で実測する（§4.10）。基準を超えたらMVPから段階2で始める |
| **段階1に監査ログがない** | インサイトの変更には `update_reason` を必須にする。Notionのページ履歴で「誰がいつ」は追える。段階2で構造化された監査ログを入れる |

| **案5へ移ると課題仮説リレーションが切れる** | §4.12で移行時に判断する。推奨はインサイトDBだけNotionに残して一方向投影する形（＝案4） |
| **案5: 画面を直せるのが作成者1人** | 画面のHTMLをgitで管理し、Artifactは発行した複製として扱う。担当者が不在でも別の人がソースから発行し直せる。*段階1ではArtifactを作らないので当面は無関係*（§7.1） |
| 抽出粒度（38件は多すぎる可能性） | 最初の数本で「根拠リンクに使われた率」を測り重要度フィルタを校正 |

### 未決事項

- Slack・Chatworkスレッドの「1リサーチ」の切り方（スレッド単位か期間単位か）
