- **日付**: 2026-11-18
- **担当**: team-lead（設計）。実装は Phase ごとに委譲する
- **complexity**: L（全体）。本 plan で確定させるのは Phase 0 と Phase 1。Phase 2 は別の plan
- **risk_level**: high（権限・無人実行・エージェント間プロトコルの方向性を含むため）

  - `scripts/model-mode.sh` はクラウドでは `src=none` で Pro 側に倒れるので、実体はセッション API で確認している。

- **ADR参照**: `docs/adr/ADR-019-always-on-operation.md`（v2）

## SPEC

- **要求の再記述**: Anthropic の「Building always-on agents」が示す5部品（inbox / timers / memory / permissions / outbox）を agent-crew に当てはめる。owner が見ていない間も安全に1歩ずつ進み、判断が要るものだけを owner に返す開発環境にする。前回提案した6項目（許可の縮小・Outbox の静音化・timer・キューの正本移行・memory 整理・シグナル修正）を、実装可能な単位まで設計する。
- **暗黙の前提**:
  - 既存の工程（fable-class・critic・学習ループ・ADR-012 の正本一箇所）を壊さない。
  - 対話運用の体験を悪くしない。
  - Claude Code と Codex の共通契約（`AGENTS.md`）を守る。
  - 利用枠は有限である。
  - repo・Git・テストの結果を真実源とする。
- **不明点**:
  - 自己解決済み（エビデンス節を参照）:
    - クラウドに Obsidian は無い。
    - `_queue.json` と `_signals.jsonl` は git 追跡下にある。
    - シグナル行の KeyError を再現した。
    - フックのドリフトと、毎ターンの再送を確認した。
    - クラウドの `model-mode.sh` は `src=none` になる。
    - 対話セッションでは `CLAUDE_CODE_SESSION_ATTENDED=1`。
    - スケジュール実行の cron は `CRON_TZ=<IANA>` の前置を受け付ける（スケジュール作成ツールの仕様に明記されている）。
  - 実装前に確認する（各タスクの前提条件に記載）:
    - Claude Code の permission ルールの書き方（T0-4）
    - unattended run での permission モード・環境変数・push 通知の挙動（T1-5）
    - クラウドから `gh` で書き込めるか（Phase 2）
  - owner にしか決められないこと:
    1. daily-brief の時刻（初期値: 平日 7:47 JST）
    2. main のブランチ保護を有効にしてよいか
    3. Slack 通知の既定値を `owner` にしてよいか
    4. Actions secret の `SLACK_WEBHOOK_URL` は設定済みか。ローカルのシェルで `SLACK_WEBHOOK_URL` を export しているか（現在 Slack が鳴っているか）
- **テーゼ**: 常時稼働とは「ずっと動く」ことではない。「状態と権限は run の外に置き、起こされた run は1歩だけ進め、owner の判断が要るものだけを返す」ことである。

### ミニADR

- **背景**: 並列 run や無人 run を可能にするには、状態と送信記録を run の外に出し、権限の主役を外側の層に置く必要がある。
- **決定**: ADR-019 v2 の D1〜D7。Phase 0（土台）と Phase 1（daily-brief だけの読み取り run）を、本 plan で実装可能な粒度まで確定する。Phase 2 は方向性だけを確定する。
- **理由**: Phase 0 と Phase 1 は状態を書かないので衝突しない。そのうえで、毎ターンの再送を止められ、権限を狭められ、毎朝の要約が届く。書く run は Inbox が git の外に出てから始める。
- **却下案**: ADR-019 の「却下した案」A〜G を参照。

### マイクロタスク一覧

パスはリポジトリルート（`/home/user/agent-crew`）からの相対パスで書く。テストは pytest で書き、シェルスクリプトは `subprocess.run` で起動する。

**T0-3 Outbox の重複除去と静音化**
- **complexity**: M / **risk_level**: medium
- **目的**: Slack に送るのを「状態の変化」だけにする。既定では needs-owner（BLOCKED）と result（スプリント完了）だけを送る。
- **対象ファイル**: `hooks/subagent_stop.sh`、`tests/test_subagent_stop.py`、`README.md`（「Slack 通知」節だけ）
- **変更内容**:
  1. **送信記録**: 状態ディレクトリを `STATE_DIR="${AGENT_CREW_STATE_DIR:-${XDG_STATE_HOME:-$HOME/.local/state}/agent-crew}"` とし、ファイル `$STATE_DIR/outbox-$(printf '%s' "$REPO_ROOT" | cksum | cut -d' ' -f1).sent` を使う（1行1キー）。`slack_notify` の呼び出しを、新しい関数 `notify_once <key> <agent> <message>` 経由にする。この関数は、キーが記録済みなら何もしない。未記録なら `slack_notify` を呼んで、キーを追記する。キーは次のとおり。
     - BLOCKED: `blocked:<slug>:<その slug の最後の block イベントの ts>`
     - スプリント完了: `sprint-done:<sprint>`
     - handoff と完了: `handoff:<slug>:<status>`
     - 差し戻し: `retry:<slug>:<retry_count>`
  2. **レベル**: 環境変数 `AGENT_CREW_SLACK_LEVEL` を読む。
     - `owner`（既定）: BLOCKED 分岐とスプリント完了分岐だけが `notify_once` を呼ぶ。READY_FOR_* の分岐（handoff・完了・差し戻し）は Slack に送らない。標準出力の NEXT STEP 提示は従来どおり出す。
     - `all`: すべての分岐が `notify_once` を呼ぶ（重複除去はかかる）。
     - それ以外の値: stderr に `WARN: unknown AGENT_CREW_SLACK_LEVEL=<値>, using owner` と出し、`owner` として扱う。
  3. **テスト**を `tests/test_subagent_stop.py` に追加する。
     - 共通の準備:
       - `PATH` の先頭に stub の `curl`（呼ばれるたびに1行追記するだけのシェルスクリプト）を置く。
       - `SLACK_WEBHOOK_URL=http://example.invalid`、`AGENT_CREW_STATE_DIR=<tmp>`、`VAULT_DIR` と `LESSONS_FILE` は一時ディレクトリを指す。
       - `QUEUE_FILE=<tmp>/_queue.json` を指定し、stdin は空でフックを実行する。
     - ケース:

       | ケース | レベル | キューの状態 | 実行回数 | 期待する curl 呼び出し |
       |---|---|---|---|---|
       | (a) | owner | READY_FOR_SORA が1件 | 1回 | 0回 |
       | (b) | owner | BLOCKED が1件 | 2回 | 合計1回 |
       | (c) | owner | 全件 DONE＋APPROVED | 2回 | 合計1回 |
       | (d) | all | READY_FOR_SORA が1件 | 2回 | 合計1回 |
       | (e) | owner | (b) の後に別の block イベント（ts が違う）を足す | 1回 | 追加で1回 |
  4. README の「Slack 通知」節に、次の3項目を5行以内で追記する。`AGENT_CREW_SLACK_LEVEL`（owner/all）、状態の変化だけを送ること、送信記録の場所。配布先にも適用されることも書く。
- **してはいけないこと**: `pm.md` に書かれた Yuki の直接送信は変更しない。settings.json のフック登録は変更しない。
- **検証コマンド**: `uv run pytest -q tests/test_subagent_stop.py` → 全件 pass
- **依存**: T0-2 の後（同じファイル）。

**T0-4 Permissions の縮小と deny の新設**
- **complexity**: S / **risk_level**: high
- **目的**: ADR-019 D5 の「内側」を `.claude/settings.json` に反映する。
- **前提条件**:

    3. deny が allow より優先されるか
    4. MCP ツールの名前の書き方（`mcp__<server>__<tool>`）
  - 回答が、下の変更内容が前提とする意味と食い違った場合は、実装しない。食い違いを plan に記録して team-lead に戻す。

  - **allow に追加**:
    - `Bash(bash scripts/*)`、`Bash(bash .claude/hooks/*)`、`Bash(bash -n *)`、`Bash(python3 scripts/*)`、`Bash(uv run pytest *)`
    - 「プロジェクトルート配下の Edit」

  - **deny を新設**:
    - Bash: `Bash(git push --force*)`、`Bash(git push -f*)`、`Bash(git push * main)`、`Bash(git push * HEAD:main)`、`Bash(gh pr merge *)`
    - GitHub MCP: `mcp__github__merge_pull_request`、`mcp__github__enable_pr_auto_merge`、`mcp__github__create_or_update_file`、`mcp__github__push_files`、`mcp__github__delete_file`

- **ロールバック**: 誤った設定で作業が止まった場合は、この変更のコミットを `git revert` する。
- **してはいけないこと**: `hooks` キー、`templates/settings.json`、`scripts/` 配下の権限は変更しない。`curl` を deny しない（`pm.md` の Slack 送信が使っている）。
- **検証コマンド**:
  - `jq -e '.permissions.allow | (index("Bash(bash *)") == null and index("Bash(python3 *)") == null and index("Edit(**)") == null)' .claude/settings.json` → `true`
  - `jq -e '.permissions.deny | (index("Bash(gh pr merge *)") != null and index("mcp__github__merge_pull_request") != null and index("mcp__claude-code-remote__create_trigger") != null)' .claude/settings.json` → `true`
  - `jq empty .claude/settings.json` → エラーなし

**T1-1 run 契約スキル**
- **complexity**: M / **risk_level**: medium
- **目的**: unattended run が従う契約を、正本1箇所（ADR-012）に置く。
- **対象ファイル**: `.agents/skills/always-on/SKILL.md`（新規）
- **変更内容**: frontmatter は `name: always-on` と、`description: スケジュール実行など owner 不在で起動された run（unattended run）が従う契約。読み取りと要約だけを行い、判断が要るものは needs-owner として返す。` の2項目。本文には次の6節を、この順で置く。
  1. `## 禁止事項` — 次の7行を箇条書きで書く。
     - コードやファイルを変更しない
     - commit・push・PR 作成・マージをしない
     - timer を作らない
     - fable-class・critic.sh・model-mode の運用表示を適用しない
     - risk high の判断をしない
     - 1 run で書くコメントは digest 1件まで
     - 最後に `git status --porcelain` が空であることを確かめ、空でなければ needs-owner の手順で終える
  2. `## 入力` — 次の4種類と、ハーネス別の操作対応表（Claude Code クラウド＝GitHub MCP／ローカル＝`gh`・`git`・`rg`）を書く。
     - (a) `crew:needs-owner` ラベルの付いた open な Issue
     - (b) open な PR のうち、作成から3日以上経っていて、レビューの承認が無いもの（CI の状態も添える）
     - (c) main の直近 24 時間の commit（`git log --since=24.hours origin/main --oneline`）
     - (d) `rg -l "CRITICAL 未解消・オーナー判断待ち" docs/plans`

     `_queue.json` は入力にしない（sprint-27 以降は使われておらず、Phase 2 で扱う）。
  3. `## owner-inbox` — 出力先は、ラベル `crew:owner-inbox` の付いた open な Issue。
     - 0件のとき: 何も書かずに終え、最終応答の先頭に `needs-owner: owner-inbox がありません` と書く。
     - 2件以上のとき: 番号が最も小さいものを使う。
  4. `## digest` — 書き方は次のとおり。
     - 1行目にマーカー `<!-- agent-crew:digest YYYY-MM-DD -->` を置く（日付は JST）。
     - 同じ日付のマーカーを持つコメントがすでにあれば、何もしない。
     - 入力 (a)〜(d) がすべて0件なら、コメントしない。
     - 本文の末尾に、前日の digest に付いたリアクションの数を1行で書く（ADR-019 の検証方法 (a)）。
  5. `## needs-owner` — 判断が要る項目は、対象の Issue に `crew:needs-owner` ラベルを付ける。対象が PR や plan で Issue が無い場合は、digest の中に `[needs-owner]` という接頭辞を付けて書く。ラベルがすでに付いていれば、付け直さない。
  6. `## timer` — `timers.md` へのリンクを置き、「timer の追加と変更は owner が UI で行う」と書く。
- **してはいけないこと**: `.claude/skills/` にコピーを置かない。既存のスキルを変更しない。
- **検証コマンド**:
  - `rg -c '^## ' .agents/skills/always-on/SKILL.md` → `6`
  - `rg -q 'agent-crew:digest' .agents/skills/always-on/SKILL.md` → 終了コード 0

**T1-3 Actions による needs-owner と digest の配送**

- **目的**: ラベル付与と digest コメントをトリガーにして、Slack へ1件ずつ送る（ADR-019 D4）。

     `github.event_name == 'workflow_dispatch' || (github.event_name == 'issues' && github.event.label.name == 'crew:needs-owner') || (github.event_name == 'issue_comment' && contains(github.event.comment.body, 'agent-crew:digest') && contains(join(github.event.issue.labels.*.name, ','), 'crew:owner-inbox'))`
