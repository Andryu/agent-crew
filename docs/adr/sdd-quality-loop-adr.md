## Context

### 背景

チーム開発でKiro系のSDD（Spec-Driven Development）オーケストレーションを運用している。各機能開発は `requirements.md` / `design.md` / `tasks.md` の3ファイル（以下「spec 3点セット」）をコンテキストの本体として進む。オーケストレーション設定（agent定義・フェーズ別プロンプト・各種specテンプレート）は既に1つの共有GitHubリポジトリ（以下「真実源リポ」）にコミットされ、チームで共有されている。

### 解きたい課題

品質問題が発生したとき、その根因分析がメンバー個人の印象論で終わり、チームの共有知に転化されない。具体的には：

- 「コンテキストが足りなかった」「設計が荒かった」という感想は出るが、**何をどう直せばよいか**が特定のspecテンプレや agent定義の改善に結びつかない
- 複数人が同種の失敗を繰り返しても、パターンとして認識されない
- 個人が得た改善アイデアが真実源リポに還流せず、属人化する

### 制約・前提

1. Kiro 3フェーズ（requirements / design / tasks）が構造の骨格である
2. 真実源リポは既に存在する。新規Hub構築は不要
3. MVPの検知トリガーは**手動**（人が気づいたとき）。自動検知はMVPスコープ外
4. チームは複数人。個人名は出さず `author_hash` 等で匿名化する

## 検討した代替案

### 案A: 自動品質スコアリング（PR連動）

PRが作成されるたびに rubric で自動採点し、スコアが閾値を下回ったら postmortem を強制起動する方式。

**却下理由**: MVPとして複雑すぎる。rubric の設計自体に工数がかかり、誤検知・false positiveが多発するリスクがある。品質の何をスコア化するかの合意もチームで取れていない段階で、自動化を先行させるのは認知過負荷になる。「手動で知見が貯まってから自動化を考える」順序が適切。

### 案B: 個人ドキュメント（wiki / esa）への蓄積

各自が気づいたことを wiki や esa に書く。

**却下理由**: 構造化されないため検索・集約が困難。個人ページが乱立して重複率が高くなり、誰もメンテしなくなる傾向がある。また、wikiの改善提案は実際のspecテンプレやpromptの変更に自動的には結びつかない。「書いた」で満足してしまう。

### 案C: Slackスレッドでの振り返り共有

振り返りをSlackで議論する。

**却下理由**: 流れていく。検索できない。構造がないため「同種根因の頻度集約」が不可能。

### 案D（採用）: `/spec-postmortem` スキル + 真実源リポへのPR還流

**採用理由**:

- 根因を固定タクソノミーで分類することで、散文にならず構造化される
- 分析の着地点を「どのテンプレ/プロンプト/agent定義をどう直すか」の差分提案に限定することで、「気づいた」が「直した」に繋がる
- 真実源リポへのPR化を経路の終端にすることで、個人知が共有知になる
- MVPは手動起動で認知負荷を最小化。段階的に自動化を追加できる
- 構造化データ（後述）にすることで、後続の集約・ダッシュボード化（ロードマップC/D/E）への拡張パスが明確

## Decision

**Kiro 3フェーズ構造 + 既存共有リポを前提とし、`/spec-postmortem` スキルによる手動起動の品質改善還流ループを採用する。**

具体的には：

1. 品質問題に気づいたメンバーが `/spec-postmortem` を手動起動
2. 固定タクソノミーで根因を1つ以上特定し、構造化 postmortem記録を生成
3. 各根因に対応する「テンプレ/プロンプト/agent定義の具体diff提案」を生成
4. 記録を真実源リポの `knowledge/postmortems/` に配置し、改善提案を同リポへのPRとして提出
5. レビュー・承認を経てメインブランチにマージされることで、改善がチーム全体に伝播

## トレードオフの明示的論拠

### postmortem記録のフォーマット: 構造化JSON vs 散文Markdown

**推奨: フロントマター付きMarkdown（構造化データ + 散文の両立）**

| 観点 | 純粋JSON | 散文Markdown | フロントマター付きMd |
|------|---------|-------------|-------------------|
| 機械可読性（集約・集計） | 最高 | 不可 | 高（フロントマターのみ） |
| 人間可読性（PRレビュー） | 低 | 最高 | 最高 |
| why_chain の表現力 | 低（ネスト地獄） | 自然 | 自然（本文に記述） |
| diff提案の表現 | 不向き | 最適 | 最適 |
| 既存PRワークフローとの親和性 | 低 | 高 | 高 |
| ツール依存度 | 高 | 低 | 低 |

JSONは「集計スクリプトに食わせる」には便利だが、PRレビューで人間が読み・コメントする用途には向かない。散文Markdownは逆に集約が難しい。フロントマター付きMarkdownは両者の長所を取る：集約に必要な構造化フィールドはフロントマターに、why_chainや証跡の散文は本文に書く。ロードマップEのダッシュボードは `grey-matter` 等でフロントマターをパースすれば実現できる。

**これが本ADRの最重要トレードオフ判断である。**

### テンプレ改善のPR粒度: 1根因1PR vs バッチPR

**推奨: 1根因1PR（ただし同一ファイルへの軽微な修正は1PRにまとめてよい）**

根因が1つでも分析に時間がかかる。複数の根因をまとめると、レビュアーの認知負荷が高くなりレビューが遅延する。「承認されなかったときに何が問題か」の切り分けも困難になる。1根因1PRは粒度が細かいが、マージされやすい・差し戻し理由が明確・CHANGELOG追記コストが低い、という実務上の利点が大きい。

## Consequences

**良くなること**

- 品質問題がspecテンプレや agent定義の具体的な変更に着地する
- 同種根因の頻度が可視化され、優先度の高い改善から着手できる
- 匿名化されたpostmortem記録がチームの学習資産になる
- 段階的な自動化（ロードマップC/D/E）への拡張経路が明確

**難しくなること / 課題**

- `/spec-postmortem` スキルの初期品質がチームへの定着率を左右する。タクソノミーの説明文が曖昧だと分類がブレる
- postmortem記録のレビュー・PRマージの運用負荷が発生する。最初は小さいが積み上がると重くなるため、自動集約（ロードマップE）への移行計画が必要
- 「分析した」「PRを出した」で終わり、実際にテンプレが変わらないという問題が起きうる。承認フローのSLAを定めることで対処する（詳細は設計書参照）
