# ADR-014: 本社機能と部門機能の分離設計

- **Status**: Accepted
- **Date**: 2026-08-01
- **Issue**: なし（Sprint-24, オーナー直接指示）

---

## 背景

組織OS導入（Sprint-24）に伴い、`docs/org/departments.md` で部門ポートフォリオ（プロダクト=アクティブ / 投資=アイドル / 動画・ゲーム=未開設）を定義した。
現状、参謀長（Rin）・レトロ（みゆきち）・セキュリティ監査（Kai）・ドキュメントレビュー（Hana）といった**部門非依存であるべき機能**と、エンジニア・QA・UXデザイナーといった**部門固有の機能**が、同一リポジトリ（`agent-crew` / stonefish）内に混在している。

投資部門（`alpha-predict-jp`）が横展開トリガー（`docs/org/departments.md` 第3条）を満たしてアクティブ化した場合、あるいは動画・ゲーム部門が新規開設された場合、本社機能を都度手作業で複製すると、`agent-crew` 側での改善（例: retro.md のルーブリック改善）が他部門に伝播しない**ドリフト問題**が発生する。これは ADR-012（グローバルスキル配布）で既に一度解決した問題と同型である。

本ADRは、この本社機能/部門機能の境界を明確化し、複数部門展開時の配布方式を決定する。

---

## 決定事項

### 1. 機能の分類

**本社機能（部門非依存 — 全部門で同一の判断基準・品質基準を保つべきもの）**

| 機能 | ファイル |
|------|----------|
| PMプロトコル・見積もりロジックの共通部分 | `pm-protocol.md` / `pm-estimation.md`（委譲ルール・見積もりロジックそのもの。部門固有スタック判断は部門機能側） |
| 参謀長（Rin） | `.claude/agents/coo.md` |
| レトロスペクティブ（みゆきち） | `.claude/agents/retro.md` |
| セキュリティ監査（Kai） | `.claude/agents/security.md` |
| ドキュメントレビュー（Hana） | `.claude/agents/doc-reviewer.md` |
| 教訓基盤 | `~/.claude/_lessons.json` → vault連携の仕組み（ADR-013のフック機構） |
| 組織文書 | `docs/org/`（`constitution.md` / `departments.md` / `weekly-council.md` / `templates/project-charter.md`） |

> **ADR-012 との関係の明確化**: ADR-012 は「エージェント定義はコピーモデル」と定めており、`pm-protocol.md` / `pm-estimation.md` は文言上その対象に含まれる。本 ADR はこれを**上書き**し、両ファイルの「委譲ルール・見積もりロジックの共通部分」を本社機能（symlink 配布）へ移す。部門固有のスタック判断（例: engineer-go 向けの委譲条件）は Phase 2 のテンプレート物理分離時に部門側ファイルへ切り出す。それまでの過渡期は現状のコピーモデルのまま運用する。

**部門機能（部門固有 — プロダクト部門の場合の現状実装）**

| 機能 | ファイル |
|------|----------|
| エンジニア（Riku, スタック別） | `.claude/agents/engineer-go.md` / `engineer-next.md` / `engineer-vue.md` |
| QA（Sora） | `.claude/agents/qa.md` |
| UXデザイナー（Mina） | `.claude/agents/ux-designer.md` |
| データアナリスト（Ren） | `.claude/agents/data-analyst.md` |
| DevOps（Tomo） | `.claude/agents/devops.md` |
| アーキテクト（Alex） | `.claude/agents/architect.md` |
| 部門固有のタスクキュー・スプリント文書 | `.claude/_queue.json` / `docs/sprints/` |

### 2. 実装方針: シンボリックリンク配布モデルの拡張（ADR-012踏襲）

ADR-012 は「スキル定義（`~/.claude/skills/`）= symlink、エージェント定義（`~/.claude/agents/`）= コピー」という非対称モデルを採用した。理由は「エージェント定義は部門ごとにカスタマイズされ得るため、コピーによる独立性を保つ」というものだった。

本ADRは、この非対称モデルに**「本社/部門」の軸を追加**して整合させる。ADR-012の結論を覆すのではなく、対象を絞り込む。

- **本社機能のエージェント定義（Rin / みゆきち / Kai / Hana）は symlink で配布する。** これらは「全部門で同一の判断基準を保つ」ことこそが存在意義であり、部門ごとのカスタマイズを許すと本来の役割（横断的な品質保証・監査）が崩れる。
- **部門機能のエージェント定義（Riku系 / Sora / Mina / Ren / Tomo / Alex）は引き続きコピーモデルを維持する。** ADR-012が指摘した「スタック別カスタマイズがあり得る」性質は部門機能側にのみ残る。
- 組織文書（`docs/org/`）も symlink で配布する。憲章・部門ポートフォリオ・週次経営会議プロトコルは定義上、全部門で単一の正本を持つべきもの。
- 教訓基盤は ADR-013 のフック機構（グローバル `~/.claude/settings.json` への登録）をそのまま踏襲し、追加変更なし。

配布元（マスター）は `agent-crew`（stonefish）リポジトリのまま維持する。部門リポジトリ（`alpha-predict-jp` 等）は、本社機能ファイルを symlink として受け取る側になる。

### 3. 部門テンプレート（新部門開設時に複製する最小セット）

`docs/org/departments.md` 第4条「部門開設の手順」で参照する、新部門開設時に複製するディレクトリ構成を以下に定義する。

```
<部門テンプレート>/
├── .claude/
│   ├── agents/
│   │   ├── coo.md          -> symlink（本社）
│   │   ├── retro.md        -> symlink（本社）
│   │   ├── security.md     -> symlink（本社）
│   │   ├── doc-reviewer.md -> symlink（本社）
│   │   ├── pm-protocol.md  -> symlink（本社、共通部分のみ）
│   │   ├── pm-estimation.md-> symlink（本社、共通部分のみ）
│   │   ├── pm.md            （コピー。部門ネイティブに一部カスタマイズ可）
│   │   └── <部門固有エージェント>.md（コピー、新規作成。例: alpha-predict-jp なら analyst 系）
│   ├── skills/               （symlink、ADR-012の既存モデルを継続。軸足スキルは部門ネイティブ新規作成）
│   └── _queue.json           （空、部門ネイティブ）
├── docs/
│   ├── org/     -> symlink（本社。憲章・部門ポートフォリオは全部門共通）
│   ├── adr/                  （部門ネイティブ。部門固有の設計判断を記録）
│   └── sprints/               （部門ネイティブ）
└── （グローバル）~/.claude/_lessons.json は ADR-013 の既存機構をそのまま利用、部門テンプレートには含めない
```

## 却下した代替案

| 代替案 | 却下理由 |
|--------|----------|
| モノレポ化（全部門を1リポジトリに統合） | 組織憲章第3条「最小権限」（部門エージェントは自部門リポジトリの権限のみ）が実現できなくなる。`permissions.allow` をリポジトリ単位で分離できず、Kai の定常スキャンによる逸脱検知の前提も崩れる。`alpha-predict-jp` は既に独立リポジトリとして稼働中で、統合の移行コストが投資対効果に見合わない。 |
| 完全コピー配布（本社機能ファイルを都度 `cp`） | ADR-012 が既に否定した方式と同型のドリフト問題を再導入する。本社機能は「全部門で同一基準を保つ」ことが存在意義であり、コピーはその目的とそもそも矛盾する。 |
| Git サブモジュール | ADR-012 で既に検討・却下済み。個人開発の運用規模に対してサブモジュール管理の複雑さが見合わない。 |
| パッケージ化（npm/pip 的な配布） | 公開パッケージ化は現時点で不要という判断（ADR-012と同一の結論）。配布対象がクローズドな個人開発チーム内に限られるため、レジストリ運用のコストに見合うリターンがない。 |

## 段階移行計画

- **Phase 1（本スプリント, Sprint-24）**: 文書と境界の確定。`docs/org/departments.md` と本ADRで本社機能/部門機能の分類を確定する。symlink は物理的にはまだ張らない（投資部門は現時点でアイドルであり、複製の必要が生じていないため）。
- **Phase 2**: テンプレートディレクトリの物理分離。上記「部門テンプレート」構成を実体として `agent-crew` 内（または別ディレクトリ）に作成し、`install.sh` に本社機能配布用のセクション（ADR-012 の `symlink_skill` 関数に相当する、エージェント定義・組織文書向けの新設関数）を追加する。この完了が横展開トリガー条件①（`docs/org/departments.md` 第3条）の充足条件となる。
- **Phase 3**: 2部門目（投資部門）への複製デプロイ。横展開トリガー3条件がすべて充足し、オーナーの Go/No-Go を経た後、`alpha-predict-jp` に本社機能の symlink を張り、Rin の部門状態統合・週次トークン会計の対象に投資部門を追加する。

Phase 2・Phase 3 の実装（`install.sh` の変更、実際の symlink 配置）は本スプリントのスコープ外であり、別スプリントで Riku に委譲する。

## トレードオフ

**良い点**

- 本社機能側の改善（例: retro.md のルーブリック改善、Kai の監査ルール追加）が `git pull` だけで全部門に伝播する（ADR-012と同じ恩恵）。
- 新部門開設のたびに本社ロジックを再実装するコストがゼロになる。
- Rin / みゆきち / Kai / Hana の判断基準が全部門で統一され、部門間のパフォーマンス比較が意味を持つようになる。

**受け入れるトレードオフ**

- 部門リポジトリは `agent-crew` が同一マシンの既定パスに clone されていることが前提となる（ADR-012 と同じ dangling symlink 制約を継承。規約: `$HOME/Workspace/agent-crew` または `$HOME/workspace/agent-crew`）。
- 本社機能ファイルは部門リポジトリ側で直接編集できない。編集は必ず `agent-crew` 側で行う運用規約が必要（部門側で誤って symlink 先を書き換えてしまう事故を防ぐため）。この規約遵守の監査は Kai の定常スキャン対象に含めることを次スプリント以降の推奨事項とする。
- Phase 2（物理分離）が完了するまでは、本ADRは「境界の合意」にとどまり、実際の配布は手作業のまま（Phase 1 の性質上の制約）。

- 投資部門がアクティブ化された時点（Phase 3 実施のトリガー）。
- 部門数が3以上になり、symlink 管理（本社機能ファイル数 × 部門数の組み合わせ）が煩雑化した場合（パッケージ化・配布ツール自作の再検討）。
- Claude Code にネイティブの本社/部門分離機構（組織単位のエージェント配布）が実装された場合、この ADR を Superseded に更新して移行する。
