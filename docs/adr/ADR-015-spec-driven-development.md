# ADR-015: 軽量機能仕様書（1機能1ファイル）方式の採用

## Status
Accepted

## Context

### 背景

Sprint-25までのレトロで、「実装が仕様から逸脱する」「仕様の所在が実装者の記憶にしか残らない」という問題が複数回指摘されていた（`agent-crew-sprint-25-tooling-002` 等、根はテスト・検証手順の非固定化だが根底には「正の仕様がどこにあるか」の曖昧さがある）。この問題への対処として、Kiro系オーケストレーションで一般的な SDD（Spec-Driven Development）の導入が検討された。

### 既存の未採用ドラフトとの関係（重要）

検討の過程で `docs/adr/sdd-quality-loop-adr.md`（および `docs/spec/sdd-quality-loop-design.md` / `-proposal.md`）という3ファイルがリポジトリのワーキングツリーに存在することが判明した。これらは git 未追跡（`git status` で `??` 表示、コミット履歴なし）のドラフトであり、内容は以下の前提に立っている。

- 複数人チームが Kiro 3フェーズ（`requirements.md` / `design.md` / `tasks.md` の「spec 3点セット」）でSDDを運用している
- オーケストレーション設定（agent定義・フェーズ別プロンプト）を共有する「真実源リポ」が既に存在し、複数人の改善をそこへPRで還流させる
- postmortem記録を `author_hash`（`sha256(github_id)` の先頭8文字）で疑似匿名化する必要がある（＝複数人が関与する前提）

これは `docs/spec/sdd-quality-loop-design.md` 冒頭に「**対象: チームSDDオーケストレーション（Kiro系）向け。agent-crew 個人開発リポジトリとは別物**」と明記されている通り、**agent-crew（本リポジトリ）とは異なる利用文脈を前提とした提案**である。agent-crewは個人開発であり、匿名化・PRレビューSLA・複数人の頻度集約といった仕組みは過剰であり、Kiro式3点セットも個人開発1名運用では管理コストが便益を上回る。

**オーナー判断（2026-08-01〜02）**: Kiro式3点セット（requirements/design/tasks）の必須化は行わない方針とする。個人開発の規模に見合った軽量な運用に置き換える。

### 解きたい課題（agent-crewに合わせて再設定）

1. 機能の「現在の正の仕様」がどこにあるか曖昧で、実装がその場の判断に流れやすい
2. 実装完了時に仕様書を更新する強制力がない（書いたきりで陳腐化する）
3. 新機能が仕様書なしで実装・QAを通過してしまう

## 決定

**「1機能1ファイル」の軽量機能仕様書（living document）方式を採用する。**

### 1. ファイル配置とテンプレート

- 配置: `docs/spec/features/<機能名>.md`（1機能につき1ファイル）
- テンプレート: `docs/spec/templates/feature-spec.md`
- 構成は4セクションのみ: **概要 / ユースケース / 仕様（現在の正） / 変更履歴**
  - 「仕様（現在の正）」は living document として常に最新の状態を保つ。過去の議論・却下案・古い設計判断は本文に残さず「変更履歴」に集約する
  - Kiro式の requirements / design / tasks への分割は行わない（1ファイルで完結させる）

### 2. 更新の強制（3手段）

ドキュメントに書くだけでは実行が保証されない（`docs/org/constitution.md` 前文の教訓）ため、以下3つの強制手段を併記する。

1. **Riku（`engineer-go.md` / `engineer-next.md` / `engineer-vue.md`）の「実装完了の定義（DoD）」に追加**:
   `変更した機能の feature-spec（docs/spec/features/<機能名>.md）を更新した（存在しない場合は新規作成した）`
2. **Sora（`qa.md`）の「完了の定義（DoD）」に追加**:
   `feature-spec と実装の差分がないか確認した`
3. **新規機能は feature-spec なしで QA を通過できない**:
   `qa.md` の DoD に `対象機能の feature-spec が存在しない場合は CHANGES_REQUESTED とする（新規機能限定。既存機能の遡及作成義務はバックログ対応 — 下記「移行方針」参照）` を明記する

具体的な追記文言（before/after形式）は本ADR末尾の「Appendix: Riku適用指示」を参照（`sdd-templates-impl` タスクでRikuが適用する）。

### 3. 移行方針（既存機能の遡及作成）

現在 `docs/spec/` にはKiro系ドラフトの他、機能仕様ではない設計メモ（`*-design.md`）が多数存在するが、これらの feature-spec 形式への遡及移行は本スプリントのスコープ外とし、バックログ化する（**主要既存機能の feature-spec 初期作成は Issue として起票することを推奨** — 起票はオーナー承認後）。**新規に着手する機能・変更を加える機能から段階的に feature-spec を増やす**方針（strangler運用）。

## 検討した代替案

### 案A: Kiro式3点セット（requirements/design/tasks）を必須化

**却下理由**: 個人開発1名運用では、フェーズ間の受け渡しオーバーヘッド（3ファイルの整合性維持）が便益を上回る。`sdd-quality-loop-adr.md` ドラフトが前提とする「複数人チームでの分業・レビューSLA」が存在しないため、3点セットの本来の価値（役割分担の明確化）が発生しない。

### 案B: 仕様書なし運用を継続（ドキュメント化しない）

**却下理由**: 「解きたい課題」の1〜3がそのまま残る。過去の教訓（`agent-crew-failure-patterns`）が示す通り、口頭・記憶ベースの仕様は必ず陳腐化・散逸する。

### 案C（採用）: 1機能1ファイルのliving document + チェックリスト強制

**採用理由**: 個人開発の規模に見合った最小コストで「正の仕様の所在」を固定でき、かつ強制手段（DoD追加）により「書いただけで終わる」を防げる。1ファイルで完結するため、Kiro3点セットのような複数ファイル間の整合性維持コストが発生しない。

## Consequences

**良くなること**

- 「この機能の仕様はどこか」を常に `docs/spec/features/<機能名>.md` 一箇所に問い合わせられる
- 実装完了・QA通過のたびに仕様書の陳腐化を検知する仕組みが働く
- Kiro3点セットの管理コストなしで、SDDの本質的な効能（実装前に仕様を固定する）の一部を得られる

**難しくなること / 課題**

- 既存機能の遡及作成が進まないと「仕様書がある機能とない機能」が併存し続ける（移行方針で許容済み、バックログ管理が必要）
- feature-specの「現在の正」を保つ運用がRiku・Sora双方の自己規律に依存する部分が残る（DoDチェックリストが唯一の強制力であり、監査スキャンでの機械チェックは本ADRのスコープ外。将来 `scripts/audit-scan.sh` 系の拡張候補とする）
- 1ファイル完結方式は、機能が大規模化した場合に肥大化するリスクがある（発生したら分割規約を別途検討する）

## Appendix: Riku適用指示（`sdd-templates-impl` 向け）

以下は `#2 sdd-templates-impl` でRikuが適用する具体的な追記内容。各ファイルへの追加は「既存箇所への1行〜数行の追記」であり、既存記述の削除・大幅書き換えは不要。

### 1. `docs/spec/templates/feature-spec.md`

新規作成済み（本タスクの成果物、`sdd-adr-design` で作成済みのためRikuは作成不要。存在確認のみでよい）。

### 2. `docs/spec/features/.gitkeep`

`docs/spec/features/` ディレクトリを新規作成し、空の `.gitkeep` を置く（git は空ディレクトリを追跡できないため）。

### 3. `.claude/agents/engineer-go.md` / `engineer-next.md` / `engineer-vue.md`

いずれのファイルにも「### 実装完了の定義（DoD）」セクションが存在する（各ファイルで見出し文言・位置は共通）。そのチェックリスト末尾に以下を1行追加する。

```diff
 ### 実装完了の定義（DoD）

 - [ ] 機能が仕様通りに動作する
 - [ ] テストが通る（`go test ./...` or `npm run test`）
 - [ ] ビルドが通る（`go build ./...` or `npm run build`）
 - [ ] 新規追加したパブリック関数/コンポーネントにコメントがある
 - [ ] TODO/FIXME を残した場合は理由をコメントに書く
+- [ ] 変更した機能の feature-spec（`docs/spec/features/<機能名>.md`）を更新した（存在しない場合は新規作成した。テンプレート: `docs/spec/templates/feature-spec.md`）
```

### 4. `.claude/agents/qa.md`

「## 完了の定義（DoD）」セクションの末尾に以下を追加する。

```diff
 ## 完了の定義（DoD）

 - [ ] 全チェックリスト項目を確認した
 - [ ] CRITICAL・MAJORの指摘がゼロになっている（または承認済み）
 - [ ] テスト・ビルドが通っている
 - [ ] 実行したテストコマンドと出力結果を完了報告の「テスト結果」セクションに記録した
 - [ ] レビュー結果をファイルに記録した
+- [ ] feature-spec（`docs/spec/features/<機能名>.md`）と実装の差分がないか確認した
+- [ ] 新規機能の場合、feature-spec が存在することを確認した（存在しない場合は CHANGES_REQUESTED とする。既存機能の遡及作成義務はなし — ADR-015「移行方針」参照）
```

### 5. `.claude/agents/pm.md`

「### ステップ1: 前スプリントの実装完了状態の突合」の末尾（次の見出し「### ステップ2」の直前）に以下を追加する。

```diff
 ### ステップ1: 前スプリントの実装完了状態の突合
 （...既存の記述...）
+
+**feature-spec 参照の明記（ADR-015）**: 計画対象タスクが既存機能の変更を含む場合、対応する `docs/spec/features/<機能名>.md` が存在するかを確認し、存在すればタスクの `notes` に参照パスを記載する。存在しない場合は新規作成が必要である旨を `notes` に記載する（新規作成の強制はRiku DoD側で担保するため、pm.md側は「気づかせる」役割に留める）。
```
