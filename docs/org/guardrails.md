# STONEFISH ガードレール v1.0

> 組織憲章 `docs/org/constitution.md` 第5条に基づく詳細規程。
> **目的は「AIの自律行動を増やす」ことであり、「AIを疑う」ことではない。**
> 境界を先に明文化し機械的に検知できる形にすることで、境界の内側では確認を挟まず進めてよい状態を作る
> （オーナー指示 2026-08-02）。各条には憲章と同様に Enforcement を併記する。

---

## 第1条 エスカレーション基準

### 経営事項（オーナー確認が必須）

以下の**4種類のみ**を経営事項とする。他の全業務は自律実行・自律マージの対象になり得る（第5条参照）。

| # | 種別 | 具体例 |
|---|------|--------|
| ① | 料金・コスト | 新規有料API/SaaS契約、月額発生する支出判断、無料枠を恒常的に超える利用計画 |
| ② | 根本転換 | プロジェクトのピボット・撤退（憲章第4条の撤退基準に基づく判定） |
| ③ | 戦略・戦術変更 | OKR・ロードマップの変更、部門の開設/停止（`departments.md`）、`weekly-council.md` ルール6に定める戦略・戦術領域 |
| ④ | MVP・OKR変更 | `project-charter.md` のMVP定義・成功指標・撤退基準の変更、Go/No-Goゲート（憲章第2条） |

**それ以外は自律実行・自律マージ可。実行方法（How）に属する判断（Issue起票・ツール改善・スプリントスコープの機微）は team-lead に委任する**（`weekly-council.md` ルール6と同一原則）。

**本当に迷ったら聞く。** 4分類への該当が曖昧な場合は、安全側（=オーナーに確認する側）に倒す。誤って経営事項扱いにする（過剰確認）はコストが低く、誤って自律実行する（過小確認）はコストが高い。

**Enforcement**:
- 経営事項に該当する提案は意思決定キュー（`docs/org/council/YYYY-MM-DD-queue.md`）にのみ載せてよく、コード変更・PRマージでは確定させない。
- QA（Sora）はレビュー時に「経営事項に該当する変更がPRに紛れていないか」をチェックリストに追加する（`.claude/agents/qa.md`）。
- 憲章第2条 Enforcement（承認の代行・推定は禁止）をそのまま適用する。

## 第2条 API・外部呼び出しの信頼性ガードレール

外部API・外部サービス（Slack Webhook、GitHub API、決済・データ取得APIなど）を呼び出すコード・エージェント動作に適用する。

| 項目 | 規約 |
|------|------|
| リトライ上限 | 3回 |
| バックオフ | 指数バックオフ（例: 1s → 2s → 4s、可能なら jitter を加える） |
| 連続失敗時 | サーキットブレーカーを発動し、**タスクをBLOCKED化して人間へ**（`scripts/queue.sh block <slug>` / `queue.py block`） |
| BLOCKED時の記録 | notesに失敗理由・呼び出し先・試行回数を記録する（Kai監査・週次会議の判断材料になる） |

> 本条は「1タスク内での外部API呼び出し失敗」に対する規約。`scripts/queue.py` の complexity別 retry 上限
> （S=2 / M=3 / L=5、既定3、`.claude/agents/engineer-*.md` 「リトライルール」節）は「QA差し戻し後の実装やり直し」に
> 対する既存の別機構であり、本条はこれを置き換えない。両者は「3回失敗したらBLOCKEDで人間に渡す」という
> 思想を共有する。

**Enforcement**: `scripts/audit-scan.sh` の 3.4「サーキットブレーカー健全性チェック」が、
retry_count が complexity別上限に達しているにもかかわらず `status` が `BLOCKED` になっていないタスクを検知し FAIL とする
（サーキットブレーカーが実際に発火したかどうかの事後検証。発火前提の予防は各エージェントの実装規約に委ねる）。

## 第3条 コストガードレール（スプリント予算）

`docs/org/council/token-report-*.md`（Rin が週次生成する部門別トークン集計）の「前期間比」列を基準にする。

| 閾値 | 判定 | 対応 |
|------|------|------|
| 前週比 +50%未満 | 正常 | 対応不要 |
| 前週比 +50%以上 | WARNING | 週次経営会議のトークン会計（`weekly-council.md`）で要因をRinが報告する |
| 前週比 +100%以上 | FAIL | 次スプリント計画の着手前に原因分析を完了し、計画書「確認事項」に記載する。原因不明のまま継続しない |

新規プロジェクト立ち上げ直後など、前週データが存在せず比較不能な場合（token-report上「新規」表記）は本条の対象外とする（`project-charter.md` の月額目安チェックで代替）。

**Enforcement**: `scripts/audit-scan.sh` の 3.5「トークン予算超過チェック」が最新の週次トークンレポートを解析し、
閾値超過をWARNING/FAILとして報告する。`.claude/agents/pm.md` ステップ2.6（スプリント開始前の定常監査スキャン）が
本チェックを含めて自動的に評価するため、追加の呼び出し手順は不要。

## 第4条 セキュリティガードレール

### 最小権限

憲章第3条を参照する。本条は上乗せしない（二重管理を避ける）。

### シークレット

- `.env` や認証情報の値をコード・コミット・Issue・PR本文・意思決定キューに含めない。
- Stopフック `scripts/privacy-check.sh` が既存の防壁として機能する（`.claude/settings.json` Stop hooks）。

### 禁止リスト（`permissions.allow` への追加を禁止するコマンドパターン）

憲章第1条 L0（人間専権: 公開・リリース、支払い・契約、対外コミュニケーション、売買執行）に該当する操作を機械的に列挙する。

| カテゴリ | 禁止パターン例 |
|---------|----------------|
| 支払い・課金 | 決済API（stripe/paypal等）への直接書き込み系呼び出し |
| 公開・リリース | `npm publish`, `gh release create`, パッケージレジストリへのpush |
| 対外コミュニケーション | SNS投稿APIの直接呼び出し（Slack以外への投稿。Slack通知は既存の `SLACK_WEBHOOK_URL` 経由の定型通知のみ許可 — `.claude/agents/pm.md` responsibility 4） |
| 本番インフラ変更 | `terraform apply`, 本番環境への `kubectl apply` 等 |
| 破壊的Git操作 | `git push --force` / `--force-with-lease`（保護ブランチ = main/master 向け） |

**Enforcement**: `scripts/audit-scan.sh` の 3.6「禁止コマンドチェック」が `.claude/settings.json` の
`permissions.allow` を上記パターンと突合し、一致した場合 FAIL とする。憲章第3条 Enforcement と同じ実行タイミング
（週次経営会議準備時・スプリント開始時）に統合されるため、実行手順の追加は不要。

### 破壊的・状態変更操作の実行根拠（推測ベースの自動実行禁止）

> 実例（2026-08-02）: `scripts/queue.py` の Issue自動クローズ機構が、タスクnotes内の自由記述テキスト
> 「PR #151」を正規表現 `#(\d+)` で無条件にIssue番号と誤認し、`gh issue close 151` を実行して
> オーナーの戦略レビュー待ちPRを誤クローズした（数分でreopenし実害なし。根本対応は Issue #152 / #144）。
> team-lead からの実インシデント報告を受け本節を追加。

close / merge / delete / publish 等、外部の状態を変更し取り消しにくい操作を自動実行する場合は以下を必須とする。

- **構造化フィールドのみを実行根拠にする**: 自由記述テキストへの正規表現マッチ・数値抽出（例: `#(\d+)`）を
  実行対象の識別根拠にしてはならない。`closes_issue: 144` のような明示的な構造化フィールドのみを根拠とする。
- **対象種別の確認**: 実行前に対象が Issue か PR か等の種別を確認する（番号だけでは種別を判別できない）。
- **既定はドライラン**: 破壊的操作を行うスクリプト・自動化は既定で「実行内容の表示のみ」（ドライラン）とし、
  実行モードは明示的なフラグ等での切り替えを要求する。

**Enforcement**: 該当実装（`scripts/queue.py` のIssue自動クローズ機構）の改修は Issue #152 / #144 で追跡する。
新規に破壊的・状態変更系の自動化を実装する場合、QA（Sora）は上記3項目をレビューチェックリストとして確認する
（`.claude/agents/qa.md`）。

## 第5条 自律マージ条件

Draft PR を **オーナーの個別承認を待たずに Ready化・マージしてよい**のは、以下を**すべて**満たす場合に限る。

| # | 条件 |
|---|------|
| ① | QA（Sora）が `APPROVED` 判定を出している（`CHANGES_REQUESTED` が残っていない） |
| ② | 第1条の経営事項（①〜④）に該当する変更が含まれていない |
| ③ | 第2条のサーキットブレーカーが発火した状態のタスクを含まない（BLOCKEDタスクを内包するPRをマージしない） |
| ④ | 第3条のコストガードレールが FAIL 状態でない（直近の `audit-scan.sh` 実行結果が FAIL を含まない） |
| ⑤ | 第4条の禁止リストに抵触する変更（`permissions.allow` への禁止パターン追加等）を含まない |

いずれか1つでも満たさない場合は、PRをDraftのまま維持し、オーナーの明示的な発言を判断根拠とする
（憲章第2条 Enforcement — 承認の代行・推定は禁止）。

> 本条は憲章第1条「PRは常にDraftで作成する」という Enforcement を変更しない。**PRの新規作成は常にDraft**が前提であり、
> 本条が定めるのは「作成済みのDraft PRを、いつ・どの条件で Ready化/マージへ進めてよいか」という後続判断である。

**Enforcement**: QA（Sora）は完了報告フォーマットに「マージ可否（ガードレール第5条準拠）」を明記する
（`.claude/agents/qa.md` 完了報告フォーマット）。①〜⑤すべて満たすと判定した場合のみ「自律マージ可」と記載し、
1つでも満たさない場合は「オーナー確認要（理由: ...）」と明記した上でDraftのまま提出する。
