# DELEGATE — 実装委譲プロトコル（Sonnet サブエージェント / Codex）

## 原則

実装者（Sonnet サブエージェント）の役割は、「よく仕様が切られたタスクの実行」に徹することである。設計判断を実装者に委ねない。

海外コミュニティで確立している知見として、「Opus の思考で形成された明確な指示を与えれば、Sonnet の実装品質は十分に保たれる」というパターンがある。計画の質さえ高ければ、実装モデルのグレードを落としても成果物の品質は落ちない。逆に言えば、計画が曖昧なままでは、どれほど高性能な実装モデルを使っても品質は安定しない。

## 起動方法（Sonnet サブエージェント）

`Agent` ツールを使い、`subagent_type: "general-purpose"`（またはプロジェクトに engineer 系のエージェントが定義されていればそれ）を指定し、`model: "sonnet"` を明示する。

- **1タスク=1エージェント**。タスクごとに新規に `Agent` を起動し、フレッシュコンテキストで実行させる。前のタスクの文脈を引き継がせない。
- 独立したタスク（planning.md で「並列委譲可能」と明記したもの）は、同一のツール呼び出しブロック内で複数の `Agent` 呼び出しとして並列起動する。

## 委譲プロンプトの必須構造

委譲プロンプトには、以下をすべて含める。

1. **planning.md のタスクテンプレート全項目** — 目的、対象ファイル（絶対パス）、変更内容、してはいけないこと、検証コマンドと期待される出力。
2. **報告フォーマットの指定** — 実装者には、作業完了時に以下の形式で報告するよう明示する。
   - 変更したファイル一覧
   - 実行した検証コマンドと、その生出力（要約ではなく実際の出力そのもの）
   - 仕様から逸脱した点があれば、その内容と理由

実装者に設計判断を委ねる文言——「適切に」「いい感じに」「よしなに」など——は、委譲プロンプトに一切含めてはならない。こうした文言は、計画フェーズでの検討不足を実装者に押し付ける行為であり、省略の温床になる。

## 実装者への必須指示3点

委譲プロンプトには、以下の3点を明示的な指示として必ず含める。

1. **検証コマンドを必ず実行し、生出力を報告に含めること。** 「テストは通るはず」といった推測での報告を許容しない。
2. **仕様に曖昧さを見つけたら、勝手に解釈せずその旨を報告して作業を停止すること。** 実装者が独自に解釈して進めた結果は、たとえ動いていても仕様準拠とは言えない。
3. **スコープ外のファイルに触れないこと。** タスクで明示されていないファイルの変更・削除・リネームは行わない。

## 並列化の指針

- 依存のないタスクは並列委譲する。トークン消費は増えるが、ウォールクロック時間を短縮できる。
- 同一ファイルを触るタスクは、たとえ内容的に独立していても直列で委譲する。並列書き込みによる競合・上書きを避けるため。
- 依存のあるタスク（前段の成果物を前提とするタスク）は、前段の完了と VERIFY を待ってから次を委譲する。

## Codex（herdr ペイン）への委譲 — Pro 運用の既定（ADR-018）

team-lead が Opus 以上でない場合、実装はプラン上限の外にある Codex（別系統・別プロセス）に出す。Codex には agents/skills の規約が届かないため、上記「委譲プロンプトの必須構造」と「必須指示3点」を**プロンプト本文に全文書き出す**。別系統は明示の禁止を読み飛ばす前例（失敗パターン §6、Sprint-13）があるので、完了後の機械的な突合を省かない。

手順:

1. **委譲テンプレを plan から生成する**: `docs/plans/<slug>.md` のマイクロタスク1件（目的・対象ファイル絶対パス・変更内容・してはいけないこと・検証コマンド）＋必須指示3点＋報告フォーマットを1つのテキストにまとめ、`docs/plans/<slug>-task-<n>.md` に保存する（成果物＝後から監査できる）。
2. **起動**: herdr の Codex ペインで、そのファイルの内容をプロンプトとして投入する（`herdr` スキルが使える環境ではペイン操作を委任してよい）。1タスク＝1セッション。前タスクの文脈は引き継がせない。
3. **生出力の回収**: Codex には「検証コマンドの生出力と変更ファイル一覧を `docs/plans/<slug>-task-<n>-report.md` に書き出す」ことを報告フォーマットとして指示する。team-lead はチャット出力ではなくこのファイルを読む。
4. **スコープ外変更の検出（必須）**: 完了後に `git diff --name-only` の出力と plan の対象ファイル一覧を突合し、一致しなければ差分を破棄して差し戻す。この生出力を VERIFY 記録に貼る。
5. **フォールバック**: herdr/Codex が使えない環境では fresh Sonnet サブエージェント（上記「起動方法」）に同じテンプレで委譲し、plan に「Codex 不使用」と1行記す。

Codex の実装は仕様準拠レビュー（verification.md 第1段階）を必ず通す。別系統の出力を team-lead が直接採用しない。
