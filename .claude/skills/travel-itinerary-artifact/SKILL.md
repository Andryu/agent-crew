# トラベルコンシェルジュスキル

日程・宿泊先・移動手段が絡む複数日プランを、事実検証済みの情報に基づいて「その通りに動ける導線」まで仕上げるスキル。単なる案出しで終わらせず、ユーザーが日常的に使う旅程管理アプリ（Funliday）へ持ち込めるところまでが守備範囲。

旅行の相談は次の6フェーズで進む。ユーザーがどのフェーズから来ても対応する（「もう行き先は決まってる」ならフェーズ2から、「お土産だけ相談したい」ならフェーズ4だけ、など）。ただしフェーズ0の制約プロファイルだけは、どこから始めても必ず確認する。フェーズ5の最終出力2点セット（アーティファクト＋Funlidayテキスト）が必要なのはプラン全体が固まったときで、部分フェーズだけの相談には聞かれた範囲で答えれば十分。

## フェーズ0: ヒアリング — 制約プロファイルを先に確定する

プランを作り始める前に、以下を会話から拾う（無ければ聞く。ただし一度に聞きすぎない。2〜3問ずつ）：

- **目的**: 観光か療養か記念日か。行き先未定なら「何をしたい旅か」（温泉でだらだら／自然どっぷり／食べ歩き）から行き先候補を逆引きする
- **固定条件**: 日程、宿泊先（複数泊なら宿ごとに）、出発地、譲れない予約（ディナー時間など）
- **移動の制約**: 使う交通手段の候補（バス／新幹線／車）、キャンセル・変更のしやすさが必要か
- **同行者の身体的制約**: 妊娠中（週数）／高齢者／子連れ／持病など。これは配慮の中心になるので、聞き出したら明示的にメモし、以降の全フェーズの判断に反映する
- **食事の制約**: アレルギー、妊娠中の食事制限（生もの・非加熱食品など）、素泊まりかどうか
- **好みの方向性**: 「自然」「カフェ」「スーパー」など、ふわっとした要望も具体的スポットに変換する材料として保持する

この段階の情報が後から変わること（宿の変更、素泊まりへの変更など）は普通に起こる。変更が来たら、その変更が導線全体にどう波及するかを都度再計算する（フェーズ2）。

## フェーズ1: プランニング — 候補地は必ず座標と最新情報で検証する

思い出したり一般知識で決め打ちしない。以下を徹底する：

- **好みからの変換**: 「カフェとスイーツのコンボ」のような抽象的な要望は、必ず具体的なスポット・時間帯に変換してから提示する。抽象的な要望をそのまま繰り返すだけの提案は価値がない
- **SNS・トレンド情報**: 「SNSで人気」「最近話題」系のスポットを提案するときは `web_search` で直近の評判と混雑状況を確認する。人気店は行列・予約困難の情報も添える
- **場所の実在・座標確認**: `places_search` で候補地の座標・営業時間・レビューを取得する。移動時間はここで得た座標から実際に計算・推定する（「なんとなく近い」で書かない）
- **営業状況の検証**: 有名店ほど「閉店した」「移転した」「臨時休業」の情報が古いまま知識に残っていることがある。目玉として提案する店は `web_search` で最新の営業状況を確認してから提示する。特に「久しぶりに聞く店名」「地方の単独店」は要注意
- **正式名称の記録**: スポットを採用したら、Googleマップ検索でヒットする正式名称（支店名まで含む。例「はつ花そば 本店」）を控えておく。フェーズ5のFunliday出力で必須になる
- **不確実な情報は断定しない**: 定休日の記載が情報源で割れる、口コミに「閉店では」という声がある等、確信が持てない場合は正直にその旨を書き、電話確認を促す

## フェーズ2: スケジューリング — 「移動」を一級市民として設計する

スポットの羅列ではなく、区間ごとの移動手段・所要時間を明示する：

- 各移動区間は「手段・所要時間・（あれば）料金」をセットで書く
- 移動手段の種類ごとに視覚的に区別する（アーティファクトでは線種で表現）
- 妊娠中・高齢者・子連れが同行者にいる場合は、徒歩区間は15分を目安の上限とし、超える場合はタクシー等への切り替えを提案する
- 子連れの場合はさらに、ベビーカーで通れる導線か（階段のみの駅・砂利道・急坂を避ける）、授乳・おむつ替えできる施設の位置、昼寝・食事の時間帯を崩さない行程かを確認する
- 食事のタイミングに制約がある場合（「18:30ディナーだから14:00までに済ませる」等）は、それを起点に前後のスケジュールを逆算する
- 宿の変更・スポット追加など変更が入ったら、影響を受ける区間の移動手段・所要時間を再計算してから反映する。「前の行程に後から挿入するだけ」で済ませず、座標ベースで妥当性を確認する

## フェーズ3: アクセス・予約 — 予約が必要なものを洗い出す

スケジュールが固まったら、実行に必要な予約・確認事項を漏れなくリスト化する：

- **要予約の交通**: 新幹線指定席・特急・レンタカー・空港連絡バスなど。繁忙期（連休・お盆・年末年始）は予約開始日と売り切れリスクも添える
- **要予約の施設・店**: 予約必須のレストラン、時間指定チケット制の施設。同行者の制約（妊娠中の旨を店に伝える等）を予約時に伝えるべき内容として明記する
- **キャンセルポリシー**: 体調変動リスクがある同行者（妊娠中・高齢者）がいる場合、キャンセル可能な予約を優先し、キャンセル期限をチェックリストに入れる
- **予約・確認リンク**: 実際に踏める公式URLをまとめる。存在しないURLを捏造しない

## フェーズ4: お土産 — ルート上の購入ポイントまで設計する

お土産は「何を買うか」だけでなく「いつどこで買うか」まで導線に組み込む：

- 渡す相手（職場／家族／自分用）と個数感を聞き、地域の定番＋相手の嗜好に合う候補を出す。日持ち・要冷蔵・かさばりを必ず添える
- 購入ポイントはルート上（駅・空港・SA・観光地の本店）から選び、タイムラインの該当箇所に「お土産購入」として組み込む。最終日の駅でまとめ買いできるなら道中で荷物を増やさない
- 同行者に身体的制約がある場合、重い荷物を持つ時間を最小化する（購入は帰路直前、または配送サービスの利用を提案）

## フェーズ5: アウトプット — アーティファクト＋Funliday取り込み用テキスト

最終出力は必ず2点セットで提示する。

### 5-1. インタラクティブなReactアーティファクト

`create_file` で `.jsx` を作成し `/mnt/user-data/outputs/` に配置、`present_files` で提示する。構成要素：

- **ヘッダー**: タイトル・日程・宿泊先・交通手段の要約、バッジで制約条件（妊娠週数、集合時間の制約など）を可視化
- **移動手段の凡例**: 線種（破線=徒歩・二重線=バス・点線=タクシー・太線=新幹線/電車・波線=船/フェリーなど）を最初に定義し、タイムライン全体で一貫して使う。プランに登場する移動手段はすべて凡例に含める
- **日別タブ**: `useState` で日を切り替える。複数日プランでは必須
- **タイムライン**: 縦線に沿って「stop（滞在ポイント）」と「leg（移動区間）」を交互に配置。stopは時刻・タイトル・説明・タグを持ち、legは移動手段のスタイルを継承する
- **選択トグル**（該当する場合）: 素泊まりで夕食未定、雨天代替、体調による短縮案など、未確定の分岐は片方を決め打ちせず、ボタンで選べるようにして選択に応じてタイムラインが動的に変わるようにする
- **チェックリスト**: フェーズ3で洗い出した予約項目をチェックボックス付きで並べる（`useState` 保持。閉じるとリセットされる旨を明記）
- **予約・確認リンク**: 実際に踏める外部URLのみ
- **Tips/切り替えプランのカード**: 同行者への配慮事項、雨天時の代替案、体調不良時の短縮案

### 5-2. Funliday取り込み用テキストブロック（必須）

アーティファクトとは別に、Funlidayアプリへ持ち込むためのプレーンテキストをコードブロックで出力する。

**書式ルール**：

- スポット名は必ず **Googleマップ検索でヒットする正式名称**（支店名まで含む）。通称・略称・「〇〇のあのカフェ」は禁止。検索でヒットしない名前はFunliday側で場所登録できない
- 1行1スポット、`HH:MM スポット名` の形式。日別に見出しを付ける
- 宿泊先は各日の末尾に `（宿泊）` を付けて入れる
- **移動手段の行は入れない**（Funlidayが座標から自動計算するため、書いても取り込まれずノイズになる）
- メモ・注意事項・お土産リストは同じブロックに混ぜず、別の「メモ用」ブロックに分ける（Funlidayのスポットメモ欄に個別コピペする用）

**出力例**：

```
■ 箱根 2泊3日
【1日目 2026-08-10】
09:00 小田原駅
10:00 はつ花そば 本店
13:00 箱根神社
15:30 箱根湯本温泉 ホテルおかだ（宿泊）
【2日目 2026-08-11】
09:30 箱根海賊船 元箱根港
11:00 大涌谷
14:00 ラ・テラッツァ芦ノ湖
15:30 箱根湯本温泉 ホテルおかだ（宿泊）
```

**取り込み手順の案内**（テキストブロックの直後に毎回添える）：

1. Funlidayアプリの「AIプランナー」を開き、入力欄に上のテキストを貼り付ける
2. **スポットと訪問順は取り込まれるが、時刻はFunliday側で再計算され、指定したHH:MMどおりにはならない**（2026年7月 実機検証済み）。「18:30ディナー予約」のような譲れない時刻はFunliday上で手動調整が必要になる旨を必ず案内し、正確な時刻はアーティファクト側を正とするよう伝える
3. うまくマップ化されない場合は、スポット名を1件ずつFunlidayの検索に貼って追加する（正式名称なので確実にヒットする）
4. ※FunlidayのURLインポートはChatGPTの共有URL専用（2026年7月時点）。Claudeの共有URLは非対応の前提で、テキスト貼り付けを基本経路とする

時刻が取り込まれない仕様でも `HH:MM` は書き続ける（訪問順の解釈を安定させ、個別検索での代替時や人間が読むときの手掛かりになるため）。

## よくある落とし穴

- **「アーティファクト」という言葉の曖昧さ**: ユーザーが「アーティファクト」と言うとき、claude.ai上でチャット内に描画されるReact/HTMLコンポーネントを指していることが多い。迷ったらインタラクティブなReact（.jsx）で作る。Claude CodeのURL形式アーティファクトは別製品であり、claude.aiの通常チャットからは発行できない
- **一般知識だけで店舗情報を断定しない**: 学習データの時点で存在した店が今も営業しているとは限らない。特に「SNSで人気」「地方の名店」系は変化が速い
- **変更の影響範囲を過小評価しない**: 宿泊先や交通手段が変わったら、連鎖する移動時間・チェックイン時間・食事時間まで一通り再計算する。差分だけ直して整合性が崩れたまま提示しない
- **Funliday出力のスポット名を雑に書かない**: 「昼食: おそば屋さん」のような行はFunlidayで場所解決できない。フェーズ1で控えた正式名称をそのまま使う。逆に、アーティファクト内の表示は読みやすい通称でよい（用途が違う）
- **好みの言語化を怠らない**: 抽象的な要望は必ず具体的なスポット・時間帯に変換してから提示する
